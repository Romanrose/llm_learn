# 从多样性到效率：CS329A 最后一讲勾勒的自我改进智能体研究前沿

## 导语

Stanford CS329A「Self-Improving AI Agents」的最后一讲没有引入新的算法框架，而是做了一件更难的事：把整个学期讲过的技术线索收拢起来，指出哪些环节已经跑通、哪些环节正在成为瓶颈、哪些问题还没有人给出好答案。讲者把未来研究方向组织成两大板块——一是如何让自我改进循环本身变得更强（推理链的多样性、验证的可靠性、训练任务的选择），二是智能的效率问题（当推理本身成为成本，算力该放在云端还是本地）。这篇 Blog 沿着这两条线索展开，并说明它们如何嵌在这门课的整体学习路径之中。

## 一、这门课的知识地图：自我改进循环的三个抓手

要理解最后一讲为什么挑出这几个方向，先要回到课程的整体结构。讲者在回顾中给出的主线是：从 LLM 概览出发，讲测试时扩展（test time scaling）与训练时扩展（train time scaling）如何借助自我改进技术推进；其基本循环由验证器（verifier）驱动——运行验证器获得反馈与奖励，再用强化学习乃至搜索算法，帮助模型在数学、编程等任务上做爬山式优化。这是课程前半部分的核心。

随后课程扩展了循环的形态：进化策略与开放性（open-endedness）让模型不只被奖励驱动，还能在被定义的探索空间中主动探索，Alpha Evolve 是这一部分的代表；再往后是工具使用驱动的端到端智能体工作流——当任务跨越多步、需要查知识库时，检索与记忆成为必需，规划与多步推理能力也随之变得关键，评估下一代模型能力的方式也因此需要重新设计。课程后段还包含后训练、多模型智能体、机器人学、推理等客座讲座，其中一位客座讲者专门讲了符号技术（symbolic techniques），它属于工具使用的大类，并能服务于合成数据的生产。

讲者特别提醒了课程名字的重心：这门课不只聚焦 LLM，而是聚焦其中的智能体层面。智能体是 LLM 的一种泛化——它有目标，与环境交互、收集反馈，并用反馈纠正自己的步骤。在当前范式下，LLM 本身往往还不足以驱动完整目标，所以很多系统是手写的工作流，在其中编排 LLM、验证器（有时让 LLM 充当评判者）、工具调用和搜索算法。也正因为工作流要朝目标推进，它才需要规划、多步推理、走错时自我纠正，以及在整体上持续提升能力——这正是「自我改进」这一层面发挥作用的地方。最后一讲的全部内容，都可以看作是对这个循环中各个接口的追问。

## 二、第一组前沿：多样性、验证与任务选择

### 多样性：单模型生成会枯竭，多智能体是「免费的」多样性

第一个方向针对的是推理链的多样性。讲者先铺陈背景：预训练是对互联网规模数据的压缩，指令微调往往需要真实人类偏好数据；替代方案是用 LLM 生成合成数据（synthetic data），做迭代微调——生成可能的解、过滤掉不正确的解，即拒绝采样（rejection sampling），只在好样本上微调。课程讲过的 STAR 就是这类变体，还可以把推理链纳入这个过程。

但问题在于：如果由单个大语言模型生成数据，它会产生非常相似的解，性能提升往往在几轮或几十轮迭代后停滞，根源是缺乏多样性。对比之下，预训练数据之所以多样，是因为它由人类在很长时间里生成。即便在高温度下，单个模型对一组提示词的输出也不会有很大多样性。

于是有了那篇多智能体微调（multi-agent fine-tuning）的论文：用多个专门化的生成智能体产生多样化的初始解，再用评论智能体（critic agent）评估和精炼。具体流程是——每个生成智能体先给出初始答案；后续步骤中，它总结并获取所有其他智能体回答的摘要，作为生成下一个回答的一部分；评论智能体则批评这组更新后的答案。与课程已熟悉的做法相比，关键差异在于：不是批评单个智能体的回答，而是使用多个智能体的回答并对其专门化和总结，从而在批评之前就获得了多样性。用讲者的话说，仅通过拥有多个智能体就「免费」获得了多数投票，假设这些智能体训练方式略有不同，也就免费获得了多样性。生成模型从相同基础模型微调而来；评论模型在混合轨迹上微调——答案开始时正确、在辩论过程中被纠正——因此它学到的是对比正确与错误答案。轨迹随后可用来微调不同的评论模型。

结果层面，讲者展示的指标是：横轴为微调迭代次数，纵轴为负对数似然（性能代理）或嵌入不相似度（越高越多样）。在多智能体微调下，开源模型能持续提升性能并保持回答的多样性，而单智能体微调则会准确率崩溃或不再提升；在数学数据集上尝试的三个开源模型中，Llama 3 对这种技术似乎更敏感；并且方法能泛化到训练域之外——在 GSM8K 这类相邻领域上，微调后的智能体表现出更高性能（讲者注明该工作稍早，数字不是那么高）。结论很直接：若要自我改进，驱动改进的推理链需要在某种程度上具有多样性，而多模型/多智能体生成是产生这种多样性的一种技术。

### 验证：LLM as a judge 不够，需要元验证

第二个方向是验证，课程此前已有专门一讲。讲者重申了难点：通常只看结果——数学题或定理证明看最终答案是否与真实答案匹配，这就是结果奖励模型；但即使答案正确，推理未必正确，而过程奖励模型非常难以构建。更麻烦的是，大型语言模型通常在定量推理上训练，它们可能生成数学上无效的证明，而且如果让它们去验证，它们会声称那些不正确的证明是有效的——LLM as a judge 在这里并不太管用。相反，专家人类能在没有参考解答的情况下查看证明，指出下一步不能从上一步推出，或引用中存在推理缺口。

DeepSeek-Math V2 的思路是训练验证器而非仅仅训练奖励模型，并引入元验证器（meta verifier）。架构上，在熟悉的生成器—验证器循环之外增加一层：元验证器审查验证器的分析是否合理、证明是否存在问题；验证器被训练来接收这些问题，并以 0.5 到 1 的尺度给证明打分；验证器再改进生成器，生成器生成更难的证明，又反过来改进验证器。另一个有趣之处是数据自动化：一旦播种了用于发现不正确证明的数据，元验证器开始学习后，就不必仅依赖人类来识别证明中的问题。讲者解释了元验证的一般价值：验证器在推理链不正确时可能得到正确分数，甚至编造错误；元验证评估的是「这些被识别出的问题是否真的存在、分数是否从这些问题中得出」，再由专家标注这个评估的质量——仅仅添加这个额外模块就能提高质量。

结果上，该工作构建在 DeepSeek V3 基础模型之上（讲者提到很多 RL 循环通常建立在 GRPO 之上，此为特定案例），在 IMO 问题和 CNML 问题上做基准测试——讲者注明此前一位客座讲师展示过 Gemini 版本，这是近期发布的开源版本。八次迭代中，仅用正一（+1）的证明分数就随迭代循环持续攀升；在 best-at-32（从 32 个生成的证明中挑选最好解答）设定下，几乎达到 2024 年 IMO 短名单证明分数 42%。讲者称之为相当有前景的爬山技术。其洞察是：最好的证明获得更高验证分数，生成器能学会区分高质量与有缺陷的证明，自我验证因此可以形成更好的改进循环。若要推广到其他领域，需要的条件是：让基于 LLM 的验证器在没有参考解答的情况下识别问题；用某种元验证模块降低验证器幻觉问题的可能性；并给生成器额外激励，通过深思熟虑的推理最大化质量。讲者也坦率指出边界：这仍然受限于验证相对容易的领域。

### 任务选择：让模型自己出题，把数据壁垒变成课程学习

第三个方向是「用什么数据、什么提示来训练」。讲者先描述现状：当前 AI 训练栈要么用人工策划的推理轨迹（监督学习阶段），要么在带可验证奖励的强化学习中由专家策划问答对——数学领域要数学专家，IMO 问题要 IMO 专家，编程要强程序员。随着模型继续超越人类智能，找到越来越多专家和此类任务的能力开始受限。

那篇被讲者称为「还没有被广泛使用，但相当有前景」的论文，提出单一模型同时提出任务并解决它们，几乎走向另一个极端：不需要外部数据来源，不需要人类生成的提示来帮助攀升。工作聚焦 coding 领域，构造三类任务：溯因（abduction）、演绎（deduction）和归纳（induction）。proposal 阶段基于这些任务类型构造任务，并提出一个 reward 来选择哪些任务有意义；solution 阶段进行验证，并有 accuracy reward，帮助对模型本身做联合更新而非单方面更新。

三类任务的编程范式很具体：deduction 任务生成程序和输入，环境执行得到输出；abduction 任务类似，同样生成程序和输入、由环境计算输出；induction 任务则采样一个已有程序，为它生成新的输入，外加一条描述该功能的自然语言消息，环境执行并某种程度上决定这是否朝正确方向走。proposer 会以过去生成的、被显式 prompt 的例子为条件，以促进多样性。

任务如何被选中？proposal 基于优化任务难度获得 reward：如果 solver 在新任务上成功率为零，reward 为零；如果成功率非零，则 reward 为一减去平均成功率。换言之，要选的是既非平凡也非不可能、solver 有时成功有时失败的中等难度任务——这通常有助于模型学习。proposer 的目标就是在当前模型权重下生成最优难度的任务，随着模型变强，proposal 应学会提出更难的问题。有效性保障方面：在 coding 抽象中可以运行程序完整性检查、实际执行看是否有错误、做安全检查，并确保多次运行输入得到完全相同的输出；提出的任务在进入训练流水线前会被验证，以防 proposal 作弊想出垃圾任务。此外维护一个任务 buffer：每个三元组（输入、输出、程序）加入 buffer，proposer 可从中采样参考，buffer 连同模型在该任务上成功或失败的次数一起保留——这引向随时间演化的课程学习（curriculum learning）思路。

结果与涌现行为：在 coding benchmark 上达到 state of the art，且在 prompt 侧没有任何人工整理的数据，超越在数万个专家示例上训练的模型；复杂度指标随时间增加；循环设置正确时，程序和答案的多样性改善，proposer 越来越多地生成越来越难的任务。讲者把 proposer 与 solver 的关系比作某种博弈论式的对抗，但总体上彼此帮助改进。值得注意的是，尽管只在自我提出的 code 任务上爬山，他们在 coding 和 math benchmark 上都看到了强劲表现——讲者称这在 math 上的结果实际上令人惊讶，但可由该领域已见到的其他结果解释；总体而言更大的模型相对更小的模型获得更大收益。

在讨论环节，另一位讲者补充了呼应证据：课程讲过的 Swirl（用合成数据做逐步 RL）发现，模型生成自己的训练数据不仅能改进生成发生的那个任务，还能提升可迁移性——在 Swirl 中是在带检索的多跳问答上训练，但随着更多合成数据生成和 RL 训练进行，模型在调用 Python、解决数学问题等其他工具调用上也变得更好，反之亦然；并且同样观察到更大的模型似乎更擅长吸收这种数据飞轮、更能通过它泛化。这引出一个更宏观的研究问题：我们能在多大程度上仅基于可生成合成数据的可验证领域推进自我改进前沿，并泛化到没有自动验证的领域——能否在可验证领域让模型越来越聪明，从而最小化甚至消除非可验证领域对标注数据的需求。讲者称这是一个有趣但非常计算密集的研究实验。

课堂提问进一步触碰了「非可验证领域」的边界。讲者举的例子包括：科学发现中运行需要几天才能完成的芯片设计仿真以收集奖励信号，或需要去湿实验室实际运行、看输出质量或奖励的化学实验——这类领域验证非常慢，而 RL 微调或测试时扩展需要验证器几乎即时，或许可以等几分钟、允许一小时，但 RL 训练需要数百到数千步迭代，不可能等几天或等一个人在循环中收集奖励。另一位讲者补充：真正不可验证的还来自创造力或任何有主观性的指标，比如创意写作——设计精确的奖励函数困难，而且如果模型稍微偏离基础，RL 或智能体可能做奖励黑客攻击（reward hacking）。对于「人们如何尝试解决」，回答是训练一个单独的奖励模型来预测仿真结果：离线收集大量数据，学习对给定输入预测输出质量，再用它作为 RL 优化循环中的验证对象；但奖励模型的泛化性是数据量的函数，且可能不准确，从而带来问题。还有一条更贴近课程的补充：即便在芯片设计之前，kernel bench 这类工作中，编译器执行能告诉你是否生成了正确代码、能拿到一些指标，但课程项目尝试在事物变复杂时读取性能分析（profiling），那是更难的问题；通常的解法是把问题分解成子部分、让模型看每个部分、并提供参考解决方案以查看知识库——讲者说自己描述的正是这样一个课程项目，说明当问题难度足够大而模型能力未及时，需要以有趣的方式分解问题来适配模型现在能做的事。

## 三、第二组前沿：智能的效率与「每瓦智能」

讲者用一句话完成转折：我们可以做自我改进，但你现在做了更多推理，而这种智能是有成本的。随后由另一位讲者介绍与 Ray 教授、John Hennessy 教授及多位合作者完成的工作，研究模型侧与硬件加速器侧的趋势，思考未来 AI 推理工作负载在模型规模类型与所需加速器类型上会如何呈现。

讲者把当下称为大型机时代：我们使用的 ChatGPT、Gemini 背后的大语言模型都在云上运行，因为模型很大；有些甚至无法访问、是专有的；即便是开源大模型，我们仍用云来运行。需求侧因此爆炸式增长——讲者给出的说法包括 Google Cloud 计算服务在过去 12 到 20 个月内增长约 1200 倍、英伟达有 10 倍的年同比增长，以及满足现在需求大约需要 250 吉瓦的数据中心；右侧图表是 Google 已处理 token 数量：去年二月 160 万亿，今年十月 1.3 千万亿。讲者称这是历史上所见增长最快的算力需求之一。

但工作负载侧有另一面：从 ChatGPT 用户这一超大规模数据集看，约 77% 的请求是实用指导、信息查询、写作等任务，其中很多并不需要最前沿的模型，更小的本地模型就可以处理。用户会随着聊天机器人变好而提出更复杂的问题，但绝大多数查询类型仍处于复杂度较低的一侧。与此同时，本地推理加速器在改进：从 2012 年到现在，本地加速器 GPU 内存大约有 126 倍提升，如今 MacBook 笔记本可有约 100 GB 内存，意味着若以量化版本（比如 8 位）服务，一些最大的模型也能本地部署。这两股趋势——大量查询可由更小模型处理、本地硬件可容纳大模型——共同提出了问题：本地推理在重新分配推理需求中可以扮演什么角色？现在几乎所有流量都流向云端加速器，但趋势表明也许可以做得不同。

为了系统研究，他们定义了一个新指标：每瓦智能（intelligence per watt）。能力侧看模型在单轮和推理类查询中可处理的查询百分比；本研究中「本地模型」指活跃参数在 200 亿或以下的模型。效率侧看本地硬件上每瓦能获得多少有效算力。简言之，每瓦智能是平均任务准确率除以模型解决该任务的平均功耗。研究覆盖 20 多个本地模型（如 quant、GPTQ、llama 3 等）、企业级与本地加速器、来自 ChatGPT 的 100 万条查询以及其他推理基准（如 natural reasoning、MMLU Pro、Super GPQA），评估指标包括准确率、能耗、延迟、使用的算力等，并开源了跨不同底层模型与硬件基底的指标。

发现有三点。第一，本地模型不仅已经非常好，改进趋势也很陡：自 2023 年以来，准确率或它们能解决的聊天查询比例提升 3.1 倍，仅发生在两年内；它们现在能处理前述查询中约 88.7% 的比例。第二，本地加速器在效率上落后于企业级芯片，例如 Apple M4 Max 的每瓦智能比 B200 低约 1.5 倍——原因是 B200 极度针对运行语言模型负载优化，而 Apple M4 也针对运行 AI 指标优化，但还优化其他类型工作负载；总体而言，设计这些芯片时并未预想到 LLM 会在本地运行，芯片设计者的主要焦点在云端规模芯片上。第三，智能效率（该指标）在过去两年约提升 5.3 倍，其中 3.1 倍来自更好的模型，1.7 倍来自硬件改进。这些趋势指向一个未来：越来越多流量可由边缘设备上的模型处理——笔记本电脑，或未来的手机。

由此展开的开放方向包括：测试时扩展的基础原则——当我们通过测试时扩展反复向模型提问时，从模型角度到底发生了什么使得正确答案涌现，把成功轨迹蒸馏回模型的最佳实践是什么；从合成数据飞轮（synthetic data flywheel）到持续学习（continual learning）的清晰衔接路径——人类在解决问题、学习新事物时有持续性的进步，而模型主要是一个离线过程（智能体产生经验，过一段时间再微调），这种人类行为与模型行为的不匹配正是持续学习可能回答的问题，即能否把正面经验、从负面经验中的学习以更自然的方式带回模型，而非当前异步的数据生成再微调的范式；以及高吞吐低延迟的测试时扩展基础设施（infra）——重复采样、生成更新之间的来回迭代、工具调用，与主流聊天机器人以单轮交互为主的使用方式非常不同，这意味着系统和推理优化有大量机会，讲者提到其实验室的 hydrogen、Tokamak 等工作在未来会再次变得重要。

讲者用一张图收束：预训练那里有很多有趣工作，这门课涉及较少（尽管合作讲者是预训练专家），课程主要聚焦后训练（post-training）与测试时扩展方法；而合成数据飞轮与持续学习是一个新近被释放出来的领域，发生在微调、在线学习与测试时扩展的连接处。围绕每瓦智能与「从一切在云端转向更多本地」的观察，还暗示了推理服务引擎的新方向：按需求与资源复杂度，在本地与云端的模型和加速器之间平滑路由流量；以及面向能效推理的新模型架构与 kernel——尤其是本地加速器上，这是相比云端加速器关注度少得多的领域。讲者强调，能源将成为未来最有价值的资源，像每瓦智能这样的指标，以及更好地理解、测量能源、瓦特与功耗并为之优化，将再次非常重要，而这是目前目标优化指标方面关注较少的领域。

## 四、问答中的两个延伸：持续学习的多种实现路径

课堂提问把「持续学习」的讨论推向实现层面。被问及这更多会体现在长期记忆系统与架构中，还是模型本身时，讲者的回答是：持续学习可能涉及长期记忆系统——那是人类的类比——但在那之前，即便在多步推理中从成功或失败中学习、让模型保持那套技能并以有用的方式更新权重或权重子集，比如「你能学习一项新技能吗、你能学会如何学习吗」，都是我们目前基本上不具备的重要能力；机器人领域正在尝试的是，何时能看如何做某事的视频就学会怎么做，而不是被给予大量任务演示。另一位讲者补充了另一条路径：上下文学习（in-context learning）也是使能持续学习的一种方式——想象有一个无限上下文，模型能完美访问其中每一部分并从中学习一切，那也许就是持续学习的一个解决方案，可以把所有正面和负面的东西放进上下文同时记住并推理；但我们没有那个，而且即便是一百万或几百万的上下文，模型对上下文内数据的推理能力也会减弱。课程中讲过的 cartridge 是另一种方式：不改变模型权重、不做微调，而是把它们带入激活中，或在这个例子里带入模型的 KV cache 中。所以，大规模增加有效上下文长度（effective context length）也可能是实现记忆、长期记忆与持续学习的另一条路。

追问「实践中哪个更容易：不断更新权重还是更新记忆存储」时，回答取决于应用场景：更新记忆存储当然可以说更容易——如果它是一个知识库，最朴素的做法是维护一个 LM 可以学会查询的数据库，直接更新数据库即可；但你真正想教给模型的是在新领域上进行推理的能力，旁路记忆系统通常不能完全实现这一点，这就是更新权重更好的地方。机器人学的例子被再次引用：无论添加多少记忆系统，已经学会的跨具身泛化（cross-embodiment generalization）若不更新语言模型权重、仅靠记忆系统是不会发生的——那更多是技能迁移的问题。

另一个问题涉及「绝对零」（absolute zero）那篇论文中智能体自我创建环境。讲者的回应是把问题拉回任务表示：在窄人工智能的世界里，你可以为游戏创建模拟，那些环境被用作玩具任务；环境在当前这一代之所以重要，是因为它们是真实世界任务的代理。所以关键不是「让智能体自我创建环境」这件事本身，而是你试图表示的任务集合是什么；如果有简单方法模拟它们，无论用智能体还是用软件创建都相当直接，真正的问题是它是否是模型与真实世界交互获取反馈的合理代理。对游戏而言，它是一个有限的可探索空间，所以更容易用代码表示并模拟。

## 五、这一讲在课程路径中的位置

把最后一讲放回课程结构，可以看到它承担的是「收口」与「指路」两件事。课程前半段建立了以验证器为枢纽、以测试时与训练时扩展为两个杠杆的自我改进循环，并用进化策略与开放性拓宽了探索的维度；中段把循环嵌入工具使用与多步工作流，讨论检索、记忆、规划与评估；后段通过客座讲座覆盖后训练、多模型智能体、机器人学、推理与符号技术。最后一讲则指出：这个循环的三个接口——喂给模型的推理链是否有足够多样性、验证器是否可信、训练任务由谁挑选——都还没有被真正解决，而这三者恰好对应本讲前三篇论文。与此同时，讲者提醒大家，循环跑得越多，推理的代价就越大，于是效率问题从「工程细节」上升为研究方向，每瓦智能这样的指标把能力与能耗放在同一个分子分母里衡量，并引出本地与云端之间的流量重分配、能效架构与 kernel、能源测量与优化等一系列问题。

讲者在结语中的自述也印证了这种定位：这门课教的内容不断在发展，现在教的东西到下次开课时就开始成为历史，但基本技术随时间推移极其有价值，因为很多新东西仍然建立在基本技术之上。另一位讲者补充说，备课过程本身也是学习，因为这些主题非常新，希望这门课只是开始。就学习路径而言，最后一讲实际上给出了一张「接下来可以做什么」的地图：如果你关心循环的上游，就去做多样性、元验证、任务自提议；如果你关心循环的成本，就去做测试时扩展的原则、合成数据飞轮与持续学习、以及面向测试时扩展的系统与推理优化；如果你关心更远处，就去碰那些验证很慢甚至主观的领域——科学发现、芯片设计仿真、湿实验室、创意写作——并为它们设计奖励模型或问题分解策略，同时警惕奖励黑客。

## 结语

这门课的最后一讲没有给出「终极答案」，而是把自我改进智能体拆成几个可以被单独攻击的瓶颈：多样性决定循环能不能持续爬坡，验证决定爬的方向对不对，任务选择决定坡在哪里，而效率决定这场爬坡能持续多久、在什么硬件上发生。课程中的具体例子——多智能体辩论带来的「免费」多样性与跨域泛化、DeepSeek-Math V2 的元验证器与 best-at-32 下的证明分数、proposer 与 solver 在中等难度任务上的对抗式共进、以及每瓦智能背后本地模型处理约 88.7% 查询与两年 5.3 倍效率提升的观察——共同说明一件事：自我改进不是单一算法，而是一条由数据、验证、任务与算力共同构成的流水线，任何一环的短板都会成为下一轮研究的起点。
