# CS329A Lecture 2 笔记：Test-time Compute Scaling

## 学习目标

- 理解 LLM 生命周期中预训练、微调、推理三个阶段的计算分布变化，以及“在推理阶段投入算力”这一新范式的含义。
- 掌握 repeated sampling（重复采样）+ verifier（验证器）的基本框架，理解 coverage 与样本数之间的幂律关系及其成立条件。
- 区分并行扩展（parallel sampling）与顺序修订（sequential revisions）两类 test-time scaling 手段，以及 outcome reward model / process reward model 在选择答案中的作用。
- 认识 generation-verification gap（生成-验证差距），理解为什么没有可靠验证器时 best-of-N、majority voting 会受限。
- 了解将多种推理时技术组合成“推理架构”的思路（Archon 框架），以及难度分桶实验关于“简单/中等题适合 test-time scaling、极难题仍依赖更强预训练模型”的结论。

---

## 课程主线

本讲从“无限猴子”比喻切入：同一个问题反复问模型多次，再用验证器挑出正确答案，可以显著提升较弱模型的表现。由此引出两条线索：

1. **科学问题**：repeated sampling 的收益为何呈现幂律？需要什么条件？
2. **工程问题**：如何分配推理算力（并行采样、顺序修订、奖励模型引导搜索、多技术组合）才能在给定预算下最大化准确率？

课程先用 scaling law 刻画 coverage 随样本数的增长，再讨论验证器的必要性与不同领域的可验证性，最后过渡到“推理时架构搜索”这一系统化视角。

---

## 核心概念

### 1. 三阶段计算分布的变化

传统流程：预训练（数据量与算力最大，历史上耗时数月）→ 微调（数据量少几个数量级）→ 推理（几乎不花钱，一次性问答）。新范式：推理阶段可以消耗多得多的算力，且可以离线完成——让 agent 持续生成 token、持续改进答案，而不改变模型参数。

### 2. Repeated Sampling + Verifier

对同一输入生成 K 个候选答案，由 verifier 判定哪个正确并作为输出。课程给出的经验观察：能力较弱的模型（如 Llama 3 8B/7B）通过重复采样加正确选择，可以在困难数学、编程、问答等任务上超过更大的专有模型。课程对此的解释是：小模型“其实已经知道答案”，只是第一次尝试时不说出来，重复采样把这些答案诱导出来。该范式在 agentic 基准（如模拟软件工程师改代码、打补丁的 SWE-bench 类任务）上同样成立：覆盖率随样本数（1 到 1000）上升，开源模型在足够采样后可以超过闭源模型——前提是有单元测试这类自动验证手段。

### 3. Test-time 的幂律缩放

课程给出类比：预训练有可预测的 scaling law（数据量、计算量、参数量 → test loss），推理阶段也可定义类似的缩放律。设 C 为 coverage（至少被一个样本解决的问题比例），K 为样本数，A、B 为拟合系数，则 coverage 与 K 之间遵循指数幂律关系，可用来预测“达到目标 coverage 需要多少样本、应分配多少资源”。课程展示该行为在约 7000 万到 700 亿参数的一系列模型（Llama 3 8B/70B、Gemma、Pythia 等）以及跨领域上都成立。

### 4. 幂律成立的条件：难题长尾

对单个问题 i，若 pass@1 为 P，则 K 个样本中至少一个正确的概率为 1 − (1 − P)^K——这是逐问题的指数关系，本身不是幂律。课程指出：要在问题集合上观察到幂律，充分必要条件是 pass@1 在问题上的分布存在**长尾**，即存在大量真正困难的问题（pass@1 很低）。经验上确实观察到：大部分题一次通过即解决，随着难度上升 pass@1 越来越低，形成长尾。

### 5. 验证器与可验证性谱系

- **易验证**：形式化数学证明（可用证明软件逐步检查）；编程（单元测试；课程指出写单元测试往往比写整个解法简单）；AI 作为编译器——用 LLM 从 PyTorch 源码生成 CUDA 底层代码，正确性可通过“任意输入下输出是否与源 PyTorch 一致”来判定（课程提到 KernelBench 数据集，并观察到覆盖率随采样数线性提升）；任意两种语言之间的翻译（衡量等价性较容易）。
- **难验证**：无验证器的领域。课程用 MATH（比 GSM8K 更难）等数据集展示：majority voting 在约 10–50 个样本后趋于饱和，与“完美验证器下的覆盖率”之间存在巨大差距，且差距在更难的问题上更明显；使用 reward model 或组合方法后差距仍然存在。这就是 generation-verification gap：模型能生成很多正确响应，但我们实际能捕获的比例有限。原因在于：最难的题在数千到上万个样本中可能只被正确解决一两次，稀有正确答案使多数投票无法捕获。

### 6. 两类扩展方式与三类选择机制

- **并行采样**：对同一输入生成多个答案。
- **顺序修订**：模型提出初始步骤/解法后不断修订、补充、换角度审视，直到准备输出；课程指出这可以是提示诱导的，而 reasoning models 已被训练出这种行为。
- **选择机制**：单元测试等程序化验证；outcome reward model（看最终答案给分）；process reward model（对解题的每一步给分，粒度是“有意义的步骤/句子”而非逐 token，通常也由语言模型训练而来，可通过人工标注每步好坏来训练）。PRM 可用于 best-of-N 打分，也可用于束搜索（beam search）：每层采多个样本，用 PRM 选得分最高的前几个继续扩展，用阈值控制分支。课程提到可用的预训练 PRM 已存在，也可针对目标任务自训；PRM 在同领域任务上效果更好，但因基于语言模型而具有一定跨任务泛化能力。课程还讨论了将并行与顺序结合的方式：对每个并行样本做顺序修订，再用 PRM/ORM 在最终答案间选择。

### 7. 难度分桶与“预训练 vs test-time”的分界

课程引用的论文在数学数据集（约 12k 训练集、500 测试题，PaLM 模型）上按 pass@1 定义难度，将问题分为五个桶。观察包括：不同难度下“顺序对并行的最优比例”不同（且从桶四到桶五仍会变化）；对简单和中等题，额外的 test-time compute 可能比扩展预训练更划算（推理 token 与预训练 token 的比率效应为正）；但对最难的题，更大/预训练更多的模型仍然更好，即使有可观（非无限）的 test-time 预算。课程强调：并非人人能预训练大模型，而 test-time scaling 是每次运行都可执行的可行手段；两者的权衡是真实的工程问题。

### 8. Archon：把 test-time scaling 当作架构搜索问题

问题陈述：给定目标基准集合、推理调用预算、可用 LLM 池、一组推理时技术，搜索如何组合它们以在预算下最大化质量。推理时操作包括：generation（直接采样）、fusion（把 K 个回答连同原问题交给 LLM 综合出一个答案——课程称其出乎意料地有效，甚至可超过 oracle selection）、critic（让模型指出回答的弱点/优势）、ranker（让模型对回答排序）、verifier（给分并给出打分理由）、单元测试生成与“单元测试评估”（不实际运行测试，而让模型依据测试评估答案）。优化器用贝叶斯优化，并做搜索空间剪枝（如第一层固定为生成器；critic 应在 ranker/fusion 之前；单元测试生成器后必须跟评估操作），在留出数据集上优化“准确率 vs 模型调用次数”的前沿。课程报告的观察：堆叠更多推理层（多模型集成、三层 critic+fusion、最终 fusion）能提升准确率；仅用开源模型即可匹配或超过当时的前沿闭源模型，在指令遵循、推理、数学、编程上平均 pass@1 提升 14.1%（课程给出的数字），且通用版架构在有限训练任务之外也表现良好。

## 关键公式与原则

- 逐问题覆盖率：对 pass@1 = P 的问题，K 个样本至少一个正确的概率为 **1 − (1 − P)^K**。
- 集合级幂律：coverage C 与样本数 K 遵循指数幂律，用系数 A、B 拟合，可用于**预测达到目标 coverage 所需样本量与资源**。
- 幂律成立的**充要条件**：问题集上 pass@1 分布存在**长尾**（大量极难题）。
- 原则一：**没有验证器，重复采样的收益会被 generation-verification gap 截断**；验证器质量决定方法上限。
- 原则二：**简单/中等题上 test-time compute 性价比高；最难题上更强预训练模型仍占优**（在合理预算内）。
- 原则三：并行与顺序不是二选一；组合、过滤后再 fusion、用 PRM 引导束搜索，通常优于单一手段。
- 原则四：把推理时技术组合视为**架构设计 + 预算约束下的优化问题**，用贝叶斯优化等方法在剪枝后的搜索空间中求解。

## 课程作业关联

- 课程明确提到：每个问题 10,000 个不同样本的数据集已在 Hugging Face 上可用，缩小 generation-verification gap 被点名为**潜在的研究项目**。
- 讨论环节提出的可研究方向：在可验证领域结合搜索/自学式探索再进入并行采样；利用“容易发现错误答案”的领域特性做进化式过滤（如物理/机器人模拟）；集成多个验证器做多数投票（计算上昂贵，课程提到他们相关工作用了约 10–20 个弱监督验证器集成）；手动检查数学答案的正确率作为验证器质量的参照（课程提到手动检查约 70–80% 通过，并提醒单元测试本身也可能覆盖不足）。
- 与后续课程的衔接：奖励模型/验证器（周一）、集成与弱监督验证器、超越重复采样的 test-time scaling（自学搜索、工具使用）。这些是理解作业与项目选题的背景。

## 常见误区

1. **把逐问题的 1 − (1 − P)^K 当作幂律本身**。它只是单题指数关系；集合级幂律需要 pass@1 的长尾分布作为条件。
2. **以为“采样越多越好”与验证器无关**。没有可靠 verifier，majority voting 会在少量样本后饱和，与 oracle 覆盖率差距巨大。
3. **把 PRM 理解为逐 token 打分**。课程明确说不是逐 token，而是按有意义的步骤/句子粒度。
4. **认为顺序修订必须专门训练**。任何指令微调模型在被提示后都能做修订；论文中微调只是选项之一。
5. **认为 test-time scaling 可以无条件替代预训练**。课程结论是分难度的：简单/中等题受益明显，最难题上更大模型仍更好。
6. **把 fusion 等同于投票**。fusion 是把 K 个回答交给 LLM 综合生成新答案，课程观察到它可超过 oracle selection（在“只选不混”的意义上）。
7. **忽视验证器的领域依赖性**。CUDA 生成、语言翻译之所以可规模化，是因为存在近乎完美的自动等价性检查；跨到无验证器领域，方法要重新设计。
