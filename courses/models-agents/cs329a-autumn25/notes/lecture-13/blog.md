# 让智能体改写系统代码：三篇论文看 LLM 如何从“生成代码”走向“优化系统”

## 导语

“AI 写代码”早已不是新鲜话题，但“写得对”和“写得快、跑得省”之间隔着一条很深的鸿沟。本文依据三篇官方论文的公开文本，分别讨论三条不同的技术路线：CodeMonkeys 把测试时计算（test-time compute）的规模扩展系统化，用于解决真实 GitHub issue；KernelBench 用一套可自动验证的基准，测量语言模型能否写出又快又正确的 GPU kernel；以及一篇关于“Agent-System Interface”的工作，用领域特定语言与可解释反馈，让 LLM 优化并行程序的 mapper（任务到处理器、数据到内存的映射）。三篇论文共享一个核心问题：当模型的原始能力有限时，系统设计——如何组织上下文、如何提供反馈、如何选择结果——能在多大程度上补足模型？下面逐篇展开，并在每处区分“论文的主张/实验”与“笔者的解释”。

---

## 一、CodeMonkeys：把“多试几次”变成一套工程

### 1.1 问题设定与三段式分解

论文针对 SWE-bench Verified 展开：每个实例给出一个 issue 描述和对应代码库，目标是编辑若干文件以修复问题，正确性由仓库测试套件自动判定。作者把解题过程拆成三个子任务，并给出各自的度量：

- **Context（上下文）**：能否把需要修改的文件放进上下文窗口，用 recall（所需文件全部被找到的比例）度量；
- **Generation（生成）**：在采样的候选编辑中是否存在正确解，用 coverage 度量；
- **Selection（选择）**：能否从候选中挑出正确的那一个，用最终得分度量。

这是一个很值得注意的方法论选择：论文主张，把“端到端分数”拆成三个可独立测量的量，才能定位瓶颈。论文同时提醒，三个子任务并不独立——例如生成更多候选会提高 coverage，却让选择更难。

### 1.2 上下文：先扫描、再排序、可摊销

论文的上下文方案相当“朴素”：用一个较小模型（Qwen2.5-Coder-32B-Instruct，本地运行）阅读代码库中的每个 Python 文件（排除测试目录），判断其是否与 issue 相关。论文报告，该扫描平均每个问题处理 2.94M token，但由于每个 issue 只运行一次、供下游 10 个候选共享，其成本占系统总成本不到 15%（成本表显示 Relevance 一项约 334.02 美元，占 14.6%）。

随后是排序压缩：先生成每个相关文件的摘要，再让 Claude 3.5 Sonnet 对文件排序（论文称温度设为 0 时 API 仍可能不确定，因此重复三次取平均排名），按排名纳入文件至 128k token 上限。论文报告：在 128k 限制下，92.6% 的实例中所需文件在上下文内；平均上下文约 74,570 token，相对“纳入所有被判定相关的文件”平均压缩约 50.5 倍。

**解释**：这里的洞察不是“扫描每个文件”本身多聪明，而是**并行采样让一次性成本可以被摊销**——这正是“为扩展 test-time compute 而设计系统”与“给现成系统加采样”的区别。

### 1.3 生成：测试与编辑的双状态机

论文采用状态机抽象建模多轮交互：模型在每轮获得执行反馈，可修改产出或“批准”并终止。关键设计是**强制模型在给编辑的同时写一个可执行的 Python 测试脚本**（以退出码表达 issue 是否复现）。作者给出的理由是：这提供更丰富的反馈以支撑串行扩展，且测试可作为后续选择的不完美验证器。

论文把生成拆成两个前后衔接的状态机：先在**无代码库上下文**的情况下迭代出初始测试脚本（降低 prompt 长度与缓存读取成本），再进入编辑状态机，在上下文与测试的基础上迭代编辑，并允许继续修改测试——论文称之为“双边调试”：测试需在未编辑代码上失败、在编辑后通过。论文报告：每个实例运行 10 对状态机，每个状态机最多 8 轮迭代，最佳配置 coverage 达 69.8%。

关于串行与并行的关系，论文的表述很克制：在成本相近时，不同分配方式常得到相近的 coverage（“前沿”现象），但这**不意味着两者可完全互换**——相同 coverage 不保证相同最终得分；且串行扩展只是间接可控，模型可能提前“批准”而卡死，而并行扩展总能再开一个“全新开始”。

### 1.4 选择：测试投票 + 选择状态机

论文比较了四种选择方法：测试多数投票；模型直接选择；先用测试通过数筛到前 3 再由模型选择；以及把单轮选择升级为完整状态机（可写新测试来区分候选，并观察测试在各候选及未编辑代码上的执行输出）。论文报告：四种方法都优于随机选择（随机期望 45.8%），最佳组合（前 3 过滤 + 选择状态机）使最终得分达 57.4%，约占随机与 oracle（69.8%）差距的一半；选择阶段占总成本不到 10%。

论文还做了“Barrel of Monkeys”实验：把自家生成与排行榜前四名提交合为 5 个候选/问题，coverage 达 80.8%，选择后得 66.2%，高于集合中最好的单体（62.8%）。论文明确指出，80.8% 是 pass@5，与 o3 报告的 71.7%（pass@1）不可直接比较——这种自我限定值得读者注意。

**解释**：这一节最诚实的地方是指出“覆盖率红利需要选择能力兑现”。随机选择只有 45.8%，说明**生成能力的提升若没有匹配的选择方法，几乎无法转化为最终分数**。

## 二、KernelBench：测量“快且对”的基准与反馈的价值

### 2.1 基准设计

论文提出 KernelBench：250 个任务，输入是 PyTorch 参考实现（`Model` 类及输入规格），要求输出 `ModelNew`，可内联 CUDA 等任意实现。任务分三级：Level 1 单一算子（100 个）、Level 2 算子序列（100 个，可融合）、Level 3 完整架构（50 个，如 AlexNet、MiniGPT）。评估完全自动化：5 组随机输入比对输出正确性；用重复计时比较墙钟时间。核心指标 fast_p 定义为“功能正确且相对基线加速超过阈值 p 的任务比例”，fast_0 即正确率。

**解释**：这个指标设计把“正确”和“快”合成单一可扫参曲线——提高 p 即提高难度，基准可随模型进步而“动态变难”，这是它区别于一次性饱和基准的关键。

### 2.2 一次性生成的结果

论文报告：在 NVIDIA L40S 上，前沿模型一次性生成（贪心解码）的 fast_1 普遍低于 20%。表格显示 OpenAI o1 在三级上分别为 10%/24%/12%，DeepSeek R1 为 12%/36%/2%（相对 PyTorch Eager）。误差分析称：推理型模型错误率更低（<55% 对 >70%），但主要差在**执行失败更少**，功能正确性上所有模型都差不多差。论文还提出一个假设：CUDA 在开源语料中占比极低（引 The Stack v1.2 为 0.073%），是模型难以写出正确 kernel 的原因之一——注意这是论文的假设性解释，而非被其实验直接证明的结论。

### 2.3 反馈：重复采样 vs 迭代精化

论文比较两种 test-time 方法（预算同为 10 次调用）：高温度重复采样，以及把编译/执行反馈乃至 profiler 信息回灌的多轮迭代精化。论文报告：两者都优于一次性；在 6 个对比情形中迭代精化在 5 个更有效；DeepSeek-R1 在 Level 2 上结合执行与 profiler 反馈后 fast_1 从 36% 升至 72%。但同时强调：**方法效果依赖基座模型质量**——R1 稳定受益，而 DeepSeek-V3 与 Llama 3.1 70B 并非总能从反馈中获益。论文还报告硬件信息注入对部分模型影响不大，而 few-shot 优化示例反而因更激进的优化导致执行失败、整体 fast_1 下降。

**解释**：这组结果对“反馈万能论”是一个温和的反例：反馈是必要但不充分的，模型本身需具备把反馈转化为修正的能力。

## 三、Agent-System Interface：用 DSL 与可解释反馈优化并行程序

### 3.1 问题与两项设计

第三篇论文关注高性能计算中的 mapper：决定任务跑在 CPU/GPU/OpenMP、数据放 FrameBuffer/ZeroCopy/系统内存、内存布局（SOA/AOS、行序、对齐）以及索引映射。手写 mapper 需数百行 C++，专家调优以天计。论文的两项设计是：

- **DSL**：声明式领域语言，把上述决策抽象为 `Task`/`Region`/`Layout`/`IndexTaskMap` 等语句，由编译器翻译为底层 C++ API。论文报告，在基准上使用 DSL 平均减少约 14 倍代码行数，且 DSL 在模型训练语料中没有示例（低资源语言）。
- **AutoGuide**：把原始执行输出（如断言失败）解释为自然语言说明与修改建议（论文说明其实现基于关键词匹配），作为生成式优化的丰富反馈。

### 3.2 实验主张

论文在 9 个基准（3 个科学计算负载 + 6 个矩阵乘法算法）上评估，使用 gpt-4o-2024-08-06。论文报告：Trace（生成式优化器）运行 10 轮的最佳 mapper 全部匹配或超过专家 mapper，最高 1.34× 加速（Circuit，主要归因于内存放置决策）；与基于标量反馈的 OpenTuner 相比，10 轮时快 11×，即使 OpenTuner 跑 1000 轮仍保持 3.8× 优势；每次应用优化约 10 分钟。消融实验称：DSL 在 10 个映射策略上的代码生成成功率显著高于 C++（单次 80% 对 0%，迭代精化 100% 对 0%）；完整反馈（执行+解释+建议）优于各简化版本。

**解释**：这篇论文的价值在于把“接口设计”本身当作提升模型有效性的手段——降低目标语言的复杂度、把不可读的系统输出转成可行动的文本。注意其性能数字是**最佳 mapper**（跨 5 次运行的 best），论文对此给出了理由（mapper 优化是离线过程，可复用），但读者应意识到这与“平均表现”是不同的统计口径。

## 四、方法对比

| 维度 | CodeMonkeys | KernelBench | Agent-System Interface |
|---|---|---|---|
| 任务 | 修真实 GitHub issue | 写高效 GPU kernel | 写并行程序 mapper |
| 系统核心 | 三段式流水线 + 状态机 + 选择 | 基准与指标（fast_p） | DSL + AutoGuide + 生成式优化 |
| 反馈利用 | 执行反馈（测试脚本） | 编译/执行/profiler 反馈 | 解释化、建议化的文本反馈 |
| 扩展方式 | 串行（迭代）+ 并行（多轨迹） | 重复采样 vs 迭代精化 | 多轮生成式优化（10 轮） |
| 主要教训 | 覆盖率需选择兑现；成本可摊销 | 反馈有效但依赖基座模型 | 接口降低语义鸿沟 |

三者可以看作互补的三层：KernelBench 提供“测量与信号”，CodeMonkeys 提供“规模化组织与选择”，ASI 论文提供“接口与反馈的表达方式”。共同点是：都把**执行结果**作为一等公民，而不是只依赖模型的一次性输出。

## 五、结语与阅读提示

三篇论文都没有宣称“模型已能自主写好系统级代码”。CodeMonkeys 的最终得分与 oracle 之间仍有一半差距，KernelBench 的一次性结果远未及格，ASI 论文的增益依赖特定 DSL 与基准范围。它们的共同贡献是**把瓶颈定位并工程化**：上下文可摊销、反馈可结构化、选择可训练、接口可设计。

阅读时建议保持三点警惕：其一，论文中的覆盖率（pass@k）与最终得分（pass@1）不可混用；其二，部分数字是最佳运行或特定硬件（L40S、P100）上的结果，外推需谨慎；其三，输入文本未包含全部附录与图表，诸如 KernelBench 的硬件泛化细节、CodeMonkeys 各子任务逐项指标的完整曲线，本文只能保留不确定性，不做补全。最后需说明：本文是依据论文公开文本的阅读导读，不构成对任何课堂讲授内容的复原；论文版本可能晚于课程时间，文中结果不应被理解为“某学期课堂上讲过”。
