# 从“会生成”到“选得对”：Stanford CS329A 第三讲中的 Robust Verification

## 导语

在自我改进型 AI agent 的叙事里，最容易被高估的能力是“生成”：模型似乎已经知道很多问题的答案，只要多采样几次，正确解往往就在候选池里。真正困难的，是在没有标准答案的测试时刻，自动判断哪一个候选解值得交付，或者在生成过程中把模型往正确方向推。Stanford CS329A Autumn 2025 的第三讲「Robust Verification」正是围绕这个缺口展开：上一讲留下的是 generation-verification gap（生成-验证差距），本讲则用四篇论文串起一条验证研究的演进路线，从训练专门的 verifier，到 process supervision，再到无需人工标注的自动过程奖励，最后走向弱验证器集成与蒸馏。本文依据课程逐字稿与讲义线索，尝试还原这条路线的问题意识、方法细节与工程含义。

## 一、本讲在课程路径中的位置：验证是推理时扩展的“后半篇文章”

第三讲并不是孤立地讨论“打分模型”。它承接上一讲关于 inference time scaling（推理时扩展）与 generation-verification gap 的讨论：语言模型通过 repeated sampling 等 test time techniques 可以生成答案，但系统仍需要一个机制来选择或引导。也就是说，生成能力提升之后，瓶颈从“能不能产出候选”转向“能不能可靠判断候选”。

这个位置决定了本讲的双重角色。一方面，它讨论的是测试时的选择器：给定问题与若干候选解，verifier 输出正确概率，系统取最高分。另一方面，它又直接通向训练：PRM 可以作为 reward model，通过强化学习改进 generator 本身。课程在结尾明确把这条线索连到“模型自我改进”：模型生成标注、训练 PRM、再用 PRM 改进生成器，形成多层次地利用模型自身数据与奖励信号的循环。因此，第三讲既是推理时扩展的技术补充，也是后续讨论 agent 自我改进、RL 训练与验证器设计的基础。

## 二、第一篇：用 verifier 把“多采样”变成“会选择”

第一篇文章是 OpenAI 2021 年的《Training Verifiers to Solve Math Word Problems》。课程给出的动机非常直接：LLM 会产生幻觉，并自信地呈现错误解答；这一判断在四年后仍然成立，只是模型整体变强了。该论文的贡献有两个层面：其一是引入 GSM8K 这一小学数学文字题基准，包含约 8,500 道小学水平数学题，强调 multi-step reasoning 与自然语言解答；其二是训练 verification model，让它输出一个解答正确的概率。

训练流程在课程中被讲得很具体：给定问题 QI 与人类标注的正确答案，generator 通过重复采样为每个问题生成多个解答，课程例子中是 100 个；然后用最终答案是否匹配真实标签来创建二元标签；再用“问题—解答—标签”训练 verifier。测试时同样生成大量答案，用 verifier 的打分排序，取最高分作为最终输出。这里的关键不是“再训练一个模型”本身，而是把测试时的选择问题转化为一个可监督的学习问题。

课程还强调了 verifier 的架构与损失设计。Verifier 本身是一个语言模型，但带有一个小的 scalar head，在逐 token 基础上输出二元预测；训练时同时使用 binary loss 与常规的语言建模下一 token 预测损失。问题中的 token 被掩码，不参与优化。最终解答分数取最后一个 token 之后的分数：如果最后一个 token 被判为正确，整个解答就被认为正确。

这套方法的效果与边界同样重要。课程提到，在 6B 与 175B 模型上，验证随着 verifier 训练集增大而变得更有效，最终超过仅做 supervised fine-tuning 的基线；但当数据量很小，例如 175B 设置下少于一千条时，验证帮助不大。另一个有趣结果是“更大的 generator 配更小的 verifier”优于“更小的 generator 配更大的 verifier”，课程认为这符合直觉：生成本质上或平均来说比验证更难。测试时扩展方面，增加每个问题的补全数量后，verifier 在大约 400 个样本附近仍能带来收益，之后不再显著；课程把这与上一讲多数投票在更少样本后就失效的情形对照，说明 verifier 延长了可用采样的范围，但并非无限。

这里还有一个值得记住的工程判断：课程提到，第一篇论文先对 generator 做两个 epoch 的微调，再采样 100 个补全、标注、训练 verifier 一个 epoch；但讲师也指出，这一步“也许值得商榷”，因为更新的语言模型在指令遵循与数学理解上已经很好，很多更新的 verifier 可能可以直接进入 verifier 训练目标。这种对历史方法保持距离的态度，是课程论证的一部分：方法会过时，问题结构不会。

## 三、第二篇：从结果奖励到过程奖励，PRM 为何更可靠

第二篇是 OpenAI 的“Let’s Verify Step by Step”。课程把它放在第一篇之后不到两年的位置，问题仍然是幻觉与早期步骤出错导致整条解答脱轨。它提出的核心区分是 outcome-based reward model（ORM）与 process-based reward model（PRM）：ORM 为整个解答给一个奖励，关心最终正确性；PRM 为解题的每一步分配不同奖励。

训练方式在课程中被拆得很清楚。给定数学问题与标准答案，generator 生成一条包含若干步骤的解答；ORM 只需把最终答案与 ground truth 匹配即可得到标签。PRM 则需要人类标注员逐步检查模型生成的步骤，为每一步分配分数，形成逐步正确或错误的标签。课程给出的例子是：一个分数的分母比分子的 3 倍少 7，若分数等于 2/5，分子是多少；前五步被标为正确，最后一步模型把 X 算成 7，而应为 15/14，因此被标为错误。最终逐步奖励可以计算为各步奖励的乘积；测试时对每一步运行 PRM，相乘得到整体质量，再决定输出还是重试。

课程特别强调 process supervision 的一个性质：它能比 outcome supervision 更好地管理 false positives。原因是模型可能产生幻觉，过程完全错误却碰巧得到正确最终答案；过程监督能看到所有步骤，因此不太可能把“步骤错但答案对”的解答整体判为好。它还鼓励可解释的推理与人类认可的解题过程——这里的“人类认可”有实际含义：标签由人类创建。

数据层面，课程提到 PRM 800K 这一开源数据集，包含 80 万个步骤级标签；生成器对每个问题逐步生成大量样本，并优先收集“有说服力的错误答案”，即最终答案正确但中间步骤错误的样本，使数据效率比随机选择交给人类标注高出 2.6 倍。结果上，PRM 优于 ORM 与多数投票；多数投票在约 100 个样本后不再提升，而 PRM 继续受益。课程还提到 PRM 能检测到正确答案在样本分布中少于 5% 的罕见正确情形，并且比多数投票更能容忍 distribution shift。

但课程没有把 PRM 说成万能。问答环节指出，PRM 可能导致 false credit assignment：某一步看起来不错，但对最终答案没有贡献；较新的方法往往把 PRM 与 ORM 结合起来，以获取两种方法的好处。PRM 的阈值本身也是新引入的 hyperparameter，需要系统处理与优化。还有一个被反复追问的问题：如果推理被跳过、模型直接给出 PRM 喜欢的答案怎么办？课程的回答区分了“用 PRM 打分”与“用 PRM 训练 generator”：如果不微调 generator，仍可通过提示要求它逐步推理；如果要用 PRM 做 RL，就必须小心 chain of thought 是否合理，而人类标注的 PRM 数据本身可以惩罚跳过推理步骤的解答。这些限定让 PRM 的讨论保持工程上的诚实。

## 四、第三篇：Math-Shepherd 与自动过程标注

第三篇是“Math-Shepherd: Stepwise Verification and Reinforcement Learning of LLMs without Human Annotation”。课程把它定位为：既然 PRM 显示了潜力，但需要大量难以收集的人工标注，能否自动化 PRM 的标签收集过程？这篇论文讨论两种方法：自动标注，以及把 reward model 引入 generator 优化的循环，通过强化学习改进生成器。

自动标注的核心定义是：一个推理步骤的质量，等于该步骤达到最终正确答案的潜力。具体做法是从当前步骤采样 n 个 completion，看最终得到正确解答的情况。Hard estimate：如果该步骤之后的 n 个生成中任何一个得到最终正确答案，则该步骤标为成功。Soft estimate：衡量频率，即当前步骤之后的生成中有多大比例达到最终正确答案。课程用 n=3 的例子说明：第一步的 hard estimate 为 1，soft estimate 为 2/3。

课程没有回避这种替代人工标注的缺陷。问答中指出：如果 n 太小，某些通往正确解的非常规路径可能看不到，步骤会被误判为零分；对于难题，大量样本可能都不正确，系统得不到信号；如果中间有错误步骤却最终得到正确解，这些步骤仍可能被标为正确。这些是自动标注的结构性风险，而不是实现细节。课程还提到，他们研究了 hard 与 soft 标注，随着 n 增大 soft 看起来更好，但最终在 n=4 附近选择 hard estimate，因为更容易测量。

验证流程是：采样候选解，用 PRM 打分，选择 PRM 分数最高的样本；此外还用这个 PRM 训练模型，鼓励模型生成被 PRM 打分越来越高的步骤，此时 PRM 充当 reward model。结果上，课程展示了 Math-Shepherd 在 MATH 等更难数据集上超过 PRM 800K 的增量，并与 self-consistency（多数投票的另一个名字）、ORM 等基线比较；还展示了用训练出的 PRM 对模型做 RL 后，结果高于仅用 ORM 做 RL，尽管增量比仅测试时扩展略小，优化在某种程度上趋于平台期。课程对这条路的总结很精炼：模型自己生成标注，训练 PRM，再用 PRM 改进 generator，既在测试时，也通过 RL 微调，形成多层次地利用模型自身、为自己服务的循环。

## 五、第四篇：用弱验证器集成缩小生成-验证差距

第四篇是 Stanford 的“Shrinking the Generation-Verification Gap with Weak Verifiers”，课程标注为 2025 年的新论文。它的方法与前几篇不同：不训练一个新的 verifier，而是利用推理计算与推理缩放，通过 verifier ensemble 来缩小差距。这里的“弱”不是故意选择差验证器，而是假设没有验证器是完美的；这些是现存最好的验证器，但仍有不完美之处。

课程把验证器类型扩展为三类：PRM、ORM，以及把 LLM 本身作为 judge——给模型看答案，问它是否正确，可以让模型使用工具、评分标准等生成分数。集成的基本图景是：不同实验室在不同数据集上训练的多个验证器，接受查询并输出分数；把它们集成起来在测试时使用，整体上改善情况，但不一定是单调的。一直有帮助的做法是，如果有标签，训练一个模型为集成成员分配权重；课程提到 naive Bayes 或逻辑回归这类非常简单的方法，为每个验证器加一个单一权重，用带标签训练集得出权重，再用于新测试数据。

课程把方法概括为 score-weight-select：先对验证器输出评分并归一化到同一尺度，过滤掉低质量验证器——课程强调验证器应高于某个质量阈值才能进入池中；然后从验证器、LM judge、reward model 得到分数，再用弱监督估计验证器准确率，用很少的标注数据得出权重，组合输出并分配分数。这里的 weak-to-strong supervision 受 Snorkel 等工作启发：有 n 个查询、每个查询 k 个解、m 个验证器，共 n×k×m 个标签；目标是估计“查询 i 样本 j 等于 1”的概率，给定所有验证器标签。Beaver 的关键假设是每个验证器捕捉正确性的独立方面；如果验证器对所有样本给出一致分数，就学不到新东西，信号在于验证器之间的相似性与差异性。在这个假设下写出概率并优化，得到每个验证器的权重。

结果上，课程展示 Beaver 在某些情况下优于朴素集成，增益在 GPQA Diamond、MATH、MMLU Pro 等相对困难的问题上更显著；在 GPQA 基线已经很低时，弱到强聚合带来相对朴素集成的大幅提升。课程还比较了不同的验证计算缩放方式：采样更多生成、使用更大模型、增加池中验证器数量；并把 pass@k oracle、有监督权重、无监督（每个数据集用 1% 训练标签）、朴素集成等放在一起比较，这些方法显著优于多数投票与多智能体验证（MAV）。课程给出的提升幅度是：困难问题上从大约 40% 出头提升到 70% 以上，匹配像 o3 mini 这样的模型；用 Llama 3.1 8B Instruct 的 generator 与 8B 及以下验证器池，平均得到 70%，几乎媲美更大模型级别通过多数投票的准确率；对 70B 级别模型应用相同生成与验证，平均得到 86.2%，非常接近 o3 mini。这里课程明确说，讨论的是整个系统的解答准确率，而不是覆盖率。

工程可行性方面，课程提到集成验证器的成本问题：每个解答要运行大量模型，若有 100 个样本，成本会放大。Beaver 的提议是训练一次，再蒸馏到更小的模型；课程展示可以蒸馏到约 4 亿参数，而原始模型在 70B 范围，捕获大池 LLM 验证器 97% 的准确率，同时测试时计算量减少 99% 以上；蒸馏版与原始版都是开源 checkpoint。课程还展示蒸馏版在成功率相对于推理计算量上效率更高，而原始 Beaver 因为能达到更高准确率水平，在那些水平上比朴素集成与多数投票更具 FLOP 效率。

## 六、四篇论文连起来看：验证研究的演进逻辑

把四篇论文放在一起，课程实际上给出了一条递进论证。第一步，验证可以被学习：用二元正确性标签训练 verifier，把多采样变成会选择，但受限于标签规模与测试时采样范围。第二步，验证可以从结果走向过程：PRM 逐步给奖励，能更好地管理假阳性，鼓励可解释推理，但需要大量人工逐步标注，并引入阈值等新超参数。第三步，过程标注可以自动化：用“该步骤达到最终正确答案的潜力”替代人工标签，把 PRM 变成 reward model，通过 RL 改进 generator，但自动标注对难题、非常规路径与错误中间步骤仍存在信号偏差。第四步，验证可以不只依赖单一模型：用弱验证器集成与弱到强监督，在少量标签下组合多个不完美验证器，再蒸馏成小模型以降低成本。

这条路线也解释了课程反复出现的几个判断：生成比验证更难，因此更大 generator 配更小 verifier 更合理；PRM 与 ORM 各有盲点，较新方法倾向于结合二者；验证器的数据效率与泛化能力比单点准确率更重要；验证不仅用于测试时选择，也可以进入训练循环，成为模型自我改进的组成部分。课程在问答中还提到，未来理想情况是模型一次通过就很好，测试时扩展与重复采样可能更多用于生成训练数据；但也要警惕，如果让模型 log probs 通过单一答案变得过于尖锐，解决方案的创造力与多样性可能在训练中丢失。这个提醒把验证研究放回自我改进 AI agents 的更大图景：验证器不仅是筛选器，也是塑造模型行为的力量。

## 结语

第三讲「Robust Verification」的核心贡献，是把“验证”从附属技巧提升为自我改进系统的关键组件。它用 GSM8K verifier 说明验证可以被监督学习；用 PRM 说明过程监督比结果监督更能识别假阳性；用 Math-Shepherd 说明过程标签可以自动生成并进入 RL 循环；用 Beaver 说明多个弱验证器的集成与蒸馏可以在有限标签与有限计算下显著缩小生成-验证差距。对学习这门课的读者而言，这一讲既是对上一讲推理时扩展的补课，也是后续 agent 自我改进、奖励建模与测试时计算分配讨论的铺垫。验证不是让模型“更会生成”，而是让系统“选得对、改得动、算得起”——这正是 robust verification 在 self-improving AI agents 路径中的位置。
