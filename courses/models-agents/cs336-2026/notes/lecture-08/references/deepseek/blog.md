# 从单卡到数据中心：大语言模型训练中的并行化策略全景

## 导语

当我们在单张 GPU 上训练一个 70 亿参数的模型时，内存会立刻告急；当我们要训练一个数千亿参数的模型时，算力更是遥不可及。大语言模型规模的指数级增长，迫使我们把目光从单个芯片移向整个数据中心。但如何把成千上万张 GPU 组织起来，让它们像一个巨大的虚拟芯片一样高效运转？这正是并行化要回答的核心问题。

在 CS336 课程的第八讲中，我们深入探讨了现代大语言模型训练中并行化的方方面面。这一讲建立在第七讲对通信底层机制的基础上，将抽象的网络原语与实际的工程实践连接起来，最终呈现出一幅完整的并行化策略图谱。本文将从数据并行讲起，逐步过渡到各种模型并行策略，最后探讨它们如何组合成我们在前沿模型训练中看到的大规模系统。

## 两个瓶颈与两种网络哲学

并行化的必要性源于两个根本瓶颈：**算力**与**内存**。单个芯片永远无法提供训练千亿参数模型所需的算力，模型本身也远远超出任何单卡的内存容量。于是，我们把多台机器连接起来，把模型切碎，把工作分发下去。

但这里立刻浮现出一个关键区分：**节点内（intranode）并行与节点间（internode）并行**。节点内的 GPU 通过超高速互联连接，通信开销极低；节点间的连接则慢得多。这个区别贯穿了整讲的内容——我们选择哪种并行策略，很大程度上取决于通信发生在哪一层。

有趣的是，不同的硬件厂商对网络拓扑有着截然不同的设计哲学。TPU 采用环形网格（toroidal mesh）拓扑，每个芯片只与固定数量的邻居相连，邻居之间环绕相接。这种设计的优势在于：无论网络扩展得多大，每个芯片的邻居数不变，通信模式极其规则且可预测。相比之下，GPU 网络更像一棵胖树（fat tree），从底层的快速连接逐层向上汇聚，理论上支持任意两个节点之间的全对全通信，但代价是随着节点数增长，网络复杂度急剧上升。

这两种拓扑直接影响了并行策略的选择。TPU 擅长那些通信模式规则的并行方式，而 GPU 网络则更适合通信模式不那么可预测的场景——比如混合专家（Mixture of Experts）模型，token 被动态路由到不同的专家，通信模式本身就带有随机性。值得注意的是，讲者提到谷歌最新发布的 TPU 已经转向更接近全对全的拓扑，这被视为硬件与工作负载共同演化的一个信号。

## 数据并行：最朴素的想法及其局限

数据并行（data parallelism）是最容易理解的并行策略。假设我们有一个大小为 B 的批次，把它均匀分到 M 台机器上，每台机器拿到 B/M 个样本，计算各自的部分梯度，然后同步所有梯度。

从算力角度看这很完美——只要每个 GPU 上有足够多的样本。但问题在于通信和内存。每处理一个批次，我们需要通信约两倍参数量大小的数据；而在内存方面，每个 GPU 都持有一份完整的模型副本，**完全不节省内存**。

更糟的是，现代优化器让内存问题雪上加霜。讲者给出了一个粗略的经验法则：我们需要大约五份权重复制，每参数 16 字节。这包括模型参数本身、梯度累加器，以及优化器状态（optimizer state）——包括一阶动量和二阶动量。在使用 Adam 优化器时，优化器状态往往占据了内存的大头，而这也是数据并行最浪费资源的地方：每个 GPU 都在冗余存储这些状态。

## ZeRO 与 FSDP：数据并行的内存革命

如果优化器状态占内存最多，为什么不把它们切碎分布到不同 GPU 上？这引出了 ZeRO 的三个阶段。

**ZeRO 阶段 1**：只切分优化器状态。每个工作节点负责更新参数的一个切片。流程是：先计算完整梯度，然后做一次 reduce-scatter 把梯度分发到各节点，各节点完成自己的参数更新，最后 all-gather 收集更新后的参数。关键洞察是：reduce-scatter 加 all-gather 的组合在通信量上等价于一次 all-reduce。因此，**ZeRO 阶段 1 与朴素数据并行相比，通信成本完全相同**——内存节省是白拿的。

**ZeRO 阶段 2**：进一步切分梯度。这带来一个微妙的问题：既然梯度也被分片了，我们就不再能完整物化整个梯度向量。解决方案是沿着计算图反向传播时，计算完某一层的梯度后立即做归约并发给正确的工作节点，随后释放。这是增量式地完成原本一次性做的事情，通信成本不变，但梯度也不再重复存储。

**ZeRO 阶段 3**，也就是广为人知的 FSDP，最激进也最优雅：一切都被分片——参数、梯度、优化器状态。每个 GPU 在任何时刻只持有模型的一个切片。前向传播时按需 all-gather 当前层的参数，计算完成后立即释放；反向传播时再次 all-gather 参数，拿到梯度后立刻 reduce-scatter 出去。通信量比阶段 2 多了一次 all-gather，似乎更昂贵了。

但 FSDP 真正精妙的地方在于它把通信和计算重叠（overlap）起来。在等待第 0 层参数到位并开始前向计算的同时，可以发起对第 1 层参数的 all-gather。只要网络足够快、计算量足够大，FSDP 可以做到几乎零开销。讲者强调，FSDP 的实际 GPU 利用率可以非常接近单 GPU 性能，而作业中要亲自实现一个 FSDP 包装器——只需把任意模块包装起来，做一堆 all-gather、计算、释放，然后反向过程中重复。

FSDP 的收益是巨大的：在 8 块 A100 上，从连 70 亿参数的模型都放不下，到可以装下 500 亿参数的模型。然而，FSDP 有两个根本局限：其一，它消耗全局批大小，如果你的批次大小是 8，就永远不可能用超过 8 个加速器有效训练（受**临界批大小**约束，批次增大带来的收益会递减）；其二，它无法削减激活值内存——那些在前向过程中产生、反向传播时必需的中间量。

## 模型并行：切分层、矩阵与专家

当数据并行的内存节省到达极限，我们必须求助于模型并行（model parallelism）。与 FSDP 切分参数但仍在每个 GPU 上遍历完整模型不同，模型并行把不同部分真正放置到不同设备上，通信的对象也从参数变成了**激活值**。

### 流水线并行

流水线并行（pipeline parallelism）是最直观的模型并行：把层切分开，放在不同 GPU 上，激活值在层间传递。朴素实现的问题是灾难性的气泡（bubble）——任何时候只有一个 GPU 活跃，利用率低得令人绝望。

解决方案是微批次（micro-batches）：像流水线一样，微批次依次进入，上层完成一个微批次的计算后立刻传递给下一层，而不是等整个批次算完。利用率大约等于阶段数除以微批次数量，因此它消耗批大小来换取效率。实践中，流水线并行的通信特征非常好——只依赖 b·s·h 大小的激活值，而且是点对点通信——因此它最适合放在最慢的链路上，比如跨数据中心。

进一步优化空间在于更聪明的调度。讲者提到了"零气泡流水线"的思想：反向传播实际上包含两件事——把偏导数传回计算图更深处，和计算当前权重的梯度。前者有严格的时间依赖，后者是叶节点，随时可算。把这两者解耦，优先做前者，在空闲间隙填补后者，几乎可以填满流水线。

### 张量并行

张量并行（tensor parallelism）沿宽度方向切分矩阵乘法。简单的想法：把 A 矩阵切成两块，B 矩阵也切成两块，各自并行计算，最后汇总。前向传播时 f 是恒等操作（把输入复制到两份计算中），g 是 all-reduce（把结果合并）；反向传播时角色反转。

实际应用中，MLP 的输入投影和注意力机制的投影做按列切分，MLP 的降维投影和注意力输出做按行切分，而层归一化等小层完全复制。张量并行对通信极为敏感——每次矩阵乘法都伴随一次所有规模的通信，而且非常频繁——因此通常只在节点内部使用。对于 GPU 用户，这通常意味着最多 8 卡。但 TPU 的环形网格拓扑恰好适合这种规则的通信模式，因此 TPU 上可以把张量并行扩展到更大的规模。

### 序列并行

讨论激活值内存时，我们得到一个经验公式：激活值约需 34·s·b·h（序列长度 × 批大小 × 隐藏维度）加上注意力项。张量并行可以削减其中大部分，但层归一化、dropout 等逐点运算不参与切分，仍然留下约 10·s·b·h 的不可削减项。

序列并行（sequence parallelism）的名称极具误导性——它并不是把序列分给不同设备各自独立处理（那是上下文并行），而是沿序列轴切分这些逐点操作需要的激活值。这非常像 FSDP 的思路：分片存储，按需 all-gather 具体化，反向传播中角色反转。通过序列并行，激活值内存可以实现对张量并行规模的完全线性依赖，配合激活重计算消除注意力项，最终得到激活内存下限：34·s·b·h 除以 t。

### 专家并行

专家并行（expert parallelism）把 MoE 层中的专家（FFN 组件）分布到不同设备上。它在多个方面与张量并行相似：高带宽消耗、减少激活内存，但它有几个独特优势：矩阵保持更大因此 GPU 利用率更高；token 可以精确路由到需要去的专家；在 MoE 模型中，优先选择专家并行而非张量并行是 NVIDIA Megatron 官方指南的明确建议。

然而专家并行极其复杂，因为涉及大量的全对全分发，且要求低延迟——计算在等待 token 到达。讲者提到 DeepSeek 的 DPP 库甚至使用了未公开的 PTX 指令来加速网络通信——这已经是接近机器码级别的优化了。

专家并行还有一个系统层面的纠结：MoE 只改变 MLP，不改变注意力。注意力层需要高张量并行来切分，而 MLP 层如果同时使用高张量并行和高专家并行，矩阵会被切成碎片，利用率急剧下降。近年来的解决方案是把注意力和 MLP 中的张量并行**解耦**，各自使用独立的并行策略。

### 上下文并行

上下文并行（context parallelism）或环形注意力，用于处理极长序列：把激活值沿序列轴拆分到不同加速器上，以环形方式传递。这主要用于长上下文扩展阶段和服务场景，概念上与前述内容有大量重叠。

## 组合策略：从乐高积木到 4D 并行

所有并行策略都各有优劣。FSDP 不能处理激活值、消耗全局批大小；张量并行能削减激活值但不影响批大小，却需要高速网络；流水线并行通信效率高但依赖大批次。没有任何一种策略是全局最优的——这个观点通过并行策略对比表格中的红色标记（缺点）被反复强调。

实践中的策略其实非常简单：首先，只要模型还不能完全放进内存，就想尽一切办法切分。在快速互联（节点内部）使用张量/专家并行，通常为 8；用流水线并行或 FSDP 处理剩余部分。一旦模型能放进去了，就全部使用数据并行来利用剩余 GPU。如果批大小太小，用梯度累积弥补。

这也正是 Megatron 的 MoE 并行化指南的核心内容：**最小化模型并行，最大化数据并行**；在 NVLink 范围内（即单机箱内）使用专家/张量并行；跨节点用流水线并行；MoE 优先专家并行；长序列用上下文并行。

## 现实案例：前沿模型的并行化配置

课程最后展示了一系列真实模型的并行化方案，让我们看到理论如何落地。

**Olmo 7B** 完全使用 FSDP 训练，展示了 FSDP 在小模型上可以扩展到大量 GPU。许多 7B 级别的模型都是用纯 FSDP 训练的。

**DeepSeek V1** 使用了数据并行加 ZeRO 阶段 1，加上张量、序列和流水线并行。**DeepSeek V3** 作为 MoE 模型，用专家并行取代了张量并行，并且采用了独特的 64 路专家并行——8 台机器组成一个专家并行域，借用了流水线的技巧来实现大规模专家并行。

**Llama 3 405B** 是少数公开详细并行化配置的模型之一：主预训练阶段使用张量并行 8、上下文并行若干、流水线并行 16、数据并行 128。长上下文扩展阶段提高上下文并行、降低数据并行。讲者顺带提到，405B 训练期间 GPU 故障了 148 次——大规模训练不仅是算法问题，也是分布式系统的挑战。

**Gemma 2** 仅用 FSDP 加张量并行和序列并行——讲者认为这基本实现了谷歌的主张：对于 TPU，你不需要流水线并行，只需一个大网格加张量并行。

近期模型如 **Mixtral 8x22B**（专家并行 8 + 流水线并行 4 + 张量并行 4）、**Nemotron 3 Super**（大量专家并行加上下文并行）、**Qwen 3**（专家并行 32 + 流水线并行 8 + 张量并行 2），都遵循了同一个模式：最大化数据并行、张量并行保持在 8 以下、专家并行可以做得很大。

## 结语

从单张 GPU 到整个数据中心，并行化的本质是一场资源的精算：算力、内存、通信带宽、批大小——每种资源都有限，每种并行策略都在某种资源的约束下换取另一种资源的释放。数据并行给我们算力但不省内存；FSDP 免费削减了参数、梯度和优化器状态的内存，却对激活值无能为力；张量并行削减激活值但吞噬通信带宽；流水线并行通信高效却依赖大批次；专家并行在很多方面更好但它带来的系统复杂度也最高。

理解这些权衡之后，组合各种策略其实遵循着简单的经验法则。而现实中那些训练出最强模型的公司，正是在这些经验法则的基础上，结合对自己硬件拓扑的深刻理解，构建出了高效的大规模并行系统。在课程的整体路径中，这讲标志着我们从"如何实现一个模型组件"走向"如何在规模上训练一个系统"。下周讲到的缩放定律，将告诉我们规模的极限在哪里，以及如何智能地分配资源。
