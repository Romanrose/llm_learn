# 从电力到智能：Dan Fu 讲推理系统、内核与循环架构

## 一、这门课讲训练，而这场讲座讲“另一侧”

CS336 的主线是训练语言模型：数据、并行、优化、评估。但 Dan Fu 开场就点出这场 guest lecture 的位置不同——当模型已经训练好，接下来要把它变成产品，中间隔着的是**推理（inference）与服务（serving）**。他给出的比喻是：你要从电力出发，把电力变成 token，再把 token 变成智能（约 [00:29] 起）。

【学习者解释】“推理”通常指模型前向计算并生成 token；“服务”则指围绕推理构建的调度、缓存、硬件分工、SLA 等系统问题。二者经常被混着说，但在工程上关注点差别很大。

Dan 用两个历史类比搭建动机。第一是工作马：1902 年曼哈顿有大量工作马，1898 年甚至开过专门讨论马粪问题的会，结论是“没办法，只能捂着鼻子忍”；但十年后汽车数量就超过了马，他称“1912 时刻很可能就是去年”（约 [03:06]–[04:12]）。第二是石油：GPU 像“新石油”，而推理是把石油变成有用动能的引擎（约 [04:31]–[05:12]）。这两个类比服务于同一个论点：**基础设施与引擎的成熟，会决定一项技术从“能用”变成“无处不在”。**

## 二、一个 token 的生命周期：从请求到字符串

讲座的第一大部分是端到端概览。Dan 特别声明这部分幻灯片是 AI 生成内容，远看结构正确，细看会有错误（约 [07:55] 起）。这里的诚实值得注意：**讲者在提示听众不要把这些示意当作精确技术图。**

一个请求进来后大致经历：

1. **Tokenize**：文本变成 token；
2. **调度（scheduling）**：请求被分配到不同 GPU 上，可能做分离式 prefill / decode（约 [08:10] 起）；
3. **缓存查询**：问“我以前见过这些 token 吗？能否省掉一些计算？”
4. **核心机器学习计算**：分成 prefill 与 decode 两大块；
5. **后处理**：把输出数字变成字符串，检查 stop token，可能跑安全检查（约 [15:37]–[16:00]）。

这里最关键的概念区分是 **prefill 与 decode**。

- **Prefill**：一次性处理成千上万个新 token，算出激活与 logits，是计算密集（compute-bound）操作，形态上非常接近训练时的前向（约 [14:12]–[14:51]）。
- **Decode**：一次生成一个 token（有 speculative decoding 时可能一次三到四个），每生成一个新 token 都要把整个模型再跑一遍，因此 flops 不大，却极度受**内存带宽（memory bandwidth）**限制（约 [15:06]–[15:37]）。

【学习者解释】这解释了为什么推理优化里经常出现“把模型权重从显存读一遍只为生成一个 token”的瓶颈描述：算力用不满，但权重必须反复搬运。

因为两者特征差异巨大，业界普遍把 prefill 和 decode 拆到不同机器或不同芯片上（约 [19:52]–[20:46]）。Dan 举了硬件层面的例子：NVIDIA 收购 Grok 后，计划用 GPU 做 prefill、用 LPU 类芯片做 decode；Cerebras 与 OpenAI 的算力合作也指向解码场景更擅长的芯片；还有 SambaNova 等（约 [21:05]–[21:43]）。

【学习者解释】“分离式架构”的核心动机是：不让计算密集型和带宽密集型的任务互相拖累。到底哪种芯片组合最优，逐字稿没有给出可核实的规格数字，本文不做推测。

## 三、流量不是训练数据：工作负载的形态

Dan 反复强调一件事：生产环境的流量**既不像训练时看到的 token 分布，也不像你凭空想象的分布**（约 [09:55]–[10:12]）。它由工作负载塑造：

- 编码 agent：输入可能几万 token，输出取决于模型是否输出 thinking token（约 [10:12]–[10:33]）；
- 摘要：与编码完全不同；
- 把整本书粘进聊天窗口再追问：又是另一种形态（约 [10:50]–[11:12]）；
- agentic 多轮：模型会去 grep 代码库、发起网络搜索，再把结果喂回来（约 [11:31]–[11:49]）。

时间维度同样重要：交互式聊天与语音模式要求快速首 token；托管型 agent 可以慢慢迭代；如果 agent 卡住来求助而你没在看，轮次之间的间隔会被拉长（约 [11:49]–[12:32]）。Dan 还举了自己与 ChatGPT 两周才交互一次的健身计划对话作为例子（约 [12:54]）。这些变量共同定义了：每轮多少新 token、生成多少 token、会话多长、轮次间隔多大（约 [12:32]–[13:16]）。

目标也会不同：交互式应用关心首 token 延迟，另一些场景更关心整体响应时间（约 [13:16]–[13:31]）。

## 四、Continuous batching 与 KV Cache：把系统塞满

当系统同时处理许多请求时，出现 **continuous batching**：时间向下流动，长请求持续生成 token，短请求插进来、几步后完成，新请求再进来；如果 GPU 内存不够，长请求可能排队（约 [16:27]–[17:45]）。

另一块是 **KV Cache** 与前缀共享：如果许多用户都在问“嗨 ChatGPT”，理论上不该为每个用户从头算激活；如果用户传进来一本书，算一次 prefill，下一轮对话不必整本重算。实现上常用树结构这类传统数据结构做查找（约 [18:08]–[18:50]）。

当模型大到单卡装不下，就要切分：tensor parallelism 把张量切到多卡；MoE 模型可以把不同 expert 切到不同 GPU。这些选择决定瓶颈在哪、需要多少卡、能同时服务多少会话（约 [18:50]–[19:52]）。

KV Cache 的存储层次也逐级下沉：GPU 显存→CPU DRAM→磁盘。Dan 提到 Jensen 近期对 CPU 性能的执着，正是因为如果一台昂贵机器被插在旁边的 CPU 卡住瓶颈，那很糟糕；也提到 OpenAI 采购 SSD / DRAM 的传闻，与这类缓存需求有关（约 [25:31]–[27:22]）。

【学习者解释】这段与操作系统里的换页 / 淘汰策略高度同构。Dan 自己也指出，这张图除了右侧 GPU 部分，看起来和 70、80 年代的操作系统图一样（约 [27:58]–[28:14]），并提到幻灯片“幻觉”出了 LRU 淘汰策略，而它其实是个相当不错的启发式（约 [28:32] 起）。

## 五、规模化下的诡异 bug：为什么系统问题也是研究问题

Dan 讲了一组只有在大规模下才会暴露的 bug（约 [22:05]–[25:31]）：

- 某些错误内核在极罕见条件下触发，logits 变 NaN，模型开始重复输出 “hi、hi、hi” 或感叹号；
- 工具调用处理被改动后不再正确返回，模型陷入“做一次互联网搜索……做一次互联网搜索”的极长循环，补全长度飙升；
- 一个被归咎于量化的故障，实际是内核 off-by-one，读到了未初始化显存，导致模型突然用中文回答英文问题。

【学习者解释】这些例子的价值不在于具体 bug，而在于一个方法论：**概率极低的路径，在数万亿 token 的规模下会变成必然事件。** 这也是为什么“理解推理系统”会反过来影响模型行为层面的研究。

## 六、两个研究项目之一：Megakernel

第一个项目是斯坦福与 Together 合作的 **Megakernel**（约 [34:17] 起）。问题定义很清楚：decode 每次只为生成一个 token 就要跑整个模型，无法像 prefill 那样获得大规模并行，于是 GPU 变成一个“美化的内存加载器”（约 [34:34]–[34:54]）。更麻烦的是，我们通常一个算子写一个 kernel：Norm、matmul、attention 各自独立，导致大量停机时间（约 [35:16]–[35:36]）。

Dan 展示的示意图里，横轴是时间，纵轴是 GPU 的 streaming multiprocessor（H100 上 132 个，B200 上 148 个，以此类推）；条形代表有用工作，空白是等待。间隙来自 kernel launch / teardown，也来自 tail effect——一批输入里有个特别长的，其他都得等它（约 [35:59]–[37:22]）。

Megakernel 的思路是：与其每个算子单独写 kernel，不如写一个覆盖多个算子的大 kernel，把 GPU 当作一个分布式系统来调度。效果上，仅对 attention 推理内核这么做就能获得 30% 到 70% 加速；对整个模型也能做，例如把下一层权重加载与当前 attention 重叠，或在 QKV + RoPE 还没算完时就开始把 KV Cache 加载进 attention（约 [37:22]–[40:05]）。实现依赖他们自己的库 ThunderKittens，定位类似 Triton 但更底层（约 [40:32]–[40:56]）。Dan 给出的结果是 H100 上达到 72% 带宽利用率，接近“光速”（约 [40:56]–[41:18]）。

代价也讲得很直白：写 Megakernel 极其耗人力。一位出色的 kernel 工程师一年大概只能为一种硬件、两三个模型、batch size 1 到 16 写出 Megakernel，到 17 就要推倒重来（约 [01:03:30]–[01:04:31]）。他们也在尝试用编译器自动化其中一部分。

【学习者解释】这里是“收益明确、人力成本极高”的典型前沿工程问题：一旦写成，速度接近硬件极限；但写成本身缺乏可扩展的方法论。

## 七、两个研究项目之二：Parcae 与循环 Transformer

第二个项目来自 UCSD 实验室、由 Hayden 主导，与 Zachary、Taylor 合作，叫 **Parcae**（约 [41:58] 起）。它问的不是“还能不能更大”，而是“扩展是否是提升质量的唯一方式”。

做法是循环 Transformer：不是让 token 一次一层地穿过整个模型，而是在某些块上让激活反复穿过同一层（约 [42:32]–[42:54]）。好处是：参数不变，但多了一个增加 flops 的旋钮；并且已有工作表明循环结构可能带来更高表达能力（约 [43:35]–[44:32]）。

问题也很严重：循环模型训练极易爆炸。学习率扫描十次有九次不收敛，出现 NaN 和巨大损失尖峰（约 [45:38]–[46:06]）。以前的做法是每层加 norm，或者干脆只挑某一个学习率（约 [46:06]–[46:25]）。

Parcae 的切入方式是数学化的稳定分析。洞见是：把 R 块里所有非线性（Softmax、GELU、RoPE 等）打包成一个盒子 R 放到一边，剩下的就是一个由 A、B 矩阵主导的线性动力系统，甚至可以写出闭式解（约 [47:05]–[50:08]）。关键在于 A 被反复取幂，因此谱半径决定系统是否爆炸——若 A 近似标量 2、循环 16 次，就是 2 的 16 次方（约 [50:08]–[50:47]）。

他们的做法是：约束 A 为负对角矩阵，使其取幂后趋于零；B 因为只应用一次，加一个线性范数约束即可（约 [51:05]–[51:48]）。结果是：即使使用对其它模型很差的学习率（如 6e-4），也能训练稳定（约 [51:48]–[52:11]）。Dan 还解释了一个有意思的现象：模型会试图扩张激活范数以获得更大表示空间，你对它施加范数约束，两股压力对抗，就表现为损失尖峰（约 [52:11]–[53:10]）。

在质量对比上，Parcae 相比此前的循环 Transformer（Recurrent Depth Model）和强 Transformer 基线都更好（约 [53:31]–[53:51]）。缩放律部分，他们发现当增加数据时，也应该增加递归次数；在固定参数、固定 flops 的等值线上，联合缩放递归次数与 token 数能带来更低的验证损失（约 [56:05]–[59:11]）。Dan 强调：今天几乎所有模型都处在“递归次数为零”的最左端（约 [58:02]–[58:23]）。

【学习者解释】这段论证的结构是：先用稳定性分析解释“为什么会爆炸”，再用约束消除爆炸，最后用缩放律说明“循环不只是省参数，可能是更好的资源分配方式”。文中引用的具体数值（如 6e-4、72%、30%–70% 等）均来自逐字稿口述，未经独立核实；本次无 Slides 文件，无法交叉验证。

## 八、问答中的几个要点

问答里有几个对理解全篇很有帮助的补充：

- **能否对预训练模型做循环？** Dan 提到一篇“钓鱼”博客称有人在 Quinn 模型上循环两三层就在数学题上取得更高质量，他们对此很感兴趣、可能有即将发布的工作，并说这让他“感到不安”（约 [01:00:46]–[01:01:39]）。
- **循环对推理的影响？** 更少参数意味着可以装下更多 KV Cache、减少通信；他还梦想把循环块做得足够小，写成一个极小的 Megakernel 常驻内存（约 [01:01:58]–[01:03:11]）。
- **Megakernel 的权衡？** 原话是“人们的血汗和泪水”，写起来极难（约 [01:03:30] 起）。
- **协同设计？** 先受内存约束：确定目标芯片后按内存决定模型规模与 KV Cache 余量；量化格式也会因硬件而异，他举了 NVIDIA 的 NVFP4 与 AMD 侧的 MXFP4（约 [01:04:57]–[01:05:58]）。
- **循环 vs 更大参数？** Dan 说计算机最优意义上这几乎有点人为：若想更高质量就该增加 flops 预算；若模型大小已定就训练更久；若受限于模型大小就多循环；若数据用尽则选那个规模下能训练最充分的模型（约 [01:06:17]–[01:07:34]）。
- **不同用例的架构差异？** agentic 循环工作流非常在意 KV Cache 保持“热”；大规模批处理不需要解码那么在意。他还提到 DeepSeek MLA 是对 KV cache 的激进压缩，以及因果 vs 非因果注意力（Google 长期在搜索用 Bert 这类双向模型）的选择（约 [01:07:56]–[01:09:53]）。
- **跨机通信能否融进 Megakernel？** 有早期工作：设置得当时可以把 NCCL 调用融进去，但有时仍受 NCCL 本身延迟限制；DeepSeek 在 MoE 推理层发布过 Megakernel 并融合了部分通信（约 [01:09:53]–[01:11:28]）。

## 九、结论：全栈创新的入口

Dan 把整场讲座收束成一个论点：如果你理解推理、理解推理引擎、理解支撑核心技术的 GPU kernel，你就能在机器学习算法中做**全栈创新**——无论是新的路由算法、新的 kernel，还是新架构（约 [05:54]–[06:15]，[59:32]–[01:00:23]）。他也坦白这个领域“还处在非常早期的阶段”，十年后人们回看今天的讨论可能会觉得显而易见（约 [33:22]–[33:56]）。

【学习者解释】把这讲放回 CS336 的语境：训练决定模型能力上限，而推理系统决定这些能力能否以可接受的成本和延迟抵达用户。两者共享同一批底层概念（kernel、内存层次、并行切分），但优化目标不同。Dan 的讲座实际上是在说，这两个世界的边界正在变成研究机会最密集的地带。
