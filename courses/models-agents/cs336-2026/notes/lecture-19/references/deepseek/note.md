# CS336 2026 · Lecture 19 · Guest lecture: Dan Fu 学习笔记

> 待审核候选稿 · 来源：平台字幕 · 尚未发布。

## 一、学习目标

本讲的视角与课程前面以“训练”为主线的讲法不同：它从模型训练完成之后的“另一侧”切入，讲一个请求在推理服务系统中如何从电力变成 token、再变成用户可以消费的智能。结合逐字稿，本讲希望学习者达到以下目标：

1. **建立“一个 token 的生命周期”的整体图景**：请求如何被调度到 GPU、如何查 KV Cache、如何经过 prefill 与 decode 两大阶段、最后如何被采样成字符串并被安全检查等后处理。逐字稿开头即说明这一讲要“从另一侧看”模型，即实际服务、推理、把电力变成 token（开场约 00:29 至 00:46 一带）。
2. **理解推理与训练在计算特征上的根本差异**：prefill 与训练类似、偏 FLOP 密集；decode 每步只为生成一个 token，偏内存带宽受限。逐字稿在讲 prefill/decode 时明确对比了二者（约 14:37 至 15:37 一带）。
3. **理解推理系统中若干关键机制**：continuous batching、KV Cache 与前缀共享、张量并行与专家并行、prefill/decode 分离、KV Cache 分层卸载（GPU→CPU DRAM→SSD）等。
4. **理解系统规模如何带来“小概率事件必然发生”的工程问题**：NaN、重复 token、工具调用死循环、随机输出中文字符等真实故障模式。
5. **通过两个研究案例理解“全栈创新”**：一个是系统层面的 megakernel（巨型内核）与 ThunderKittens；另一个是架构层面的 Parcae 循环 Transformer 与稳定化重参数化。
6. **理解推理侧约束如何反过来影响模型架构设计**：参数规模、KV Cache 大小、注意力形式、量化格式与硬件的协同设计。

本讲反复强调的一句话是：如果理解推理、理解推理引擎、理解底层 GPU kernel，就能在机器学习算法层面做出全栈创新（约 06:15 一带、结尾 59:32 一带均再次强调）。

## 二、概念主线

整讲可以概括为一条从“宏观动机”到“系统机制”再到“研究案例”的主线：

**动机层**：作者用 1902 年曼哈顿 13 万匹工作马与马粪问题的会议、以及 1912 年汽车数量超过马的历史类比，说明技术替代可能在很短时间内发生，并认为语言模型的“1912 时刻”很可能就是去年（约 03:06 至 04:12 一带）。他同时把 GPU 比作“新石油”，把推理比作“把电力转化为智能的引擎”（约 04:31 至 05:38 一带）。

**系统层**：一个请求进入推理系统后，经历调度、缓存查找、prefill、decode、采样与后处理。系统要在多个请求之间做 continuous batching，要管理 KV Cache 的存储层级，要在多 GPU 之间拆分模型，还要把 prefill 与 decode 分离到不同的机器集合上。

**研究层**：在这个系统中任取一个部分，都能提出研究问题。作者给了两个例子：
- 系统侧：把多个操作融合进一个巨型内核，减少 kernel launch/teardown、尾部效应造成的 GPU 空转，提升 decode 的带宽利用率。
- 架构侧：循环 Transformer 通过复用参数换取更多 FLOPs，但朴素训练会爆炸；用状态空间模型式的残差分析约束 A、B 矩阵后可稳定训练并提升质量。

## 三、关键机制

### 3.1 请求生命周期与 scheduling

逐字稿给出的高层流程是：请求被调度到不同 GPU，可能做分离式 prefill/decode；先查 KV Cache 判断是否见过该请求或部分前缀；再执行核心机器学习计算；可以在机器之间、节点内跨 GPU 并行；最后得到 token，做字符串转换、stop token 检查、安全检查等（约 08:10 至 16:00 一带）。推理引擎本质上在一个“调度—执行—采样”的循环中运行。

### 3.2 Prefill 与 decode 的计算特征

逐字稿用具体例子解释：假设你有 10,000 个从未见过的 token，要计算激活与 logit，这是“10,000 个 token 输入、一个 token 输出”的 prefill，非常受计算量限制，看起来和训练时很像，只是不跑反向传播。decode 则是接下来一次生成一个 token，若 speculative decoding 工作，也许一次三到四个 token；每生成一个新 token 就要把模型再跑一遍，FLOPs 不多但非常受内存带宽限制（约 14:12 至 15:37 一带）。作者还指出 prefill 通常比单个 decode 步耗时更长，但 decode 步数远多于 prefill（约 20:31 至 20:46 一带）。

### 3.3 Continuous batching

逐字稿描述：时间向下流动，新请求不断进来；系统必须同时处理多个请求，资源既包括计算资源也包括 KV Cache 占用的内存资源；短请求可能很快完成，长请求可能因 GPU 内存不足而排队（约 16:27 至 17:45 一带）。

### 3.4 KV Cache、前缀共享与分层存储

作者解释：很多用户在说“嗨，ChatGPT/Claude”，理论上不必为每个用户重新计算；如果用户传入一本长书，先做一次 prefill，下一轮对话就不必把整个东西重算。KV Cache 使用前缀共享，用类似树的数据结构查看哪些 token 以前见过（约 18:08 至 18:50 一带）。存储层级从 GPU 开始，GPU 内存用完就放到 CPU DRAM，再进一步放到磁盘/SSD；作者提到 Jensen 近期对 CPU 性能的关注、以及 OpenAI 购买 SSD/DRAM 的传言都与这类需求有关（约 25:31 至 27:22 一带）。他还把 KV Cache 卸载与操作系统调度类比，指出 LRU 驱逐策略在这张图里被“幻觉”出来，而 LRU 与最优解差距在 2 倍以内（约 27:58 至 28:51 一带）。作者强调“从来没人希望往 GPU 上放更少流量”，在 SLA 约束下希望服务尽可能多的流量（约 29:24 一带）。

### 3.5 并行与分离式部署

对一万亿参数、280 GB GPU 的场景，不可能把整个模型装到每一块 GPU 上，可以把张量切成多份（tensor parallelism），也可以把 MoE 的不同 expert 拆到不同 GPU（约 18:50 至 19:52 一带）。实践中倾向把 prefill 与 decode 拆到不同机器集合，因为二者瓶颈不同；作者举了 NVIDIA 收购 Grok、计划用 GPU 做 prefill、用 LPU 做 decode，以及 Cerebras 与 OpenAI 的合作、SambaNova 等（约 20:11 至 21:43 一带）。还提到 NVl72 Grace Blackwell：72 块 GPU 通过快速互连连接，需要思考如何把万亿参数模型拆分到 72 块 GPU、如何处理容错（约 29:54 至 31:09 一带）。

### 3.6 大规模下的诡异 bug

作者列举了若干只有在大规模才会暴露的故障：概率 0.001% 以下的事件导致 logit 变成 NaN，模型开始输出重复 token（如“hi、hi、hi、hi”）；工具调用不再被正确处理，补全长度飙升，模型陷入“嘿，做一次互联网搜索”的末日循环数万 token；一个内核 off-by-one 错误读到未初始化内存，导致模型随机输出中文字符，被误认为是中文微调或量化问题（约 22:05 至 25:31 一带）。

### 3.7 缓存感知的 prefill-decode 分离

这是作者团队几个月前的工作，路由层只需两行代码。思路是：多数请求是对话中的逐轮请求，假设平均对话 10 轮，则约 10% 是全新的、数千 token 的新请求，计算成本高；不应把这种长 prefill 与一个进行到一半的短对话放在同一批 GPU 上。于是设置路由器：缓存命中率很低的新请求送到一组 GPU，热请求送到另一组 prefill 节点。作者称可获得高达 40% 更快的服务速度（约 31:29 至 33:22 一带）。

### 3.8 Megakernel 与 ThunderKittens

decode 的根本挑战是“必须运行整个模型才能生成单个 token”，无法获得 prefill/训练那样的大规模并行性，几乎变成“美化的内存加载器”。通常按操作逐个写 kernel 会导致大量停机：kernel launch/teardown 的红黄间隙、长短 prompt 造成的尾部效应，且会跨 kernel 累积。Megakernel 的思路是把多个操作写进一个 kernel，类似 flash attention 的融合但更激进，把 GPU 当作大规模分布式系统来调度工作。作者给出具体例子：在 QKV 投影加 RoPE 还没结束时就开始加载 KV Cache，或在 attention 结束前开始加载 O 投影权重。实现依赖一个基于指令的抽象与大型虚拟化共享内存系统，配套库是 ThunderKittens，定位类似 Triton 但更底层。回报是接近光速的解码速度：H100 上达到 72% 带宽利用率。仅对 attention 推理内核这样做能获得 30% 到 70% 的加速（约 34:17 至 41:18 一带）。作者在问答中补充：写 megakernel 极其耗费人力，一个才华横溢的 kernel 工程师一年大概只能为一种硬件、两三个模型、batch size 1 到 16 写出 megakernel（约 01:03:30 至 01:04:31 一带）。

### 3.9 Parcae：循环 Transformer 与稳定化

Parcae 出自作者在 UCSD 的实验室，由 Hayden 主导，与 Zachary、Taylor 合作。想法是取 Transformer 的某些块让它们在循环中运行：不是让 token 一次一层穿过整个模型，而是在某个时刻把它送回循环里再跑一次，从而在参数不变的情况下用“循环次数”这个旋钮增加 FLOPs。出发点之一是“每参数的最佳质量是什么”。作者引用马里兰大学 Tom Goldstein 组在 ARC 任务上的结果，并提到 OpenAI 某人曾声称 Claude 是循环语言模型、后来承认是编造的（约 41:58 至 45:38 一带）。

问题是朴素训练循环模型会爆炸：学习率扫描十次有九次不收敛，出现 NaN 和巨大损失尖峰。Parcae 的做法是把注意力、GELU、前馈等所有非线性放进一个盒子 R，只保留 A、B 矩阵来分析残差动力系统；经验观察是残差变化不大。忽略非线性后得到可用高中数学求解的闭式解，激活主要由 A 的高次幂主导。作者用标量类比：如果 A 是 2、T 约 16，就把激活提升到 2 的 16 次方，非常大——这解释了损失尖峰。此前工作中对 A、B 的选择要么是“临界稳定”要么不稳定。Parcae 约束 A 为负对角矩阵，使其高次幂趋于零；对 B 施加简单线性范数约束（B 只应用一次）。约束后谱半径小于 1，系统稳定。作者指出即使使用 6e-4 这种对其他模型很糟糕的学习率也能得到稳定模型，并展示了橙色基线爆炸到 10 的 19 次方、蓝线施加范数后激活不爆炸但损失仍可能变糟的对比：模型本来试图扩张激活以获得更大表示空间，范数把它压回来，两种压力互相争斗就表现为损失尖峰（约 45:38 至 53:31 一带）。

结果方面，作者给出与 Recurrent Depth Model 及强 Transformer 基线的比较表，称 Parcae 在多种应用上性能更高、困惑度和端到端质量更好；并做了初步缩放律实验，结论是固定参数、增加数据时也应增加递归次数，递归遵循经典幂律；问答中补充存在三维图（递归次数、数据、参数）指向同时缩放三者（约 53:31 至 59:32 一带）。

## 四、公式的假设与符号（仅依据逐字稿）

逐字稿中未给出可逐字核对的公式排版，只能整理其文字描述的符号含义，以下均为待核：

- **R**：把注意力、GELU、前馈网络等所有非线性放进的一个“盒子”，逐字稿称其为“某个大的非线性东西”（约 48:04 至 48:23 一带）。
- **A**：残差在每次循环中如何被变换的矩阵；被提升到很高次幂（约 48:23 至 50:08 一带）。
- **B**：对初始向量的某种变换，即在开始循环之前的第一个向量；只应用一次（约 48:23、51:27 一带）。
- **T**：循环步数；逐字稿在标量类比中举例 T 约为 16（约 50:29 一带）。
- **谱半径**：作者称“基本上就是范数的另一个说法”，用于判断 A 的高次幂是否爆炸（约 50:08 一带）。
- **闭式解**：忽略非线性后，给定初始激活与初始注入，可直接计算第 T+1 步的激活（约 49:30 至 49:46 一带）。

## 五、常见误区

1. **把推理等同于训练**。逐字稿反复指出 prefill 像训练（无反向传播），decode 则完全不同，受内存带宽限制，不能套用训练的并行度假设（约 14:37 至 15:37 一带）。
2. **忽略工作负载形态**。作者强调生产流量既不像训练 token，也不像凭空想象的负载；编码、摘要、闲聊、agentic 循环等形态差异巨大，输入输出 token 分布、轮次间隔、SLA 目标都不同（约 09:55 至 13:52 一带）。
3. **把小规模经验直接外推**。0.001% 概率的事件在大规模下必然发生，NaN、重复 token、工具调用死循环、随机中文输出等都是大系统特有的故障（约 22:05 至 25:31 一带）。
4. **把随机中文输出简单归因于中文微调或量化**。作者明确指出那次实际是内核 off-by-one 读到未初始化内存（约 24:07 至 25:31 一带）。
5. **以为 megakernel 是免费午餐**。作者强调它写起来非常费力，通常只为特定硬件、特定模型、特定 batch size 范围服务（约 01:03:30 至 01:04:31 一带）。
6. **以为循环模型只要叠循环就行**。朴素训练会爆炸，需要像 Parcae 那样对 A、B 做约束（约 45:38 至 52:29 一带）。
7. **只从“计算最优”单一维度看架构选择**。作者在问答中指出，还要考虑模型能否被采用、如何部署、开源后别人能否在笔记本上跑、以及硬件（如华为芯片、NVFP4 与 MXFP4）等因素（约 01:06:17 至 01:07:56 一带）。
