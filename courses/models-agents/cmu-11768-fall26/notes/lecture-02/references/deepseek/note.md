## 一、学习目标

学完本节课，应该能够：

1. 说清“工具”在语言模型智能体中的定义与边界：工具是语言模型调用外部计算机程序的接口，模型提出调用，外部软件决定是否以及如何执行（Slides 第 3 页）。
2. 区分工具的两类收益——“扩展”（Extend）与“促进”（Facilitate），并能对给定例子判断属于哪一类（Slides 第 4 页、第 5 页；逐字稿 01:17 起）。
3. 识别典型工具类别：文本回复（finish 控制动作）、信息检索、代码执行、图像生成、自定义函数（Slides 第 8–12 页）。
4. 理解“代码作为元工具”的含义与代价：表达力强、能组合控制流与库；但更难约束、影响更大，需要沙盒与资源限制（Slides 第 14–17 页）。
5. 描述工具调用的机制链路：schema 进入提示词 → 模型按自身协议发出调用 → 解析 → 校验 → 分发执行 → 用 call ID 匹配结果（Slides 第 19–25 页）。
6. 区分语法/形状/类型/取值四类约束，理解为什么约束解码“保证形式而不保证语义正确”（Slides 第 28–35 页）。
7. 比较直接 REST 调用与 MCP 的契约差别，尤其是凭证中介（credential brokering）这一点（Slides 第 37–46 页）。
8. 说明并行工具调用的适用条件、时间收益与实现要点（Slides 第 48–51 页）。
9. 用“选择—参数—轨迹—任务”四层以及效率、可靠性、安全性三个运营维度来评估工具使用（Slides 第 53–57 页）。

## 二、概念主线

本节课的主线可以概括为一句幻灯片原话：工具使用是一个分层系统（Slides 第 59 页）。

- 能力层：工具为智能体增加检索、执行、生成与应用类动作；这正是智能体区别于纯语言模型的地方。
- 机制层：schema 进入提示词；不同模型有各自的工具调用序列化协议；harness 负责校验、分发、按 ID 匹配结果。
- 约束层：JSON Schema 与语法掩码保证“形式正确”，但不保证语义正确、权限正确或工具选择正确。
- 接口层：直接 REST 调用与 MCP 是暴露能力的两种替代方式，后者额外处理凭证隔离。
- 系统层：编排依赖关系与并发，并从选择、参数、结果、成本、运营故障等角度做评估。

一个贯穿性的判断标准在 Slides 第 5 页给出：只有在工具的收益超过延迟、成本、失败与风险时，才应该调用工具。这句话是后面所有“为什么不全用代码”“为什么要沙盒”“为什么评估要看运营指标”的共同理由。

## 三、关键机制

### 3.1 工具的分类与两类收益

Slides 第 3 页给出定义与例子清单：搜索、计算器、浏览器、Python、API。Slides 第 4 页区分两类收益：

- 扩展（Extend）：访问模型参数中不可得的信息或动作。
- 促进（Facilitate）：把外部程序做得更可靠或更高效的操作委托出去。

逐字稿中的例子很适合用来检验理解：模型无从知道四个月前的日期，因为参数被冻结，这属于“扩展”；两个七位数相乘模型其实能做，但调用计算器更快更可靠，这属于“促进”（逐字稿 02:02–02:45）。Slides 第 5 页把场景与收益对应起来：当前信息→搜索→新鲜证据；精确计算→计算器或 Python→可靠执行；私有状态→账户 API→被授权的应用数据；外部动作→浏览器或 API→改变环境。

课堂互动部分补充了一批 ChatGPT 用例（逐字稿 04:00–05:52）：写代码、渲染 Blender、生成图像、商品推荐（需要网络搜索或直连电商 API）、渲染 LaTeX 并生成 PDF、与 Slack 之类的系统交互。注意 LaTeX 一处课堂上有讨论：讲师表示不确定那究竟是工具还是前端渲染，后来确认它会创建 PDF，才归为工具。这个细节提醒我们：判断某能力是“工具”还是“界面效果”，要看是否有外部程序被调用。

### 3.2 典型工具与 finish 的两种实现

Slides 第 8–12 页给出五个具体例子，均保留：

1. 文本回复：`finish("Accra is the capital of Ghana.")`。幻灯片明确标注这是 harness 控制动作（CONTROL），不是外部程序。
2. 信息检索：`search_web("site:cmu.edu announced today")` → 三条匹配新闻。
3. 代码执行：`execute_code("sum([18,23,41,54])/4")` → 34.0。
4. 图像生成：`generate_image("watercolor robot studying in a library")` → generated_image.png。
5. 自定义函数：`create_grocery_cart(["bananas","milk","coffee"])` → Cart C17 · 3 items · $31.42。

逐字稿补充了两点：其一，文本回复在智能体循环里可以用两种方式实现——单独的 finish 工具，或者“模型决定不调用工具就直接结束循环”（逐字稿 06:41–07:02）。其二，图像生成的特殊之处在于模型会在调用前大幅改写查询，历史上甚至能从下载图片时隐约看到生成器实际收到的描述（逐字稿 09:16–09:38）。这提示“决定查询内容”本身就是工具有效性的一部分。

### 3.3 代码作为元工具

Slides 第 14 页：代码在一次动作中组合控制流、库与多个操作。Slides 第 15 页引用 CodeAct，第 16 页给出结果：在展示的子集中，代码在 8/8 个模型上取得最佳成功率；在 7/8 个模型上使用最少轮数；在全部 17 个模型上这两个计数都是 12/17。逐字稿用一个具体例子解释“元工具”的意思：把“面包师烤了 200 条面包，还剩多少条”拆成赋值工具、减法工具等函数调用树，再引入循环等控制流（逐字稿 10:55–11:49）。逐字稿还给出一个经典对比任务——确定购买 Kodak 1 手机最具成本效益的国家（考虑美国、日本、德国、印度），串行方式要反复调用汇率、价格、税费工具，而写一段程序即可一次完成（逐字稿 12:44–13:30）。逐字稿转述 CodeAct 的核心结果是成功率上升、平均交互轮数下降，且这一优势甚至出现在传统上不需要代码的工具使用任务上（逐字稿 13:55）。

代价在 Slides 第 17 页列得很清楚：表达力强（循环、变量、库，适合多步数据操作与组合）；更难约束（动作空间宽，校验精度低于窄类型函数）；影响更大（文件、网络、进程），因此需要沙盒、资源限制、权限与审计日志。逐字稿的课堂问答补充了具体风险：可能写出无限循环需要额外处理；可能引入被攻破的库从而危及整个系统；更容易占用内存、磁盘、CPU（逐字稿 14:41–15:43）。

### 3.4 从 token 到分发：工具调用的机制链路

Slides 第 19 页把文本续写与工具续写并列：文本续写是“The weather is sunny.”，工具续写是 `<tool_call> get_weather(...)`，并注明“模型请求动作，harness 执行”。逐字稿补充了一个重要观察：ReAct 循环如今不再表示为独立代码，而更像是单次补全——同一份输出里既可能有给用户的文本，也有工具调用；若使用推理模型，还可能先有思维 token，再有消息，再有工具调用（逐字稿 16:35–18:05）。

Slides 第 20 页说明消息如何变成模型输入：API 层的 system/user/assistant 角色由 chat template 序列化为单一输入序列（以 Qwen 格式为例）。Slides 第 21 页给出工具定义 JSON（`get_weather`，参数 `city` 为 string 且 required）并说明 harness 同时发送 messages 与 tool schemas。Slides 第 22 页给出“定义进、调用出”：提示词含 `<tools>` 块，模型发出 `<tool_call>` 块，API 响应附带唯一 call ID。

Slides 第 23 页是重要的一页：同一份 schema，不同模型有不同序列化协议。Qwen 3.8 用 function/parameter 标签；Mistral Small 4 用 `[TOOL_CALLS]` 控制 token 加 call ID；DeepSeek V3.2 用 DSML invocation 块（`<｜DSML｜｜function_calls>` 等）。幻灯片结论是：一份 schema，模型特定的序列化与解析。逐字稿补充两处实践含义：不能假设为 DeepSeek 写的解析代码能直接用于 Qwen；微调时应当匹配模型已被训练过的工具调用格式；好消息是这类格式在 Hugging Face 的 apply chat template 一类函数中已实现（逐字稿 21:02–23:20）。逐字稿中还出现了一个关于“这些特殊 token 是否必须存在于预训练词表”的问答，讲师的回答倾向于：通常并非必须在全网预训练阶段就存在，更典型的是在中间训练阶段引入，之后再做强化学习（逐字稿 18:05–19:10）。这一细节涉及训练流程，具体表述以原视频为准。

Slides 第 24 页给出 OpenHands 的分发流程：初始化时注册（`resolve_tool(spec, state)` → 名称到 `ToolDefinition`（schema · Action · executor）的 `tools_map`）；每次模型调用时分发（解析 `{name, args}` → 查表 → 用 `action_from_arguments(args)` 校验 → `executor(action)` → 返回 `ObservationEvent(call_id)`）。逐字稿补充了两类失败：校验失败（模型给出错误的工具调用）和执行失败（例如 Python 工具接受任意字符串，但真正运行时才报错）（逐字稿 24:15–25:05）。

Slides 第 25 页说明结果按 call ID 返回：assistant 的 tool call 带 `"id": "call_123"`，tool 结果消息带 `"tool_call_id": "call_123"`，并注明这同样适用于并行调用。逐字稿给出一条容易踩坑的实践细节：部分提供方（讲师以 Anthropic 为例）在出现“工具调用没有匹配的工具结果”时会直接拒绝该历史并停止生成，这在程序崩溃后恢复的场景中会造成麻烦（逐字稿 25:33–26:47）。此说法属于讲师经验陈述，未在幻灯片中给出，使用时宜标注为课堂经验。

### 3.5 约束解码：保证形式，不保证正确

Slides 第 27 页给出畸形工具调用的例子：JSON 缺少最后的右括号，harness 无法解析。Slides 第 28 页列出四类约束：语法（valid JSON）、形状（expected fields）、类型（city 是 string）、取值（units 是 C 或 F），并明确边界：约束保证形式，不保证真值、权限、工具选择或任务成功。

Slides 第 29 页给出 JSON Schema 示例，含 `type`、`properties`、`enum`、`required` 与 `additionalProperties: false`，并列出其特点：用于描述 JSON 数据的词汇表、类型/必填字段/允许取值、机器可读的验证规则。Slides 第 30 页用两棵派生树对比：`{"city":"Pgh","units":"F"}` 可由 `unit → "C" | "F"` 派生；`{"city":"Pgh","units":"K"}` 不行，因为 K 不能从 unit 派生（注意幻灯片设定不接受 Kelvin 作为温度单位）。

Slides 第 31 页解释下推自动机（PDA）：有限控制记录文法规则中的局部位置，栈记忆任意深度的嵌套。逐字稿给出更通俗的对照：正则文法可用有限状态自动机解析，而 JSON Schema 不能只用正则文法表达，需要上下文无关文法，进而需要带栈的 PDA；做法是在从左到右生成输出时逐步验证（逐字稿 29:22–32:38）。

Slides 第 32 页给出关键工程细节：语法检查发生在分词之下。先编译一次（`unit → "C" | "F"` 编译到字节级 PDA），再对每个候选 token 检查：token `t₁: "F"}` 解码为字节 `22 46 22 7D`，对全部字节跑 `advance(bytes)`，保留或掩蔽。幻灯片特别提醒：一个 token 可能跨越多个语法终结符，也可能停在某个终结符中间，因此不能把 token 边界当作语法边界。

Slides 第 33 页给出缓存 token 掩码的四步流程：1）解析前缀，对已输出字节推进持久 PDA 栈；2）取缓存决策，栈顶节点索引预计算的、与上下文无关的 token 有效性；3）检查少数派，把上下文相关的候选 token 对完整栈运行，并在匹配的栈之间求并集；4）掩蔽并继续，合并决策、掩蔽 logits、采样 token、更新 PDA 栈。Slides 第 35 页总结加速来源：缓存处理大多数 token、持久栈支持分支、CPU 工作与 GPU 推理重叠。逐字稿补充了 token 掩蔽的直观理解：对每个候选 token 看文法是否允许，允许得 1，不允许设为负无穷，再重新归一化（逐字稿 33:05–33:31），并提到这套方法被广泛用于推理库、由本校机器学习系的人开发（逐字稿 32:38）。

一个重要的边界情形（逐字稿 34:27–35:17）：即使有约束解码，仍可能拿不到格式良好的工具调用——当 token 预算用完时，输出可能仍在一条有效路径上但没有到达终态。讲师称这是很罕见的难题，并把“在推理栈里实现按剩余 token 数截断”当作可选的加分方向提及；这类具体做法未在幻灯片中给出，属于课堂提议，不宜当作官方要求。

### 3.6 REST 与 MCP

Slides 第 37 页：库暴露的是进程内 API，调用方与被调函数共享同一进程，Python 提供名称、参数、类型与返回类型，但还不能远程调用——网络客户端仍需要地址、协议、序列化与认证。示例 `weather_lib.py` 定义了 `get_weather(city, units: Literal["C","F"]="F") -> Weather`。

Slides 第 38 页：REST API 通过 HTTP 暴露函数，示例以 FastAPI 绑定端点并记录 API key 头（`X-API-Key`）。Slides 第 39 页说明 REST 服务器发布 OpenAPI 描述：OpenAPI 描述 HTTP 操作，内嵌 JSON Schema 描述其取值。

Slides 第 40 页：编码智能体常用 curl 直接调用 REST API，并给出示例命令；同时指出风险——有 shell 权限的智能体也可能读取或滥用该密钥。幻灯片原话是：直接 REST 访问很简单，但智能体的 shell 会拿到 API 凭证。

Slides 第 42 页说明 MCP 连接 host 与 servers 的拓扑：本地 stdio（文件系统服务器）、远程 HTTP（Sentry 服务器），并明确 MCP 是面向智能体的替代接口，而不是调用 REST API 的必要条件。Slides 第 43 页说明 FastMCP 默认把每个 OpenAPI 路由转换成可发现的 MCP 工具。Slides 第 44 页强调用分离的凭证启动 MCP：`UPSTREAM_API_KEY` 授权 API 调用，`MCP_API_KEY` 保护 MCP 端点；并注明静态 token 仅用于教学/开发，生产应校验 JWT 或使用 OAuth。Slides 第 45 页给出关键机制——凭证中介：服务器接受一个凭证并在上游使用另一个凭证，模型看不到任何一个秘密。

逐字稿对这部分补足了动机：讲师起初认为有了 API 就不需要 MCP，后来认可的核心区别是安全层——上游 GitHub token 给 MCP 服务器，而不是给智能体；给智能体的是 MCP API key，这样即使泄露也相对无害，否则智能体可能把 GitHub token 推到公开仓库（逐字稿 39:00–42:51）。逐字稿还提到 MCP 注册表与第三方目录站点的存在（逐字稿 44:11–44:39），这类具体站点与数量属于口头提及，宜按待核处理。

Slides 第 46 页给出对照表：两者共享名称、描述与结构化输入的 JSON Schema；发现方式不同（取 OpenAPI 文档 vs 运行时 `tools/list`）；调用方式不同（HTTP 动词+路径+参数 vs 经 MCP 传输的 `tools/call`）；认证不同（客户端认证到 API vs 客户端认证到 MCP、上游认证分离）；范围不同（描述 HTTP 操作 vs 还支持 resources、prompts 与 extensions）。

### 3.7 编排并发

Slides 第 48 页给出串行成本：生成 0.8s + 天气 1.2s + 生成 0.8s + 日历 0.9s + 生成 0.8s + 航班 1.1s + 生成 0.8s ≈ 6.4 秒。Slides 第 49 页给出并行成本：两个生成阶段加最慢的工具，即 2 × 0.8 + max(1.2, 0.9, 1.1) ≈ 2.8 秒。这些是幻灯片给出的示意数值，用于说明结构差异，不是实测基准。

Slides 第 50 页给出并行前提：可安全并行的是“匹兹堡天气 / 读今天的日历 / 查航班状态”；必须串行的是“找客户 ID / 用 ID 取订单 / 退款选中的订单”。结论是只并行独立且可安全并发的调用。Slides 第 51 页给出实现要点：用 `asyncio.gather(..., return_exceptions=True)` 并发执行，并在结果乱序返回时保留 call ID。

逐字稿补充了两点：其一，并行调用通常通过一次智能体响应里放多个工具调用块实现，执行上一般真并发（逐字稿 45:25–47:01）。其二，讲师提出一个有趣的观察——更新、更强的模型在并行工具调用上表现好得多，原因之一是强化学习对任务时长施加重惩罚，迫使模型并行化；这一点是课堂推论（逐字稿 47:01–48:37），不应当作已被幻灯片确认的结论。

### 3.8 评估

Slides 第 53 页列出 Berkeley Function Calling Leaderboard V4 的维度：单轮（simple、multiple、parallel、multiple-parallel）、多轮（base、missing function、missing parameter、long context）、智能体（web search、memory）、鲁棒性（幻觉测量、格式敏感性）。

Slides 第 54 页给出四层“评估整栈”的框架（保留示例指标）：选择（工具对否，precision/recall，不需要执行，典型失败是缺失或多余调用）；参数（值对否，AST/schema 匹配，不执行，典型失败是字段或值错误）；轨迹（顺序对否，序列成功率，通常要执行，典型失败是依赖错误）；任务（目标达成否，端到端成功，要执行，典型失败是看似合理的错误答案）。

Slides 第 55 页给出三个运营维度：效率（延迟、调用数、token、成本）、可靠性（超时、重试、部分失败）、安全性（策略、权限、副作用）。幻灯片特别指出：一个正确的智能体仍可能慢到或贵到不可用；可靠性评估应在真实提供方行为下报告任务成功率；安全性需要测试对抗性输出和高后果动作。

Slides 第 56 页给出运营故障的归因表：模型（错工具、坏参数、忽略结果）、harness（解析、认证、校验、ID 不匹配）、提供方或工具（超时、限流、执行错误）。结论是生产评估既需要基准准确率，也需要运营失败率。

Slides 第 57 页是 OpenRouter 提供方工具调用错误率图（来源标注为 2026 年 8 月 27 日）。逐字稿提到该图针对同一个模型的多个提供方，错误率差异很大（逐字稿 51:43–52:14），并讨论了原因：量化级别（FP8 与 FP4 的差别）、投机解码是否有损、各提供方是否实现约束解码、以及提供方本身的可靠性（逐字稿 52:40–55:49）。需要强调：图上的具体数值在本笔记的文本提取中无法确认，属“待核”；上述原因分析是课堂讨论，且讲师对部分点使用了“可能”“我不确定”等措辞，不应写成确定结论。

## 四、公式与符号的假设

本讲没有需要推导的数学公式，出现的都是成本估算式与形式语言记号，因此这里列出的是“读法与其背后的假设”。

1. 时间估算（Slides 第 48、49 页）
   - 串行总时长 ≈ Σ(每次生成) + Σ(每个工具)。
   - 并行总时长 ≈ 2 × 0.8 + max(1.2, 0.9, 1.1) ≈ 2.8 秒。
   - 符号：0.8s 为一次生成的示意时长；1.2/0.9/1.1s 分别为天气/日历/航班工具的示意时长。
   - 假设：这些是教学用示意数值而非实测；并行要求调用之间不存在依赖；每次“生成”时长相同；工具之间可真正并发且不会互相限流。若实际提供方限流或工具共享资源，该估算不成立。

2. 约束解码的掩蔽规则（Slides 第 34 页图；逐字稿口头描述）
   - 讲师口头描述为：合法下一 token 得 1，非法得 0，把非法项设为负无穷，再重新归一化，使概率只落在合法 token 上。
   - 待核：Slide 34 是图示，其具体公式与坐标含义仅凭文本提取无法确认，本笔记不给出公式形式。

3. 形式语言记号（Slides 第 30、32 页）
   - `unit → "C" | "F"`：产生式写法，表示 unit 可派生为 C 或 F。幻灯片明确把 K 排除在温度单位之外。
   - `advance(bytes)`：PDA 对字节序列推进状态的函数，输入是 token 解码后的字节（如 `22 46 22 7D` 对应 `"F"}`）。
   - 假设：文法先编译一次到字节级 PDA；检查发生在分词之下；因此 token 边界不能当作语法边界。

4. “选择—参数—轨迹—任务”四层（Slides 第 54 页）
   - 这不是公式，而是一个评估分解。其隐含假设是：某些指标（选择、参数）无需真正执行即可测量，而轨迹与任务指标通常需要执行。

## 五、常见误区

1. 以为约束解码能保证正确。Slides 第 28 页明确：约束只保证形式，不保证真值、权限、工具选择或任务成功。逐字稿的 Python 例子更直白：字符串可以被解析为 Python，但程序本身仍可能是错的。
2. 以为工具调用格式是通用的。Slides 第 23 页的三家格式并列说明不能跨模型复用解析逻辑；逐字稿补充微调时必须匹配已有格式。
3. 以为代码越多越好。代码表达力强，但动作空间宽、校验不精确、影响面大，需要沙盒、资源限制、权限与审计（Slides 第 17 页）。
4. 以为 MCP 只是“换个方式调 API”。Slides 第 46 页的对照表与第 45 页的凭证中介说明：MCP 的核心差异之一是认证与凭证分离，而不是调用语法。
5. 以为工具结果可以随便丢弃或错配。Slides 第 25 页强调 call ID 匹配，尤其在并行场景；逐字稿补充缺少匹配结果时某些提供方会拒绝该历史。
6. 以为并行就是“把所有调用一起发出去”。Slides 第 50 页给出明确反例链：找 ID → 取订单 → 退款。
7. 以为准确率就是全部。Slides 第 55 页：正确但慢或贵的智能体可能不可用；还需要可靠性（超时、重试、部分失败）和安全性（策略、权限、副作用）。
8. 以为同一模型在不同提供方表现一致。Slides 第 57 页与逐字稿讨论表明背后有量化、解码算法、约束解码实现与可靠性等差异（具体数值待核）。
9. 把 finish 当成外部工具。Slides 第 8 页把它标注为 harness 控制动作。
10. 把攻击面只放在模型上。Slides 第 56 页的归因表把故障分给模型、harness、提供方或工具三方。

## 七、术语对照（便于回看幻灯片）

- 工具（tool）：语言模型调用外部计算机程序的接口（Slide 3）。
- 扩展 / 促进（Extend / Facilitate）：两类工具收益（Slide 4）。
- 元工具（meta-tool）：指代码，因其能组合控制流、库与多操作（Slide 14）。
- 工具调用（tool call）：模型输出的动作请求，由 harness 执行（Slide 19）。
- chat template：把角色化消息序列化为单一模型输入序列（Slide 20）。
- call ID：把工具结果匹配回调用的标识，含并行场景（Slide 25）。
- 约束解码（constrained decoding）：在解码时掩蔽不合文法的 token（Slides 第 27–35 页）。
- JSON Schema：描述 JSON 数据的机器可读验证规则（Slide 29）。
- 下推自动机（PDA）：有限控制加栈，可解析上下文无关文法（Slide 31）。
- OpenAPI：描述 HTTP 操作并内嵌 JSON Schema（Slide 39）。
- MCP：面向智能体的替代接口，含独立凭证与工具发现（Slides 第 42–46 页）。
- 凭证中介（credential brokering）：服务器接受一个凭证、在上游使用另一个凭证（Slide 45）。
- 并行工具调用：独立调用共享一次生成与一次等待（Slides 第 48–51 页）。
