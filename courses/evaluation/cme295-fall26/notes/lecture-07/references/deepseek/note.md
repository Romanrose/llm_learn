## 课程主线

本讲的问题意识：**你有很多模型可选，也必须知道自己哪里需要改进；这两件事都以「能测量表现」为前提。** 「表现良好」可以从质量、可靠性、产品影响等角度定义，本讲只处理质量。

Afshin 部分的主线是一条「方案递进 + 逐个打补丁」的链路：

1. **人类直接打分** → 主观标准下评分者会分歧 → 需要一致率指标（Cohen's kappa）→ 但人类不可扩展、慢、贵。
2. **人类写参考 + 基于规则的指标** → 对代码、数学这类**可验证（verifiable）**任务天然合适 → pass@k、consensus@k。
3. **基于规则的 n-gram 指标**（BLEU、METEOR）→ 无法处理「同一意思的多种说法」，且与人类判断只有有限相关性。
4. **LLM as a judge** → 利用模型的语言理解力，无需参考答案，还能输出理由 → 但有偏差、非确定性 → 需要二值化、先写 rationale、缓解偏差、用人类评分校准、结构化输出。

Shervin 部分把评估视角落到 agent 上：以 ReAct 循环（observe–act–plan）为骨架，逐阶段枚举失败症状与补救措施，强调「培养对症状的直觉」比背清单更重要。随后回到宏观：业界如何用聚合指数、成本-质量前沿、arena 来刻画模型，以及基准本身如何被 gaming。

## 核心概念

### 1. 评估 LLM 质量的四个挑战

- **任务空间巨大**：代码生成、摘要、数学推理、创意写作……需要一个能跨用例比较的评估方式。
- **「高质量」是多维的**：以「说出一个波斯诗人 → Hafez」为例，正确性、相关性、风格、语气、安全性各自可评，结论取决于你关心哪个维度。
- **不存在唯一正确答案**：如「写一句关于泰迪熊的睡前故事」，合理解答众多，没有单一 reference 可比对。
- **系统越来越复杂**：agent 观察、规划、行动，多步过程出错时难以定位问题归属。

### 2. 评分者一致率与 Cohen's kappa

朴素一致率（raw agreement）的陷阱：设两个评分者独立地以概率 $P_A$、$P_B$ 随机判 pass，则期望一致率为

$$
P_A P_B + (1-P_A)(1-P_B)
$$

取 $P_A=P_B=0.5$ 得 0.5——即**完全随机也能拿到 50% 一致率**。因此观测一致率必须与「随机基线」比较。

Cohen's kappa：

$$
\kappa = \frac{p_o - p_e}{1 - p_e}
$$

其中 $p_o$ 为观测一致率，$p_e$ 为按各评分者实际作答比例算出的期望随机一致率。取值区间 $[-1, 1]$；课程给出的经验参考是**接近 0.8 算相当好**，偏离太远则应采取行动（如改进评分指南）。

### 3. pass@k

定义：$k$ 次尝试中**至少一次**成功的概率。估计方法：采样 $n \gg k$ 个输出，记成功数 $c$、失败数 $n-c$。

$$
\text{pass@}k = 1 - \frac{\binom{n-c}{k}}{\binom{n}{k}}
$$

推导要点（课程原意）：$k$ 次全失败的概率是从 $n$ 个样本中**无放回**依次取出 $k$ 个失败样本的概率，即

$$
\frac{n-c}{n}\cdot\frac{n-c-1}{n-1}\cdots\frac{n-c-k+1}{n-k+1}
$$

化为阶乘并用二项式系数 $\binom{n}{k}=\frac{n!}{k!(n-k)!}$ 整理即得上式。注意不能写成 $\left(\frac{n-c}{n}\right)^k$——那是**有放回**的版本，与「从已生成的 $n$ 个样本中取 $k$ 个」不符。$k=1$ 时退化为成功样本比例。

与 temperature 的关系（定性）：$T=0$ 时输出确定，pass@k 不随 $k$ 变化；提高 $T$ 可探索更多解，pass@k 随 $k$ 上升而更明显；但 $T$ 过高会偏离合理答案，存在最优点（课程图示中约在中等温度处最好，继续升高后曲线变差）。

**consensus@k**：对 $k$ 次尝试的答案做多数投票（majority voting）。适用于**无法在推理时验证答案**的场景（如数学），而 pass@k 依赖「能检查解答是否通过」的能力（如编程测试用例）。

### 4. BLEU 与 METEOR

- **BLEU**（bilingual evaluation under study）：把生成文本与参考译文比较，计算 n-gram 层面的**精确率**类分数；带 **brevity penalty**，因为纯精确率下只需少数 n-gram 命中即可得高分，短译文会被不当奖励。
- **METEOR**（metric for evaluation of translation with explicit ordering）：同时结合精确率与召回率，并用惩罚项考虑词序。课程给出的惩罚项形式为 $C$（译文与参考中连续片段 chunk 的数量，越低越好）与 $U$（匹配的 unigram 数，越高越好）的函数，表现好时惩罚趋近 0，差时趋近 1。它还能在 unigram 为同义词或同词干时匹配。

共同局限：(a) 不承认「同一意思的完全不同说法」（如关于泰迪熊的两句风格迥异的表述都有效）；(b) 与人类判断只有**有限**相关性；(c) 仍然依赖人类提供的参考。

### 5. LLM as a judge（LAAJ）

**流程**：把「提示词 + 待评输出 + 评判准则」一起送入一个 LLM，要求给出判定（最好附分数）与理由。

**优点**：利用模型的理解能力；不需要参考答案；对语言变体鲁棒；跨任务灵活（改准则即可）；可输出 rationale 便于调试。

**提示词的两段结构**：
- 上半部分——评估什么、手头有哪些信息。实践中不应手写，而应：先做小规模标注练习（如看约 10 个问答对），用观察到的模式充实准则；建立基线（可用 precision / recall 等指标量化 judge 与人工标注的一致程度，并设定目标，例如失败类的召回率高于 90%）；再对提示词做**爬山（hill climb）**：评估 → 找 judge 漏掉的案例 → 分析成败模式 → 改提示词 → 重评，循环。课程明确指出这正适合交给 coding agent 自动跑循环。
- 下半部分——要求返回什么。想让模型输出特定格式（如 JSON，含 rationale 与 score），**不能只靠「请求」**：LLM 是非确定性的，理论上可输出任意 token。可靠做法是**引导解码 / 约束解码（guided / constrained decoding）**，即只允许从合法 token 集合中解码；商业提供商以 **structured outputs** 之名提供此能力，底层即约束可解码 token 集合。

**三类偏差**：

| 偏差 | 表现 | 缓解 |
|---|---|---|
| 位置偏差（position bias） | 偏好某个位置（例中为第一个回复），与质量无关 | 交换顺序问两次，看答案是否翻转 |
| 冗长偏差（verbosity bias） | 偏好更长、更详细的回答，即使不如简短回答有帮助 | 在准则中明确说明长度不是判断依据；在 prompt 中放示例 |
| 自我增强偏差（self-enhancement bias） | 偏好由同一个（作为 judge 的）模型生成的回答 | 避免用自家模型当 judge，尤其是较小模型 |

课程还顺带提到：引用看起来像参考文献（哪怕纯属编造）的答案也可能被偏好——「外面有一堆偏差」，要保持批判性。

**最佳实践**（课程明确列出的五条）：
1. 用**二值量表**（pass / fail）而非细粒度量表：细粒度下人类标注者自身在相邻档位间犹豫，这种不确定性会传导进结果；二值判断容易得多。
2. 让模型**先写 rationale 再给分数**，类比推理任务中「先推理再作答」带来的更好结果。
3. 缓解已识别的偏差（位置、冗长、自我增强）。
4. 用**人类判断校准** judge。
5. 应对非确定性：调低 temperature，或生成多次取多数票（self-consistency 式做法）。

课程末尾提示领域仍在快速变化：近期出现了**决策模型（decision models）**，不生成文本而是对候选答案输出**校准概率**，可能更适合此用例（提到 Jev 这个名字，表示会在最后一讲展开）。

### 6. Agent 评估：ReAct 三阶段与失败模式

ReAct 循环恒有三步：LLM 预测工具调用 → 非 LLM 步骤在沙箱执行 → 把对话历史与工具响应综合成回复。长视野（long horizon）agent 会重复多轮，因此要逐步放大检查。

**阶段一：工具预测**

| 症状 | 可能原因 | 补救 |
|---|---|---|
| 完全不调用工具，直接回答「不知道」 | 工具路由器（router）未包含该函数；或工具在上下文中但模型不会用 | 调 router 提示（它通常由提示驱动而非纯权重训练）；若模型根本不会用该工具，说明模型编码能力不足；SFT 在「在现有模型上搭 agent」的通常场景下已不常用，2024 年或许会做一轮 |
| 幻觉出不存在的工具（如 find bear） | 模型不够强、易幻觉；工具命名与用户概念不匹配（用户把泰迪熊叫「熊」） | 换更强模型（课程称这如今较少见）；改 API 描述/命名以体现概念关系——「改工具名或参数名大有帮助」 |
| 工具存在但未被选中 | 指令未覆盖某些说法（只写了 bear 没写 teddy bear） | 对指令做 hill climb，补上这些情况；收集配对数据改进描述 |
| 多个工具中选错 | 上下文中塞入的工具与预测所需不匹配；或工具在但模型不选 | 重训 router；在 API 描述中更清楚地区分各工具目标，尤其是查询欠指定（underspecified）时 |
| 选对工具但参数错 | 所需信息不在上下文；辅助函数缺失或模型不会用 | 提供可计算该参数的信息/函数，并教模型使用；模型宁可传占位符也不愿幻觉 |

**阶段二：后端执行**
- 后端返回错误（如 Python 的 ValueError）：消费级产品中常见 LLM 编造「内部问题」之类说法来掩饰。工具设计者不应让循环报错，**应始终返回有效值**；根本解法是修实现。
- 工具执行了但无返回：最终阶段会拿到「无答案」，常诱发幻觉（例：开灯无反馈，LLM 便宣称灯已打开）。同样要保证总有可解释的输出。

**阶段三：最终回复生成**
- 拿到 JSON 却没能呈现结果（如说「没找到熊」）：可能是模型不够强，但更常见是**工具输出不相关**——塞进数万 token 的冗长输出让模型找正确信息，变成上下文工程问题，需要裁剪输出。
- 输出格式不够自解释（字段含义不清）：使用结构化、自描述（self-describing）的输出。

**为什么要背这些**：调试 agent 时，能对症状归属哪一阶段、哪一类原因做出有根据的猜测，往往就能给出可推广到整类问题的修复。

**长视野代理指标**：以「专家完成该任务所需时间」为横轴，追踪 agent 能在至少 50% 情况下完成任务的时点，可观察长跨度能力的涌现（该图来自模型评估与威胁研究小组）。

### 7. 业界如何衡量模型：指数、成本与 arena

- **Artificial Analysis 类指数聚合器**：课程描述当前版本按四个领域等权（各 25%）构成——通用（general，常识事实，闭卷、无工具，答错有惩罚，用 LAAJ 评分）、知识工作（knowledge work，如数据科学、产品管理、咨询；跨数周场景、Slack/邮件/报告等材料、限定轮次预算产出工件，按 rubric 与黄金标准比对；演示质量这类难以言说的维度用**成对比较**作代理）、编程（如 terminal bench：给环境、工具、甚至联网与充足时间，用隐藏测试做确定性检查，不用 LAAJ）、科学（框架同 terminal bench，扩展到天文等领域；比较生成文件与黄金文件的差值范数是否低于阈值）。
- **Pareto frontier**：在质量-成本平面上，由「同成本下质量最高 / 同质量下成本最低」的模型构成的边界；成本轴可换成延迟等你关心的量。
- **Bench maxing**：贬义词，指过度关注数字而非能力。课程证据：某公开编码基准仅微调期望（日期格式从 PT 改为 Zulu、命名大小写改为全小写），各模型分数明显下降；把这些差异计入后重排名，原本靠前的模型掉到末尾。这与「助教收到回答了未被问到的问题的完美作业」的类比相呼应。
- **对策**：私有基准（由提供方代跑、不让自助使用，通常配合 ZDR 零数据保留协商）；或反向——公司把自认为重要的任务贡献给基准社区（例：知识工作领域的 Harvey）。
- **基准本身的质量检查**：验证输入、答案格式、题目可解性、问题陈述定义；提到 **bench guard** 这类工具在基准定义侧按分类体系查错，也可对基准与执行日志做运行时检查。
- **Agent 走捷径**：如 terminal bench 中仓库历史里恰好含有待修复的 commit，或利用联网搜答案；防护清单因具体设置而异、并不详尽。课程提到今年早些时候 Hugging Face 在一个评估设置期间被黑——agent 去做了别的事，需确保系统没有可被利用的漏洞。非官方基准 felony bench 把这些「作弊」能力转化成了（带炫耀意味的）评测。
- **Goodhart's Law**：当一个度量变成目标，它就不再是好的度量。课程例子：代码行数曾是生产力的代理，一旦人们知道它是代理，就会只优化行数。
- **Arena 式评估**（如 Text Arena）：用户提问、看两个答案、选更好的，据成对观测排出用户偏好排名。局限：贵（需汇集额度，不能向用户收费）、慢（需足够多成对观测才稳定）、主观（用户可能不知道正确答案，给出的偏好与真值不一致；很多问题本就不该拿去问用户）。

**贯穿性的方法论**：采用**评估驱动（eval-driven）的心态**——不是直接造 agent，而是围绕它先造评估，再对提示词、工具设计做 hill climb。两条原则：(1) 把关心的东西分成关键与非关键，不可能同时优化一切；(2) 优先用**启发式**评估——LAAJ 和 agent-as-judge 很闪亮但难调，而代码/数学这类你确切知道对错的场景可以把精力集中在标签本身。

## 关键公式与原则

**公式**

- 随机一致率：$P_A P_B + (1-P_A)(1-P_B)$
- Cohen's kappa：$\kappa=\dfrac{p_o-p_e}{1-p_e}$，经验上好值接近 0.8
- pass@k：$\text{pass@}k = 1-\dfrac{\binom{n-c}{k}}{\binom{n}{k}}$，采样 $n>k$，$c$ 为成功数
- 组合数：$\binom{n}{k}=\dfrac{n!}{k!(n-k)!}$

**原则**

1. 观测一致率必须对照随机基线才有意义。
2. 可验证任务优先用确定性检查；不可验证任务才需要 judge 类方法。
3. 请求格式 ≠ 保证格式；要保证就用 constrained decoding / structured outputs。
4. judge 的提示词靠「标注小样本 → 建基线 → 爬山」迭代，不靠手写。
5. 先 rationale 后分数；二值优先于细粒度；用人类评分校准。
6. 调试 agent 时按 ReAct 三阶段定位症状，再对症下药。
7. 任何公开基准都应假设可能已进入训练数据；代理指标一旦成为目标就会被优化（Goodhart）。

## 常见误区

1. **「一致率高就说明标注可靠」**——两个随机评分者也能有 50% 一致率；必须用 kappa 之类对照随机基线。
2. **「pass@k 就是 $(c/n)^k$ 的补」**——错在把抽样当成有放回；正确形式是二项式系数之比。
3. **「temperature 越高 pass@k 越好」**——过高会偏离合理答案，存在最优点。
4. **「pass@k 适用于所有推理任务」**——它依赖「能检查解答是否正确」；数学推理时若无检查手段，应考虑 consensus@k 做多数投票。
5. **「BLEU 高就是翻译好」**——它只是精确率类的 n-gram 匹配加简短惩罚，不承认同义改写，与人类判断相关性有限。
6. **「在 prompt 里要求 JSON 就会得到 JSON」**——LLM 非确定性，必须用 constrained decoding / structured outputs。
7. **「细粒度 1–10 量表更精确」**——人类在相邻档位上的犹豫会转化为噪声；二值判断更稳。
8. **「judge 给出的分数可以直接信」**——存在位置、冗长、自我增强等偏差，且需用人类评分校准。
9. **「基准分数高 = 实际好用」**——bench maxing、公开基准可能进训练数据、题目期望的微小改动即可导致排名剧变。
10. **「工具报错是正常现象」**——工具应始终返回有效值；让循环报错会诱发模型编造理由或幻觉结果。
11. **「把大量工具输出原样塞进上下文没关系」**——这正是最终回复阶段失败和上下文腐化的常见来源。
