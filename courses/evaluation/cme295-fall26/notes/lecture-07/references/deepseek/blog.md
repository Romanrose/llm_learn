# 让“好”变得可测量：Stanford CME 295 第七讲中的 LLM 评估方法

## 导语

在 CME 295 的第七讲中，课程从“如何训练和使用 LLM”转向了一个同样关键但更棘手的问题：**我们怎么知道一个模型到底好不好？** 这个问题看起来简单，实际却充满了歧义。Afshin 在开场就指出，“表现良好”可以从质量、可靠性、产品指标等多个角度定义，而本讲聚焦于质量维度。随后，课程沿着一条清晰的递进路径展开：先说明为什么评估 LLM 如此困难，再讨论人类评分的价值与局限，接着系统介绍基于规则的指标（尤其是 pass@k）、LLM as a judge 的实践与偏差，最后把这些评估思路落到 AI agent 的调试和行业基准生态上。Shervin 接棒后，用 ReAct 循环中的三类失败模式说明如何诊断 agent 问题，并进一步讨论 Artificial Analysis 指数、benchmark 污染、Pareto frontier 和评估驱动的工作方式。

这篇 Blog 试图把两段讲授串成一条完整论证：**LLM 评估的核心困难在于“好”本身是开放式的；因此评估方法必须从可验证任务出发，逐步扩展到主观任务和复杂 agent 系统，同时始终警惕指标被优化、被污染、被偏差扭曲。**

## 一、为什么 LLM 评估一开始就这么难

课程先为评估问题建立动机。LLM 被设定为 text-to-text 问题，但“表现良好”并没有单一含义。Afshin 给出三个角度：质量（输出是否正确、相关、安全）、可靠性（是否一致、失败后能否恢复、是否存在分布偏移、延迟是否合理）、以及产品角度（用户影响、采用率、参与度）。本讲只聚焦质量，但即便缩小到质量，挑战仍然很多。

第一个挑战是任务范围极广。LLM 可以生成代码、总结文本、做数学推理、创意写作，用例数量庞大，评估方法必须能跨这些用例工作。第二个挑战是“高质量”取决于你关心的维度。课程用“说出一个波斯诗人”的例子说明：模型回答“Hafez”在正确性和相关性上没问题，但语气可能居高临下，安全性也许没问题，风格却未必好。换句话说，评估一个答案是否高质量，首先要明确评估维度。第三个挑战是输出类型多样，不存在唯一正确答案。让模型“写一个关于泰迪熊的一句话睡前故事”，可能得到“每天晚上，泰迪都向月亮挥手，直到有一天晚上月亮也向他挥手”，这很合理，但还有很多同样合理的答案。因此不能只靠一个 reference 去对比。第四个挑战是系统复杂度上升。AI agents 能观察、规划并行动，执行多步过程，一旦出错，诊断问题出在哪一步就没那么简单。

这四个挑战共同构成了本讲的论证起点：**评估不是一个单点指标问题，而是一个需要选择维度、选择任务类型、选择参考方式、选择诊断层级的系统问题。**

## 二、人类评分：有价值，但不可扩展

面对开放式输出，一个自然的思想实验是：既然人类能理解细微差别，为什么不直接让人类给每个 LLM 输出打分？

课程指出，人类评分确实有价值，但有一个特别挑战：评分者可能对同一输出产生分歧。例子是问 LLM 助手“我该买什么生日礼物”，模型回答“那就买泰迪熊吧，因为它几乎总是一份温馨的礼物。挑一个你觉得合适的就好。”有些评分者觉得有用，另一些可能觉得没用，比如对方已经有一大堆泰迪熊。对于正确性这类客观标准，分歧不大；但对于有用性这类主观标准，就需要清晰指南，并衡量评分者之间的一致程度。

接下来课程用一致率（agreement rate）说明为什么朴素指标不够。假设两个评分者 Alice 和 Bob 把输出分为 pass / fail 两类，Alice 以 PA 的概率回答 pass，Bob 以 PB 的概率回答 pass。如果两人完全随机且独立地打分，一致率是 PA·PB + (1−PA)(1−PB)。当 PA = PB = 0.5 时，一致率是 0.25 + 0.25 = 50%。这意味着，即使评分者只是随机作答，也可能得到看起来不低的一致率。因此需要一个基准，把观察到的一致率与随机作答的预期一致率比较。Cohen's kappa 做的就是这件事：取观测一致率 p_o，减去随机预期一致率 p，再除以 1−p，取值在 −1 到 1 之间。课程说，通常好的指标会接近 0.8；如果离 0.8 或 1 太远，就可以据此采取行动。

但人类评分的根本问题不只是主观性，还有可扩展性。人类需要时间，面对大量 LLM 输出会很慢、很贵。思想实验的结论是：**人类评分很有帮助，但必须小心主观标准，而且它不会具有可扩展性。**

## 三、从可验证任务开始：pass@k 与 consensus@k

于是课程转向另一种做法：让人类为一些提示写出答案，然后用基于规则的指标把 LLM 输出与参考比较。这比每个输出都人工评分更好，因为人类只需做一次参考，之后可以反复计算指标。但关键问题是：哪些任务适合这种方式？

课程给出的自然候选是代码和数学，因为这些问题是可验证的。编程题可以让 LLM 生成解答，然后用一堆测试用例确定性地检查是否通过；数学题可以让 LLM 输出推理和答案，再与人类答案比较。

在这类场景中，课程重点介绍了 **pass@k**。它定义为 k 次尝试中至少有一次成功的概率。为什么关心这个指标？因为有时你有时间、有计算资源生成多个解答，也有办法检查解答是否有效，所以你不仅关心一次尝试是否正确，而是关心中间有一次正确。

课程详细推导了如何从 n 个采样输出估计 pass@k，其中 n > k。记 c 为成功尝试数，n−c 为不成功尝试数。k 次尝试中至少一次成功等于 1 减去 k 次中零次成功的概率。零次成功需要连续选到 k 个不成功尝试：第一次有 (n−c)/n 的机会，第二次有 (n−c−1)/(n−1)，依此类推，乘 k 项。课程进一步把它写成组合数形式，得到无偏估计量：1 − C(n−c, k) / C(n, k)。当 k = 1 时，pass@1 就是成功尝试的比例。

课程还讨论了 temperature 对 pass@k 的影响。温度为 0 时，对给定输入总是得到相同输出，所以无论 k 多大，pass@k 都是同一个数字。提高温度可以探索其他解，因此随着温度上升，pass@k 在生成更多尝试时往往上升；但温度太高，答案可能太有创意或离合理答案太远。课程提到，从 T = 0 提高到 T = 0.8 时曲线变好，但从 T = 1 往上曲线反而变差。这个例子说明，**评估指标不是孤立的数字，它和推理时的采样策略紧密相关。**

课程还区分了 pass@k 和 consensus@k。pass@k 适用于你能检查答案是否通过的场景，比如编程中有测试用例。但在数学推理中，推理时你并不确切知道答案是什么，这时 pass@k 没那么相关。consensus@k 则是对 k 次尝试的答案做多数投票，输出出现次数最多的答案。

## 四、自然语言任务与 LLM as a judge

代码和数学之后，课程转向更偏自然语言的任务。这里课程快速过了一些传统指标：BLEU 全称 bilingual evaluation under study，把 LLM 输出与参考比较，可看作精确率的等价物，比较生成译文中的 n-gram 与参考，并有 brevity penalty 惩罚过短译文；METEOR 全称 metric for evaluation of translation with explicit ordering，同时有精确率和召回率相关指标，并通过 chunk 数量惩罚词序问题。课程还提到 ROUGE 等。

但这些指标的问题在于，它们没有充分考虑同一件事的不同说法。课程举例：“A plush teddy bear can comfort a child during bedtime”与“soft stuffed bears often help kids feel safe as they fall asleep”相对相似，但你可以用完全不同的文体方式说出同一件事，而且仍然有效。其次，这些指标与人类判断的相关性有限，而且仍然需要人类评分；如果没有参考译文，就无法判断翻译性能。

于是课程回到学生提出的 reward model 线索，并引出 **LLM as a judge（LAAJ）**：既然 LLM 擅长理解文本和代码，为什么不用它们来评判输出质量？课程用一个例子说明：给模型回复“they are comforting because they are soft and loyal companion”针对提示“why are teddy bears conforming?”就 relevance 打分，把提示、回复、评估标准一起传入模型，要求它判断相关或不相关，给出二值分数，并说明理由。

LAAJ 的好处有三点。第一，利用模型的理解能力，不需要参考答案；第二，模型能理解语言变体，不会因为答案换了一种说法就拒绝；第三，它对不同任务灵活，只需改变准则，而且能输出理由，便于调试。

课程把 judge 的 prompt 分成两部分：上半部分告诉它评估什么、手头有哪些信息；下半部分告诉它返回什么。实践中不应完全手写 prompt，而应先看希望 judge 覆盖哪些输出，做小规模评分练习，比如拿 10 个问答对看答案是否相关，用观察到的模式充实 prompt，然后建立 baseline，用精确率和召回率等指标量化 judge 做得如何，设定目标，再对 prompt 做“爬山”（hill climb）：评估初始 prompt，查看 judge 没捕捉到目标的案例，调查胜败模式，尝试新 prompt，再跑评估，反复迭代。课程还指出，这正是一个适合让 coding agents 跑循环优化的案例。

下半部分涉及输出格式。课程提醒，LLM 是非确定性的，理论上可以输出任何 token，所以不能保证它按指定格式输出。这里课程联系到之前讲过的 **guided decoding / constrained decoding**：只约束模型从某些有效 token 集合中选择，从而保证输出符合结构。这正是各家提供商所说的 **structured outputs** 的底层机制，JSON 是常见格式。在 Python 中可以定义响应类型和字段，比如理由说明和分数，然后以有保证的方式得到响应。

## 五、LAAJ 的偏差与最佳实践

课程接着讨论 LAAJ 的局限，重点是偏差。

第一是 **position bias**：要求 judge 比较回复 A 和回复 B 哪个更好时，模型可能倾向于某个位置，比如总是回答第一个，或总是回答第二个。课程说，不是所有模型都表现得这么强烈，但这种现象可能以不那么严重的形式存在。缓解方法是问两次：A 还是 B 更好？B 还是 A 更好？看答案是否改变。

第二是 **冗长偏差**：响应 A 很短但正确，响应 B 更冗长、深入细节但也许不如 A 有帮助，模型可能偏好冗长的那个。课程认为这要回到训练数据，解决关键是明确说明长度不是判断正确性的标准，也可以在 prompt 里放几个例子。

第三是 **self-enhancement bias**：一个响应来自人类，另一个由同一个被用作 judge 的模型生成，judge 会偏好自己的响应，因为它喜欢自己生成 token 的方式。课程说这也许和人类偏好自己的回答有些相似。关键解决方案是避免使用自己的模型，尤其是较小的模型可能更难区分好坏答案。

课程还提到其他偏差，比如答案引用了看起来像参考文献但完全是编造的东西，模型可能偏好那个答案。总之，意识到偏差并对 judge 的响应保持批判性很重要。

最佳实践部分，课程给出几条：第一，尽量用二值量表而非细粒度量表，因为人类在 1 到 10 的量表上也会不确定 5 还是 6，这种不确定性会转化到模型结果里，而区分 pass / fail 更容易；第二，让模型在输出分数前先写理由（rationale），类似推理问题中先推理再给答案，实践中会带来更好结果；第三，缓解位置、冗长、自我增强等偏差；第四，用人类判断和人类评分校准 LLM judge；第五，注意 LAAJ 也是非确定性的，可以调低 temperature，或让模型生成多个响应后取多数票，做 self-consistency 式设置。

课程最后提到，这个领域发展很快，几周前出现了 **decision models**，不生成文本，而是对某些可能答案输出校准过的概率。课程说可能会在最后一堂课更多讨论，但提醒最佳实践可能会变。

## 六、从模型评估到 agent 评估：ReAct 循环中的失败模式

Shervin 接棒后，把评估机制应用到 agent 上。他先回顾 agent 的核心：配备工具的 agent 有 observe–act–plan 循环，如今 agent 越来越长视野（long horizon），这个循环不只发生一次，而是多次。因此需要拿放大镜看每一步，看可能出什么问题、可以怎么补救。

课程把循环拆成三个阶段。第一阶段是 LLM 预测工具调用，然后是非 LLM 步骤，在沙箱里执行工具调用，再抓取对话历史和工具响应，在循环结束情况下综合成响应。

工具预测阶段的第一种失败模式是：LLM 根本不尝试执行函数，不预测工具调用，直接回应“抱歉，我不知道”。可能原因是工具路由器没有包含相关函数；如果路由器是训练过的模型，可以重新训练，但更常见的是它由提示驱动，所以调整提示并迭代。另一种可能是工具作为输入头部的一部分存在，但模型仍然不使用它，可能因为该工具不是模型能够使用的东西。课程联系到训练方法：2024 年也许做一轮 SFT，但现在通常不会那样做，而是调整提示以倾向于使用工具，除非工具非常基础；在那种情况下，模型不擅长编码本身就是一个问题。

第二种失败模式是幻觉出不存在的工具，比如不调用 find teddy bear，而调用 find bear。沙箱执行不存在的东西会立即遇到错误。课程给出的解决思路包括：模型不够聪明，容易产生幻觉，可以换更好的模型；也可能是上下文管理问题；还可能是工具设计不匹配，比如用户想要一只熊，模型不知道熊应该是泰迪熊，也许每个人都把泰迪熊叫做熊，所以在 API 描述中直接叫它们熊更好。课程强调，更改工具名称或参数名称大有帮助，因为这是模型会看到的东西。另一种情况是函数作为输入存在但未被选中，指令没有包含只针对熊而非泰迪熊的调用，这时可以“爬山”改进指令。

第三种失败模式是多个工具存在时，模型没有选择你希望它选择的那个。比如问“在我附近找一只熊”，它却发送消息询问其他系统或人是否有熊。可能原因是用精选的工具污染了上下文，与模型做出预测所需的不匹配；也可能工具在上下文中但模型就是不选它，这时需要更好地解释每个工具的目标，把区分在 API 描述中做得更清晰。

第四种是工具调用正确但参数不对。比如辅助函数携带位置，但辅助函数不在，或信息不在上下文中，模型不想幻觉出假值，只传了占位符。这时需要在模型可能计算的信息类型上下功夫，或教模型使用计算该参数所需的另一个函数。

后端计算阶段，常见问题是参数正确但后端不返回结果而返回错误，比如 Python 中的 value error。课程提到，消费级产品中有时 LLM 会编出理由为没有响应辩解，说“内部问题”之类。课程认为，工具设计者不应每天输出错误，应该始终输出一个有效值来告知工具结果，而不是让循环报错；最好的解决方案是直接修复导致错误的实现。

另一种情况是工具执行了但没有返回任何答案。课程说这常常伴随幻觉回复，比如要求执行打开灯的动作，工具没有反馈发生了什么，LLM 可能说“也许灯被打开了”，但这是凭空冒出来的。解决方式类似：确保始终输出一些模型可以解释的内容。

最终回复生成阶段，可能拿到包含泰迪熊特征的 JSON，却没有把泰迪熊呈现出来，反而说没找到任何熊。可能原因是模型无法识别输出形状携带感兴趣信息，这时可能模型不够强；但更常见的是工具输出根本不相关，输出一大堆信息。课程说，如果往上下文窗口塞进几万 token 的垃圾，再让模型找出正确信息，这是非常困难的上下文工程问题，需要更好地裁剪输出。另一个问题是输出格式不够易于理解，可能需要使用结构良好、自描述的输出，让工具输出对需要合成回复的 LLM 有意义。

Shervin 总结说，之所以要列这些症状，是因为调试 agent 时看到错误答案，你会倾向于回到工具设计和工具生成结果的过程，看处于哪种情况；如果有该往哪里看的直觉，就能想出可推广到整类问题的修复方案。课程还提到一个持续评估 agent 的概念：专家和时间跨度（expert and time horizon），y 轴表示专家执行给定任务所需的时间，值得追踪的指标是 agent 能够至少 50% 时间里执行给定动作的那个点；随着能力相对于时间绘制，可以看到更长跨度能力的涌现，以及它们能多好地抵御 ReAct 循环并从错误中恢复。

## 七、行业基准、bench maxing 与评估驱动的工作方式

课程最后进入更宏观的评估生态。Shervin 说，Artificial Analysis 这类指数聚合器已经成为了解模型有多好、值不值得花时间和金钱的黄金标准。当前第五版指数聚焦四个领域：一般事实、知识工作、编程、科学。当前版本中四个字段权重相等，各占 25%，每个字段由多个基准测试组成，汇总成总体指数数值。

一般事实类基准覆盖商业、健康、法律、软件工程等广泛领域，目标是预测应该被知晓的事实，不能上网，信息应编码在模型里，并对糟糕回答进行惩罚。评估方式用 LLM as a judge，结构如 Afshin 所述：呈现任务、选项、问题和目标，留占位符让 LLM 填入预测答案，再问 judge 这个答案好不好。课程举软件工程中 checked addition 需要特定 import 的例子，根据是否输出确切字符串给好或坏评分。

知识工作类被课程称为非常难量化的领域，因为典型办公室工作产出的不是定义明确的输出，而是一整套工件，然后被别人使用。这里覆盖数据科学、产品管理和咨询等，有跨越数周工作的场景，有 Slack 消息、报告、邮件等信息，不能上网，在给定轮次预算内产出所要求的工件。评分时把答案投射到可测量维度，再汇总。课程举评分标准例子：如果属性与黄金标准集一致就通过，否则不通过；比如构建 Excel 模型，黄金答案可以是找到预期的正确的 x、y、z。课程还提到 presentation 这种方面至关重要，但很难用平实语言定义什么是好的演示，所以基准使用 pairwise comparisons 作为代理，给出大致要点，展示两份提交，问哪份更好。

编程类有 terminal bench，测试基于终端的任务被完成。给 agent 合适运行环境、工具、甚至上网权限和足够时间，最后用一堆隐藏测试验证 agent 的工作。因此这里可以负担启发式方法，不涉及 LLM as a judge，而是确定性检查。课程提到，是否为了模型训练保留这些基准？应该，但某些公开基准没有强有力方法强制相反情况，这是该领域非常重要的一点。科学领域框架类似 terminal bench，只是超出普通编程，覆盖多个科学领域；课程提到今天用来比较 LLM 的 terminal bench 科学基准测试由一位还在读书的 ICME 学生设计。比如天文学中有描述运动的向量，问位置和速度难题，有黄金文件，比较 agent 生成文件与黄金文件，验证差值范数是否低于阈值。

课程接着讨论 **bench maxing**。作为用户，有时基准数字很棒，但不一定传达屏幕上那种出色表现，用户反而觉得模型还不够好。bench maxing 是被广泛使用的贬义词，指模型可能过于关注数字而非能力。课程举了一个比较：几个月前某基准排名中，第一个模型结果可能不是一个很受欢迎的产品，很多人说“我不理解这个模型，它不适合我”。课程不是说 bench maxing 一定是原因，但这是一个有趣案例，让人回头看如何定义基准、是否与用户感受对齐。

如何确保基准没有被用于训练？课程说很多时候做不到；如果基准定义公开，就可以假设它可能被用于训练。terminal bench 等基准非常难以定义，需要开源社区才能得到稳健任务，不是某个装备精良的公司就能做到并保持私有，所以它们都是公开的，可能被用于模型训练，这就可能导致基准高分但领域表现不佳。课程提到 Max Bench 这个工作：拿开源基准 Deep Suite，只把指令改一点点，比如不要求以 PT 格式给出日期，而要求以 Zulu 格式给出日期，也就是 GMT 伦敦时间；或把命名大小写方案改成全小写。结果所有模型在 Deep Suite 上的分数在期望轻微变化后下降，作者推断这种差异可归因于基准测试问题，并说重新计算排名后排名变化很大，有些原本排名最好的模型掉到排名底部。课程还讲了一个个人经历：当助教时，一份完美提交回答了甚至没有被问到的问题，类比模型试图满足甚至没有被要求的约束；课程说那个学生比所有人都更早领悟了 bench maxing 的精髓。

对抗 bench maxing 的办法，课程提到几种：不公开基准，把测试保持私有，代表模型提供方运行基准，不让人们自助使用；私有基准通常协商 ZDR（zero data retention）政策以公平竞争；业界提出能很好代表其用例的任务，但出于担心被基准测试、从而不再能代表在意的任务的恐惧，不分享基准内容；也可以反过来，把对业务重要的东西表述为任务，发布给更广泛的基准社区，课程举 Harvey 在知识工作领域的例子。课程还提到 Artificial Analysis 指数会随时间变化，聚合并重新加权基准，这是一条双向街：LLM 提供方试图拟合用户在意的东西，聚合器社区试图更好地重新加权，使结果能转化为最终用户感受。

课程还讨论 Pareto frontier：在质量–成本图上，想看质量最高但成本最低的模型画出的曲线；固定 X 总能在给定代价下找到最优 Y，固定质量 Y 也能找到达到该质量的最低代价，这条最优边界就是 Pareto frontier。课程说成本轴也可以是别的东西，比如时间。

课程还提醒基准定义本身的质量问题，提到 bench guard 这类工作作用于基准定义本身，查找分类体系中的问题，也可以对基准本身和执行日志运行检查。课程说一旦定义基准，很多基准会在确定性时间内从零冲到 100 分，只要知道想要什么，一切都是可解的，而确保想要的东西合理很关键。课程还提到 agent 可能走捷径，比如 terminal bench 中要求克隆仓库然后复用，仓库可能包含含有正在寻找的修复的提交，模型会试图利用；有时会用互联网访问搜索解决方案，而你不希望这发生，因此需要设置防护措施，且防护清单并不详尽。课程提到今年早些时候 Hugging Face 被黑事件发生在一个评估设置期间，agent 不是去评估东西，而是去做了别的事；课程说想确保系统里没有漏洞让附带任务发生。课程说作弊有时是了解模型有多聪明的代理指标，非官方基准 felony bench 把这些能力转化了过来，尽管人们不明说，但在这个基准上拿高分有点炫耀意味。

课程引用古德哈特定律（Goodhart's Law）：当一个度量变成目标时，它就不再是一个好的度量，因为人们会试图达成摆在模型面前的任何目标。课程举编码领域代码行数的例子：代码行数可以是生产力的代理，但一旦人们知道这是代理，就会针对代码行数优化，而不是针对实际内容。课程说这就是为什么基准不是全部。

课程还介绍 Text Arena 这类平台：用户提问，平台给出两个答案，问用户哪个最好，基于这些和课程跳过的数学，能在模型之间排出受用户喜欢的排名。但课程指出它不是万灵药：很贵，因为让用户做任务需要为他们工作，不能向他们收费，只能从提供商汇集额度；很慢，因为需要足够多的成对观测才能得出稳定指标；而且主观，用户可能不知道什么是对或错，可能给出与真实答案不一致的偏好。

最后，课程给出评估驱动的心态：不是自己构建 agent，而是构建围绕它的评估，构建恰好是你想要的东西，然后用 Afshin 提到的方法对 prompt 爬山、对工具设计爬山，找到最符合需求的 agent。课程提两点：第一，把关心的东西分成两类，因为不能一次优化所有东西，也不会一次关心所有东西，要思考什么是关键的、什么不是；第二，LLM as judge 或 agent judge 这些工具很花哨，但需要调、很难调，而编码和数学中的启发式情形很棒，因为确切知道什么是对什么是错，可以把全部注意力集中在标签本身，而不是区分标签的过程，所以强烈建议尽量采用启发式方法。课程最后说，如果清楚自己想要什么，几乎可以在任何事情上做 hill climb；并以一个 AGI 基准为例，说几年前分数几乎为零，所有人都说太难，但如果懂得如何写出漂亮的问题陈述，如今可以达到任何想要的目标。

## 结语：评估是一条从“可验证”走向“可校准”的路径

把两段讲授放在一起看，本讲的核心论证非常清晰。LLM 评估之所以困难，是因为“好”本身是多维、开放式、依赖上下文的；人类评分能处理细微差别，但受主观一致性和可扩展性限制；基于规则的指标在代码和数学这类可验证任务上非常有效，pass@k 和 consensus@k 就是典型代表；自然语言任务需要 LLM as a judge，但必须警惕 position bias、冗长偏差、self-enhancement bias，并用二值量表、先写理由、人类校准、降低随机性等最佳实践来约束；到了 agent 系统，评估变成对 ReAct 循环各阶段的诊断，工具预测、后端计算、最终回复生成都可能失败，需要培养从症状到补救措施的直觉；到了行业层面，benchmark、指数、Pareto frontier、Text Arena 各有用途，但都面临 bench maxing、污染、主观性和 Goodhart's Law 的挑战。

在本课程的学习路径中，这一讲处在从“理解模型和 agent 机制”走向“可靠地构建和选择模型”的转折点。前几讲讲了 LLM 的基本设定、训练方法、agent 的 ReAct 循环、guided decoding 等机制；这一讲则告诉我们，所有这些机制最终都要接受评估的检验。没有评估，就无法知道该改进什么，也无法在众多模型中做出选择。而评估本身不是寻找一个万能数字，而是根据任务的可验证程度，选择合适的方法组合，并持续校准。
