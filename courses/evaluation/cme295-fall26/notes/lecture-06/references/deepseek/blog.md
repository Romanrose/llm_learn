# 从 RAG 到 Harness：AI Agents 如何补齐 LLM 的两块短板

## 导语

在 CME 295 的前五讲里，我们反复拆解了 Transformer 和 LLM 的内部机制：tokenization、注意力、预训练、指令微调、推理模型。到了第六讲，视角发生了一次明显的翻转——我们不再问“模型内部如何运作”，而是问“模型被放进一个什么样的系统里，才能真正完成任务”。这一讲的主题是 AI Agents（智能体），而它的叙事主线非常清晰：先指出 vanilla LLM 的两个硬性局限，再用 RAG 解决“知识”问题，用 tool calling 解决“行动”问题，最后把两者装进 harness，形成 ReAct 循环，并以 coding agent 作为综合案例收尾。

理解这条主线，也就理解了本讲在整门课中的位置：前面几讲给了你“引擎”，这一讲开始搭“车”。

## 一、两个局限：知识截止与无法行动

讲者用编程工作流的演变作为引子。几年前人们还主要手写代码；ChatGPT 出现后，大家开始用它辅助生成片段；到 2024 年，IDE 的自动补全越来越好，依托的正是 LLM 擅长的 next token prediction；再到今天，coding agent 已经能端到端地写代码、写测试、跑测试，甚至部署上线。从“你写 prompt 拿代码”到“你描述任务、工具替你完成”，中间发生的很多事情，就是这一讲要填补的差值。

第一个局限是**知识截止**。LLM 只知道训练数据里的事实。课程提到，模型卡上会标注 knowledge cut-off date，例如示例中 GPT-6 Astra 的截止日期是 2026 年 4 月 30 日。这意味着如果你问它本周中期选举的结果，它不会知道；如果你问它你私有代码库的问题，它也无从回答，因为它没见过你的代码。

第二个局限是**只能回答、不能执行动作**。你让它订一个 17 英寸的泰迪熊，它不知道该怎么办——它只是一个接收 prompt、然后回应 prompt 的模型。

这两个局限对应了本讲的两大技术板块：RAG 与 tools。而把它们串起来的，是 harness 这个概念。

## 二、RAG：为什么不能“把所有东西都塞进上下文”

面对知识截止，最直觉的方案是把训练结束之后发生的所有事情都塞进 prompt。课程用三层约束说明这行不通。

第一层是**上下文窗口有限**。示例中 GPT-6 Astra 的上下文约为 100 万 token，听起来很多，但远不足以容纳所有数据。

第二层是**输入变长后性能下降**。课程引用了 needle in a haystack（大海捞针）测试：横轴是输入规模，纵轴是检索特定事实的能力，颜色表示表现。在较短输入下模型表现相当好；但随着输入变长，模型在检索位于文档靠前位置的事实时会明显吃力。也就是说，即使窗口装得下，模型也未必用得好。

第三层是**成本**。定价按 token 计费，输入 token 尤其如此；而且课程特别提醒，推理 token 并不总是展示给你看，但同样计费。检索到的信息也算进成本。

于是就有了 RAG（Retrieval Augmented Generation，检索增强生成）。它的三步正好对应缩写：**retrieve**——把查询与知识库文档比较，检索相关文档；**augment**——用检索结果增强 prompt；**generate**——基于增强后的 prompt 生成回答。课程用中期选举举例：把与选举结果相关的信息放进 prompt，再问模型结果，模型就能答。

### 建库：chunk、embedding 与超参数

要让检索奏效，第一步是建知识库：收集文档，切分成 chunk，再用 embedding vector 表示每个 chunk。这里有三个超参数：

- **嵌入维度**：文档越微妙难懂，越倾向用更大的维度，通常是数千量级。
- **chunk size**：不希望太大，否则输入过长，通常在数百 token 量级。
- **overlap**：chunk 之间通常保留约 10% 的重叠。原因是朴素切分可能把信息切断，或正好切在句子中间，导致脱离前文就看不懂。

### 两阶段检索：召回与重排

检索通常是两步。第一步是**候选检索**，目标是最大化 recall（召回率）。做法是把查询和每个 chunk 的嵌入做相似度计算，取分数最高的一批候选。这里用的是 bi-encoder 设定：查询和 chunk 分别送入编码器（课程呼应第二讲的 encoder-only 模型），chunk 嵌入可以预先算好，推理时只需算查询嵌入，再用 approximate nearest neighbor 算法做相似度操作，因此相对便宜。课程强调，chunk 是固定的，随请求变化的只有查询；知识库可以随新文档增长，但必须用同一个模型，因为相似度比较要在同一标准下才有意义。

第二步是**ranking / re-ranking**。此时候选集已经从百万级缩到约一百，可以负担更贵的计算：不再让查询和文档各自过编码器，而是把它们作为一个序列送入**单一共享编码器**，让 token 之间通过自注意力相互交互。课程用了一个很能说明问题的例子：查询“带红围巾和蓝袜子的泰迪熊”与“带蓝围巾和红袜子的泰迪熊”，在 bi-encoder 下可能嵌入得很接近；但在单一编码器里，模型可以建模查询 token 与文档 token 之间的关系，从而做出更精细的判断。架构上通常用 encoder-only transformer，取 class token 的编码嵌入投影到相关性维度，这与第二讲的 BERT 非常相似。训练需要相关与不相关的标注数据。

### 语义相似度不够：BM25 与混合检索

课程用“Cuddly 在哪里？”这个贯穿全讲的泰迪熊例子说明纯语义检索的失败模式。知识库里有“Huggy 喜欢在楼下工作”“巴黎位于哪里”“他当时心情很黏人”“Cuddly 大多数日子都在书堆中度过”等文档。纯语义相似度可能把前两个检索出来，但答案并不在里面——因为 cuddly 与 Huggy 语义接近，而“巴黎位于哪里”也是个问题句式。

这时需要**BM25**：通过比较查询和文档中出现的精确词语来衡量接近程度。基于 BM25，会命中包含“Cuddly”字面的那两个 chunk。但纯关键词匹配同样不够，因为自然语言可以用不同说法表达同一件事。实践中的做法是**混合检索**：把语义相似度给出的排名和关键词搜索给出的排名结合起来，得到最终混合排名，多数情况下优于单独使用任一种。

课程还提到两类改进。其一是**假设文档嵌入**（hypothetical document embedding）：从 prompt 生成一个假文档，再基于假文档与 chunk 做相似度运算，因为文档与文档之间更相似，编码器更容易判断相关性。其二是**查询重写**：当一个查询包含多个问题时，单一嵌入难以捕捉，可以把 prompt 重写成不同问题，分别检索。

另一个改进针对 chunk 本身：即使有重叠，chunk 也可能脱离上下文就没有意义。做法是让 LLM 基于整个文档为每个 chunk 补充上下文，使其自包含。这里可以结合上一讲关于 prompt caching 的技巧：把固定不变的整体文档放在 prompt 顶部，只对特定 chunk 提问，从而利用缓存定价。课程给出的量级是：缓存输入比常规输入便宜约一个数量级。

### 评估：NDCG、MRR、precision 与 recall

排序做完，自然要问“做得有多好”。课程介绍了几个指标：

- **NDCG**（normalized discounted cumulative gain）：在 top K 上计算，核心思想是让更相关的结果排在更高位置；用完美排序的 DCG 做归一化，使指标落在 0 到 1 之间，越接近 1 越好。
- **reciprocal rank**：第一个相关 chunk 排名的倒数。
- **recall@K**：在所有相关文档中，top K 实际召回了多少。
- **precision@K**：top K 中实际相关的比例。

评估需要带标注的数据集：对某个 query，哪些文档相关、哪些不相关，然后拿预测的 top K 与真实相关集比较。

### 一个重要的领域差异：代码检索靠 grep

课程专门指出，前述语义相似度与关键词搜索主要适用于自然语言问题。编程场景不同：你关心的往往是特定函数，检索语义相似的代码意义不大，精确匹配才有意义。所以 coding agent 普遍使用 **grep**（global regular expression print），按词项在代码库中搜索所有出现位置。这一点在后面 coding agent 部分会再次被强调。

## 三、Tools：让模型“预测一个动作”

RAG 解决了静态知识，但“找到我附近的泰迪熊”这类需求它无能为力：数据可能是过时的、静态的，你需要实时后端查询，还需要知道用户位置。这就引出了 tools。

工具调用的机制是一个**三阶段过程**：第一阶段，LLM 不直接给回答，而是预测该用哪个工具、传什么参数（例如先调用定位函数拿到 GPS 坐标）；第二阶段，实际执行这个动作，向后端查询坐标周围有什么；第三阶段，把后端结果喂回 LLM，让它转成自然语言回复给用户。课程特别说明，第一阶段之后必须等待动作发生；延迟因工具而异，GPS 几乎瞬时，网络搜索会让用户感知到，但通常不构成主导延迟。

实现上，工具通常用 Python 表达：有一个同名函数实现实际操作，但**只有 API 描述、输入和输出会展示给 LLM**，函数内部的代码逻辑不会展示。因此输入输出必须**可解释**：输入要有清晰的参数名和类型（如 location），输出要用结构化类型（如 enum、带 name、distance、mood 的类），这样模型才能把结果重新解释成自然语言。

课程列举了工具的类型：web search（UI 上“正在搜索网页”的提示，本质是让你消化延迟）、天气与股票等快捷方式、代码库查询、计算类工具（next token prediction 不擅长算术，把乘法交给确定性的计算器更高效）、代码执行（画图、生成图表），以及发邮件这类动作。

关于“工具集是否在训练时就固定”，课程给出了一个有时间维度的回答：一两年前答案是肯定的，做法是把任务分解成两个阶段——预测工具调用及参数、把后端结果转回自然语言——作为 SFT 的一部分做下一 token 预测。但如今不再如此：训练教模型广义的计算与 Python 使用，但不把具体工具固化进权重，而是改用 prompting，靠函数 API 附带的文档字符串引导。而且随着模型原生编码能力增强，这种需求正在减少。课程还讨论了一个实践技巧：工具描述本身可以让另一个模型来写，用一组查询和标签做目标，让模型迭代描述，直到生成的答案逼近预期标签；标签本身往往最难获得，需要专家投入。

### 工具选择的冲突与路由

当工具从一个变成“一个宇宙”，问题就出现了：**冲突**。课程用“给我看看我的泰迪熊的早晨作息”举例：GDrive 工具和 get doc 工具范围重叠，但输出相同，这是**良性冲突**。而“你能帮我找到我的泰迪熊吗”则可能被解读为在电脑里找泰迪熊图片，也可能被解读为在物理世界找泰迪熊——这就改变了查询的解读。

有人提出这或许是用户表述不清的问题。课程的反驳是：当存在用户不关心的工具可能抢走查询时，把责任推给用户并不公平；而且控制工具空间的人和提供工具服务的人往往是不同实体。至于用 temperature 为零强制确定性，课程认为这会降低质量，并可能让指定不足的查询永远得到错误答案，因此不是可取的方向。

缓解手段是**工具选择**：不在整个工具宇宙上操作，而是取一个子集。判断依据包括对话历史（在谈泰迪熊的物理存在，则 find teddy bear 更合适）、记忆（过去类似查询的模式）、用户画像（财务人员触发财务工具，工程师触发另一套）、以及用户对工具的激活/停用偏好。路由模型通常是一个**超轻量 LLM**，因为任务不难，需要低延迟。工具选择是两步：先基于这些参数选出子集，再把子集放进上下文让 LLM 操作。

除了冲突，工具太多的另一个问题是课程称为 **context rod** 的现象：上下文越大，工具调用能力越下降。所以服务提供商非常注意上下文里放什么，最小化冗余是其一。

### MCP：标准化工具接入

为了让工具一次实现、处处可用，出现了标准化协议 **MCP**。它有两个概念：**MCP server** 承载工具实现与业务逻辑，**MCP client** 查询服务器并使用工具；用户不直接看到 server，而是通过 client 交互。MCP 标准化了三类东西：**tools**（工具参数与输出的模板）、**prompts**（指向特定工作流的句柄与快捷方式）、**resources**（应用层可能想喂给工具的资源）。课程用一只热爱诗歌的泰迪熊举例：tools 可以是“找到某本诗集”和“推荐书籍”，prompts 可以是“找特定书名”和“按品味推荐”，resources 可以是泰迪熊现有的个人藏书。

### 提示词缓存：让“写长指令”变得便宜

把大量工具使用说明塞进 prompt 会不会很贵？答案是 **prompt caching**。课程展示了不同提供商相对常规输入 token 的成本节省，幅度约在 O(10) 量级；还出现了缓存保留时长的选项，如五分钟写入、一小时写入——首次发出 prompt 时被缓存，生存时间（time to live）内重复请求可复用。高流量、持续复用的工作流适合选五分钟，付一次存储费后反复命中。

课程随后做了一个练习，讨论 prompt 的消息顺序：user prompt、tool definitions、user context（提供商推断、你看不到的信息，如时间日期、由 IP 给出的粗略位置，帮助模型不调用工具就知道“今天几号”）。结论是**固定部分必须放在顶部**才能利用缓存；把固定的指令集放前面，变化的查询放后面，跨请求相同的部分就能命中缓存。修改工具描述会让缓存失效，但工具通常最多每天改一次，代价可以接受。

## 四、Harness 与 ReAct：把工具装进循环

课程给出了 **harness** 的直觉定义：模型是引擎，harness 是围绕它的一切——工具、动作的排序方式、压缩策略、记忆、任何与 prompting 相关的东西。两者是互补的：弱模型配强 harness，或强模型配弱 harness，都得不到最好结果；要一辆能上路的车，两者都需要。

在此之上，课程介绍了 2023 年被形式化的 **ReAct**（reason + act）范式：输入之后，模型先观察当前状态，再规划要执行的动作，然后在 act 步骤执行，再观察动作导致的状态，如此循环，直到对观察到的状态满意，才把输出返回用户。

课程用“泰迪熊冷了”举例：观察是泰迪熊冷、与温度有关；规划是先确定当前温度；act 是调用评估温度的函数并读回结果；发现低于舒适温度后，规划升温并调用升温工具；验证温度合理后结束。这是一个恒温器式的智能体。课程指出，这些观察、规划、执行步骤很大程度上是通过 SFT 学到的，会成为 LLM 的原生能力；而每一步执行工具后回顾发生了什么，本身就是必需的推理，但它不等同于推理模型那层额外的推理——即使非推理模型也会经历这三步。

智能体之间也有协议，如 **A2A**，定义给定智能体的技能集以及其它智能体可交互的函数。

## 五、压缩与记忆：上下文总会满

工具调用会产生大量只在下一轮需要的输出，上下文窗口终究会满。课程给出三种**压缩策略**：其一，删除不再需要的信息；其二，基于时间的滑动窗口，假设相关性随对话时间距离衰减；其三，最流行的做法——把迄今的一切结构化成预定义桶，用摘要过程继续对话，课程举了 coding agent **Pi** 的例子，它定义了“当前进度”“剩余工作”等桶。

压缩发生在对话层面，若希望信息持久，则需要**记忆**。短期记忆只是上下文窗口的花哨说法；长期记忆则是你明确告诉 LLM“记住这个”的信息，可以基于过去对话做 RAG 检索，也可以用结构化摘要，或让记忆工具把信息存到始终作为上下文一部分的地方。关于推理轨迹是否该在压缩后保留，课程的回答是：取决于它是否对每个关心的维度都有贡献，但保留内容主体应是关于用户兴趣的高层面视图，而非原始推理轨迹。

## 六、Coding agent：把所有东西合起来

Coding agent 的核心正是 ReAct 的智能体循环：一连串工具调用，然后观察结果。它的几个特点值得单独说。

第一，**执行环境**是 coding agent 非常典型的特征。第二，**安全审批**：早期每个动作都要人工点“允许/不允许”，如今改为用更轻量的模型独立判断所提议动作的安全性，即 **auto approval**。第三，**大量忽略传统 RAG**：如 Afshin 开头所述，grep 在预测用户想要什么方面极其有效，智能体会猜测你想要的内容变体并用 grep 搜索，它超级快，非常擅长为推理阶段提供输入。第四，**agents.md**：一种标准化方式，把每次会话都希望智能体知道的规则集中放置，持久化你的偏好。第五，**skills**：把重复工作流写成配方，包含提示词、可能的工具调用或脚本；通常不是手写，而是端到端做一遍后让 agent 重新组织成技能。课程还推荐 **Pi**，其 harness 非常极简，围绕每个步骤的提示词被压到最低，能看到模型最原始的表现，也常被用于在单一 harness 上比较模型。

课程还提到 **computer use**：让智能体控制计算机，目前超级低效，因为它对屏幕截图并预测下一个动作，用起来可能令人沮丧，后续讲座会讨论可能的下一步。最后是**多智能体**：**sub agents** 被启动来处理不需要大量推理、可委派的任务，代价是每个子智能体都要有自己的上下文，所以极简 harness 如 Pi 宣称不支持或仅最低限度支持；**agent swarms** 则是多个智能体为同一目标协作、共享进展，课程既提到近期一些数学进展，也提醒把大量权力交给外部智能体的脆弱性，并推荐了模型评估与威胁研究组的读物。

## 结语

回看整讲，结构其实非常工整：两个局限（知识截止、无法行动）催生两大技术（RAG、tools），两大技术被装进一个概念框架（harness + ReAct），再由一个综合案例（coding agent）验证。对学习者而言，这一讲的价值在于它把前几讲的模型内部知识转化成了系统设计知识：你知道了 bi-encoder 为什么便宜、cross-encoder 为什么更精细，知道了 chunk size 与 overlap 如何权衡，知道了 prompt caching 如何让长指令变得经济，也知道了工具选择的冲突为何不能简单归咎于用户。这些判断力，正是从“会用模型”走向“会搭系统”的分水岭。
