## 一、学习目标

学完本讲，应当能够：

1. 说清楚 vanilla LLM 的两个核心局限——知识被训练数据截止日期限制、只能“回答”不能“执行动作”——以及它们分别如何引出 RAG 与 tools。
2. 完整复述 RAG 的 retrieve / augment / generate 三步，并解释为什么第一步检索最关键。
3. 区分 candidate retrieval（bi-encoder、最大化 recall）与 re-ranking（cross-encoder、建模 query–chunk token 交互），说明两者为何在成本与表达力上互补。
4. 了解检索评估的基本指标（NDCG@K、reciprocal rank、precision/recall@K）及其直觉。
5. 解释 tool call 的三阶段流程（预测动作 → 执行 → 把结果读回模型），以及工具的输入/输出为何必须可解释。
6. 理解 tool selection、harness、ReAct、压缩策略、短期/长期记忆、coding agent 与子智能体等概念之间的关系。
7. 识别常见错误直觉：把所有东西塞进上下文、以为语义检索万能、以为工具越多越好。

## 二、课程主线

本讲有一条清晰的因果链：

**LLM 的局限 → 不能靠“全塞进 prompt”解决 → RAG（解决知识问题）→ tools（解决动作问题）→ tool selection 与 harness（解决规模与编排问题）→ agent 范式（ReAct、记忆、压缩）→ coding agents 与多智能体**

课程用一个贯穿性的编程演进叙事开场：从手写代码，到 ChatGPT 辅助写代码，到 IDE 自动补全（利用 next token prediction 的强项），再到今天能端到端承担任务的 coding agent。课程解释：这一讲关注的正是“从 ChatGPT 到 coding agent”之间发生的“差值”。

## 三、核心概念

### 1. 两个动机性局限

**局限一：知识截止（knowledge cut-off date）。** LLM 只知道训练数据中的事实；问它关于私有代码库或截止日期之后的事件，它无从知晓。模型卡上通常会标注知识截止日期。

**局限二：只能回答，不能执行动作。** 让 LLM“订一个泰迪熊”，它无法执行，因为它只是对 prompt 作出回应。

### 2. 为什么不能“把所有信息塞进上下文”

课程给出三层递进的反驳（课程按“假设前一个不是问题”的方式层层推进）：

1. **上下文窗口有限**：即使窗口很大，也不足以容纳训练结束以来的全部信息。
2. **长上下文性能下降**：needle-in-a-haystack 测试表明，输入越长，模型检索放在文档靠前位置的事实越困难。课程强调：即使模型“装得下”，也不代表“用得好”。
3. **成本**：按输入 token 计费；检索到的 token 也算钱；推理 token 同样是隐藏成本。

结论：应当只放入与任务相关的信息——这就是 RAG 的动机。

### 3. RAG：Retrieval Augmented Generation

三步：

- **Retrieve**：将 query 与知识库文档比较，检索相关文档。
- **Augment**：把检索到的片段放进 prompt。
- **Generate**：用增强后的 prompt 生成回答。

课程强调第一步（检索）是最关键的，因此重点展开。一个关键复杂性：自然语言可以用不同说法表达同一件事，纯词面精确匹配不够。

**知识库构建流程**：收集文档 → 切分为 chunk → 用 embedding 表示每个 chunk。涉及三个超参数：

- **embedding 维度**：文档越微妙/难理解，越倾向更大维度；课程给出“数千量级”的定性描述。
- **chunk size**：不能太大（避免输入膨胀），课程给出“数百 token 量级”。
- **overlap**：课程提到约 10% 的常见做法。原因有二：朴素切分可能切断信息；切在句子中间时，缺少前文会导致语义不可读。

### 4. 两阶段检索

**第一阶段：candidate retrieval（候选检索）**

- 目标：最大化 **recall**。
- 方法：**bi-encoder** 设定——query 与 chunk 分别编码，chunk 嵌入可预先计算，推理时只算 query 嵌入，再做相似度操作，可用 approximate nearest neighbor 加速。
- 因为要与海量文档比较，使用较便宜的模型。
- 课程解释：知识库可以增补新文档，但必须使用同一嵌入模型，否则相似度不可比。
- 局限示例：query “where is cuddly?” 可能因语义相近而检索到 “Huggy 喜欢在楼下工作” 和 “巴黎位于哪里”，但答案并不在其中。
- 补充手段：**BM25**，基于查询与文档中精确词语出现情况的词面匹配度量。纯 BM25 也会漏掉换一种说法表达的内容。
- 实践结论：**混合检索**——融合语义相似度排名与关键词排名，通常优于单独使用任一方法。

**缓解检索局限的若干方法**（课程列举，非穷尽）：

- **hypothetical document embedding**：由 prompt 生成一个假文档，再用假文档与 chunk 做相似度，缩小“问题”与“句子”之间的形态差异。
- **查询改写**：把包含多个子问题的 query 拆写成多个问题，分别检索。
- **为 chunk 添加上下文**：让 LLM 基于整篇文档为某个 chunk 补充上下文，使其自包含。课程联系上一讲的 **prompt caching**：把固定内容（整篇文档）放在 prompt 顶部以命中缓存价格；并给出 OpenAI 输入价格与缓存输入价格相差约一个数量级的定性说明（“缓存输入便宜约 10 倍”）。

**第二阶段：ranking / re-ranking（重排序）**

- 目标：捕捉更细微的 query–document 信息。
- 可行性：候选集已从海量缩小到约一百个。
- 方法：**cross-encoder**——query 与 chunk 作为序列一起送入单一编码器（用特殊 token 区分），让 token 之间通过双向注意力交互；取 class token（CLS）的编码投影到相关性维度（如 0–1），预测相关/不相关。架构上是 encoder-only transformer，与第二讲的 BERT 非常相似。
- 课程示例：bi-encoder 下 “red scarf and blue socks” 与 “blue scarf and red socks” 的嵌入可能相近；cross-encoder 能让相关 token 与文档 token 交互，从而更精细。
- 训练需要相关/不相关 chunk 的标注数据。
- 课程解释：向量数据库服务于第一阶段（存储 chunk 及嵌入）；第二阶段无法预先计算联合嵌入，因此用不上向量数据库。

**检索评估指标**：

- **NDCG@K**（normalized discounted cumulative gain）：只看 top K 预测；相关文档排得越靠前（i 越小），折损累计增益越高；用完美排序的 DCG 归一化，使指标落在 0–1，越接近 1 越好。课程说明 log 内取值不小于 2，故不会为负。
- **Reciprocal rank**：第一个相关 chunk 排名的倒数。
- **Recall@K**：所有相关文档中被 top K 召回的比例。
- **Precision@K**：top K 中实际相关的比例。
- 评估方式：使用带标注（某 query 下哪些文档相关）的数据集，比较预测 top K 与实际相关集合。

**代码场景的特殊性**：课程明确指出，上述语义相似度与关键词搜索主要适用于自然语言问题；coding agent 中多数时候关心精确匹配，实践中大量使用 **grep**（global regular expression print）在代码库中搜索词项出现位置。课程解释：正则表达式在猜测用户想要什么的具体变体方面极其高效，grep 很快，且很适合为推理阶段提供输入。

**K 个 chunk 如何进 prompt**：课程解释这取决于具体设置；常见做法是把 K 个都放进去，也可以设阈值过滤；通常按相关性从高到低排列，但实现方式多样。

### 5. Tools：让模型执行动作

**三阶段流程**：

1. 基于 LLM 预测要执行什么动作（tool call 及其参数）；
2. 实际执行该动作（与 LLM 无关的后端）；
3. 把后端结果喂回 LLM，生成面向用户的最终回答。

课程示例：找附近的泰迪熊 → 先调用定位工具获得坐标 → 再调用后端查询该坐标附近有什么 → 把结果读回。课程解释：执行 tool call 时需要等待；延迟因动作而异（定位几乎瞬时，网络/后端搜索可能被用户感知，但通常不是主导延迟）。

**工具的实现与设计原则**：

- 常见提供商以 Python 函数形式表达工具：函数名、docstring、输入/输出类型会展示给 LLM；函数内部逻辑不展示给 LLM，属于实现细节。
- **输入必须可解释**：参数命名清晰（如 `location`）并标注类型。
- **输出必须可解释**：后端返回结构化结果（如含 name、distance、mood 的类，或用 enum 等结构化类型），以便 LLM 重新转成自然语言。
- 课程列举的工具类别：web search（UI 上“正在搜索网页”等提示用于消化延迟）、天气/股票等快捷工具、代码库查询、计算类工具（next token prediction 不擅长确定性算术，计算器工具更确定、更高效）、代码执行（如生成图表）、发送邮件等动作类工具。

**训练还是提示？** 课程给出历史对比：一两年前的做法是把“预测工具调用及参数”和“把可解释的后端结果转回自然语言”作为 SFT 的下一 token 预测目标固化进权重；如今则更多依赖 **prompting**，因为模型已具备较通用的编码/计算能力。课程解释：只要工具设计良好、输入输出可解释，对详细提示的依赖会下降；编写工具描述本身也可以借助另一个模型迭代，直到模型能产出期望答案（需要带标签的查询集，标签往往最难获得，合成标签常常对不齐）。

**MCP（Model Context Protocol）**：

- 动机：多个 LLM 各有表达方式，没有标准就要为每个 LLM 重复实现；MCP 把工具连接到各支持它的提供商。
- 两个概念：**MCP server**（工具实现与业务逻辑）与 **MCP client**（查询服务器、使用工具；用户直接交互的是 client）。
- 标准化三个类别：**tools**（参数、输出等模板）、**prompts**（涉及工具的工作流句柄/快捷方式）、**resources**（应用层可能想提供给工具的内容）。
- 课程例子：诗歌爱好者泰迪熊——tools（查找给定诗集、推荐书籍）、prompts（找特定书名、按品味推荐）、resources（泰迪熊现有藏书）。
- 课程澄清：MCP 是“如何编写工具”的标准，不解决“描述里该写什么提示”的问题，二者正交。

**prompt caching 与成本**：把固定内容（工具定义、指令等）放在 prompt 顶部以命中缓存；课程给出缓存输入相对常规输入约 O(10) 量级节省的定性说明，并提到缓存有生存时间（如五分钟写入、一小时写入），高流量工作流适合短 TTL 以复用缓存。

**消息顺序练习**：课程给出一种顺序（user prompt、tool definitions、user context 等）并让听众判断。答案是：固定部分不在顶部，无法利用 prompt caching；应把固定部分前置。课程解释：**user context** 不是用户写的，而是提供商推断并注入的（时间、日期、由 IP 得到的粗略位置等），每次查询可能变化；工具定义若经 tool selection 选中，可视为固定子集；缓存键值在工具变更后会失效，但工具描述通常每天最多改一次，代价可接受。

### 6. Tool selection

**问题**：工具宇宙可能很大；工具之间可能存在范围重叠与冲突。课程例子：“show me my teddy bear's morning routine” 可能被 GDrive 类工具或 `get_doc` 拾取——若输出相同，属**良性冲突**；但 “can you help me find my teddy bear?” 既可解读为在电脑里找文件/图片，也可解读为物理位置，此时冲突会改变对查询的解读。

课程讨论了“这是否只是用户没写清楚”的反驳：课程解释——把问题全归咎于用户并不公平；控制工具空间的人和提供工具服务的人常是不同实体；面对不符合用户意图的回答，通常应偏向谨慎。关于“能否强制确定性”：可以设 temperature 为零，但课程解释这通常伴随质量下降，且可能让指定不足的查询永远错下去，因此确定性未必可取。

**缓解：工具选择**——不在整个工具宇宙上操作，而是选一个子集。可用信号包括：

- 对话历史（在谈泰迪熊的物理存在 → find teddy bear 更合适）；
- 记忆（过去类似但更具体的查询模式）；
- 用户画像（企业环境中财务、工程师各有常用工具集）；
- 用户对工具的激活/停用偏好（可提示激活，或尊重设置、偏向谨慎）。

课程解释：路由模型通常是很轻量的 LLM（仍在自然语言空间操作，transformer 风格架构即可），不需要最昂贵的模型，追求低延迟；工具选择是两步过程——先选子集，再把子集放入上下文让 LLM 在其上操作。若两个工具有重叠能力，是否都选中取决于路由提示中的规则。

**另一个限制工具数量的理由**：**context rot**——上下文越大，工具调用能力出现性能下降；服务提供商因此非常注意上下文内容、最小化冗余。

### 7. Harness 与 ReAct

**harness**：课程给出的直觉定义——模型是引擎，harness 是模型之外围绕它的一切：工具、动作如何排序、压缩策略、记忆、prompting 等。课程强调模型与 harness 互补：弱模型配强 harness、或强模型配弱 harness，都得不到最好结果。

**ReAct（reason + act）**：2023 年被形式化的范式，用“观察 → 规划 → 行动 → 再观察”的循环描述模型达成目标的过程，直到系统对观察到的状态满意才向用户输出。

课程例子（恒温器式智能体）：输入是“泰迪熊很冷” → 观察：与温度有关 → 规划：先了解当前温度 → act：调用测温工具并读回 → 发现低于舒适温度 → 规划：升温 → act：调用升温工具 → 验证温度合理 → 结束。课程指出周围许多由工具驱动、带 LLM 的智能体都可类比。

课程问答要点：这些步骤很大程度上通过 SFT 成为模型的原生能力；每次执行工具后都需要一个回顾“发生了什么”的阶段——课程解释这属于“必需的推理”，但不一定等同于推理模型那层额外推理；三个步骤在非推理模型中也会发生。

**A2A**：课程提到智能体之间有互操作协议（如去年发布的 A2A），定义智能体的技能集与其他智能体可交互的函数。

### 8. 压缩策略与记忆

**压缩策略**（课程给出三类）：

1. **删除不再需要的信息**：工具调用产生的中间输出可能只在下一轮需要，可移除；
2. **基于时间的滑动窗口**：信息相关性与“距现在多久”成正比；
3. **结构化摘要（课程称为最流行）**：把迄今做过的事组织进预定义桶（如 current progress、remaining work），用摘要继续对话。课程举 coding agent Pi 为例。

课程问答：推理轨迹通常不会原样保留，留存的是关于用户意图的高层视图。

**记忆**：

- **短期记忆**：课程直言这只是“上下文窗口”的花哨说法；
- **长期记忆**：用户明确要求记住的信息（如头脑风暴出的礼物关键词），可通过基于过去对话的 RAG 检索，或用结构化摘要式方法，或由记忆工具写入某个始终存在于上下文中的位置。

### 9. Coding agents

核心是 reason + act 的智能体循环（agent loop）：一连串 tool call 加观察。课程强调的特点：

- **执行环境**：coding agent 与用户系统交互的典型特征。
- **动作安全与自动审批（auto approval）**：早期每个动作都要人工批准；现在更多用轻量模型查看全部上下文、独立判断所提议动作是否安全。
- **大量使用 grep、基本绕过传统 RAG**：课程解释——用户要的是具体东西，智能体猜测变体并用 grep 搜索极其高效，grep 快且很适合为推理提供输入。
- **agents.md**：标准化方式，把每次会话都希望智能体知道的规则集中放置，持久化并控制偏好。
- **skills**：把重复工作流写成“配方”（提示、可能含工具调用或脚本的文件夹）；课程建议让 coding agent 从端到端完成的工作流中反向整理出 skill。
- **生态举例**：课程推荐 Pi，因其 harness 极简、每步提示保持最少，便于观察模型最原始的表现，也常用于在单一 harness 下比较模型。
- **computer use**：让智能体控制计算机；课程评价当前“超级低效”，因为它对屏幕截图并预测下一动作；课程预告后续讲座可能讨论改进方向。

### 10. 多智能体

- **子智能体（sub-agents）**：把不需要大量推理的任务委派出去；课程解释这相当昂贵（每个子智能体需要自己的上下文和完整响应循环），因此极简 harness（如 Pi）宣称不支持或仅最低限度支持。
- **智能体集群（agent swarms）**：多个智能体围绕目标协作，有通信通道共享进展或分组；课程提到近期一些数学进展，也提醒把大量权力交给外部智能体的脆弱性，并提及 Hugging Face 被攻击事件，推荐模型评估与威胁研究组的读物（课程未给出链接，本笔记不补）。

## 四、关键公式与原则

**NDCG@K（课程给出的直觉形式）**

$$\mathrm{NDCG@K}=\frac{\mathrm{DCG@K}}{\mathrm{IDCG@K}},\qquad \mathrm{DCG@K}=\sum_{i=1}^{K}\frac{\mathrm{rel}_i}{\log_2(i+1)}$$

- $\mathrm{rel}_i$：第 $i$ 位结果的相关性；
- 分母 $\mathrm{IDCG@K}$ 是完美排序下的 DCG，用于把指标归一化到 0–1；
- 课程说明 log 内取值不小于 2，指标非负；越接近 1 排序越好。

**Reciprocal rank**：$\mathrm{RR}=1/r$，$r$ 为第一个相关 chunk 的排名。

**Precision@K / Recall@K**：分别衡量 top K 中相关比例、以及所有相关文档中被 top K 召回的比例。

**课程原则（非数学公式，但可作为设计准则）**：

1. 不要把“装得下”当成“用得好”——长上下文有性能与成本双重代价。
2. 检索阶段最大化 recall、排序阶段追求精细表达力；两阶段用不同成本档位的模型。
3. 语义相似度与词面匹配互补，实践中用混合排名。
4. 工具的输入与输出必须可解释，因为 LLM 要读写它们。
5. 固定内容前置以命中 prompt caching；变化内容后置。
6. 工具不是越多越好：范围冲突与 context rot 都是代价；用 tool selection 缩小工具子集。
7. 模型与 harness 互补，评估时必须说明 harness。
8. 压缩与记忆解决“上下文会满”这一必然问题；结构化摘要比原样保留推理轨迹更常用。

## 五、课程作业关联

逐字稿未直接布置作业或给出作业编号。可据课程内容定位可能的关联点（以下为推断，非课程原话）：

- RAG 部分与第二讲的 encoder-only 模型（BERT 类）直接相连：bi-encoder 与 cross-encoder 的实现、CLS 投影、相关性二分类训练，都是可落地的编码任务。

- prompt caching 与消息顺序的练习（固定部分前置）是成本相关的实现细节，容易被作业中的性能/成本要求考到。

## 六、常见误区

1. **“上下文窗口够大就能解决知识截止。”** 课程用三层论证反驳：窗口有限、长上下文性能下降（needle-in-a-haystack）、成本。
2. **“检索就是语义相似度。”** 课程用 “where is cuddly?” 的例子说明语义检索会返回语义相近但无答案的 chunk；BM25 也有盲区；实践中用混合排名。
3. **“bi-encoder 和 cross-encoder 只是模型大小不同。”** 区别在于是否让 query 与 chunk 的 token 在单一编码器中交互；这决定了表达力，也决定了能否预计算嵌入。
4. **“向量数据库能加速整个检索流程。”** 课程明确：它服务于第一阶段；第二阶段必须计算联合嵌入，无法预先计算。
5. **“工具调用能力必须靠 SFT 固化进权重。”** 课程给出历史对比：早期如此，如今更多靠 prompting，因为模型编码能力变强、工具设计良好时对详细提示的依赖下降。
6. **“工具越多，能力越强。”** 课程指出范围冲突（含良性冲突与改变查询解读的冲突）与 context rot 两类代价，因此需要 tool selection。
7. **“把固定指令放哪里无所谓。”** 课程的消息顺序练习表明：固定部分不前置就无法命中 prompt caching；缓存失效的代价（工具变更）通常可接受，因为工具描述变更频率低。
8. **“记忆就是上下文窗口。”** 课程把短期记忆直接等同于上下文窗口，长期记忆则是需要显式保存/检索的机制（RAG 式或结构化摘要式）。
9. **“推理轨迹应当原样保留。”** 课程问答指出，留存的是用户意图的高层视图，而非推理轨迹本身。
10. **“coding agent 也用传统 RAG 检索代码。”** 课程明确：代码场景更依赖精确匹配（grep），语义相似度没那么有意义。
