# CS147 assignment-09：合并评估发现而不抹平差异

## 学习目标与概念

合并的目标是得到可行动的问题集合。相似措辞可能指向不同问题，不同措辞也可能描述同一个断点。

## 可执行学习流程

1. 先保留每位评估者的原始编号，将问题按任务和界面状态排列。
2. 逐条复现，再按触发条件、缺失反馈与任务影响判断是否重复。
3. 对合并问题保留多个来源；对不同场景或机制的问题分别记录，避免一条宽泛意见吞掉关键细节。
4. 讨论严重程度分歧，把已观察事实与推测风险分开；无法达成一致时保留理由。
5. 形成给被评团队的修复优先级和验证建议，记录原型版本以免修复后报告失去对应关系。

## 交付与自检

建议交付：原始问题到合并问题映射、去重说明、分歧记录、优先级清单与复测建议。

评估合并是否提高可行动性。问题条数减少不是成功标准，来源可追溯和触发条件准确更重要。

## 练习示例

虚构练习：“找不到返回”与“返回后数据丢失”不能合并为“导航差”；前者是发现性问题，后者是状态保持问题，需要不同修复。

## 误区与下一步

误区是按关键词机械去重、用多数票删除少数人发现的问题，以及直接平均严重程度分数而不讨论机制。

完成后保存证据、原型版本与决策理由；下一单元应使用它们，而不是重新从空白开始。此稿未核实全部正式 rubric，也未进行课堂回听。

## 汇总映射表：可直接使用的交付模板

以下模板是自学建议，不是官方提交表格。

- 字段：原始发现ID；合并ID；触发条件；证据差异；优先级讨论；修复验证。
- 虚构填写示例：E1-03与E2-07｜H04｜连续加入同一项｜一人见重复，另一人只见按钮没反馈｜先复现两者因果，不直接平均分｜修复后检查重复与反馈分别消失。

每个字段都应由自己的研究、测试或实现填写。无法确认的地方写“待验证”并说明验证动作，不用虚构用户话语或成功数据补齐。提交前请另一位读者仅凭该记录复现你的过程；需要口头补充才能理解的地方，应回到文档补清楚。
