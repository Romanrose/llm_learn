# CS146S 第 11 讲：智能体代码审查：把意见变成可以验证的问题

> 基于官方讲义的中文学习笔记。仅依据已读取的官方讲义整理，不复述未取得的课堂口头内容。下方问题分析、对照表和练习为本站补充，不是官方作业或逐字稿。

## 课程依据

本讲讨论代码审查的职责、按风险组织审查、不同关注点的审查器、上下文与执行验证，并建议使用历史缺陷和回滚案例评估效果。 [阅读官方讲义](https://docs.google.com/presentation/d/1u8WYtFj0O9yc4H4JX9D4URYKhDzvrAGKLzn38DXSrak/htmlpresent)。

## 从一个问题开始

审查器评论很多，是否说明它更有价值？

下面是本站的评估建议：将已知缺陷的历史修改与正常修改混合，检查审查器能否找到问题、是否误报，以及人工验证每条意见需要多久。多审查器可以覆盖不同视角，但也可能重复报告同一问题。汇总阶段需要保留证据并去重，不能把意见数量直接当作质量指标。

## 实现时的对照表

下面是本站设计的检查视角，可结合自己的项目使用。

| 观察对象 | 需要明确什么 | 自查问题 |
| --- | --- | --- |
| 定位 | 明确指出文件与触发条件 | 读者能否找到相关逻辑 |
| 影响 | 解释错误会造成什么结果 | 是否区别实际故障与偏好 |
| 证据 | 复现、测试或完整推导 | 是否只凭局部差异猜测 |
| 处置 | 修复建议和验证办法 | 是否引入更大的改动 |

## 动手练习

选择一个已有回归测试的小型缺陷，给审查器看修复前的代码和必要上下文；再给一份正确实现作为对照。记录发现率、误报和定位准确度。检查结论时隐藏答案，避免把测试中的期望结果直接喂给审查器。
