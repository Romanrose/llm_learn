# CS146S 第 02 讲：把模型放进可工作的 Harness

## 课程依据

本讲把系统提示、工具、配置文件、规划、Skills、Hooks、子智能体和上下文压缩放在同一个 Harness 中讨论，并强调工具接口与上下文的简洁性。 [阅读官方讲义](https://docs.google.com/presentation/d/1RZu-p18Qybbgm8WVP2RH04ESc4Bn377B-T9j5-TBFdQ/htmlpresent)。

## 从一个问题开始

为什么同一个模型，放进两个开发工具里会表现不同？

可以把一次失败定位到不同边界：模型没有提出正确行动，工具没有正确执行，或者返回结果没有进入下一轮。它们需要不同修复。修改提示词未必能解决工具返回格式错误；增加工具也未必能解决项目说明缺失。先保存执行记录，再确定要改哪一层，能减少没有依据的调参。

## 实现时的对照表

下面是本站设计的检查视角，可结合自己的项目使用。

| 观察对象 | 需要明确什么 | 自查问题 |
| --- | --- | --- |
| 系统说明 | 角色、环境与工作约定 | 是否与当前项目匹配 |
| 工具接口 | 可以执行哪些动作 | 名称、参数与错误是否明确 |
| 任务上下文 | 本次修改需要知道什么 | 是否有过期或无关信息 |
| 压缩与委派 | 长任务如何继续 | 关键约束是否丢失 |

## 动手练习

拿同一个小任务做两次实验。第一次只给目标，第二次补充目录结构、构建命令和验收条件。保留工具调用与最终差异，比较读取路径是否准确、失败是否被识别、验收是否完成。这个实验比较的是两种上下文配置，不足以证明模型能力发生变化。
