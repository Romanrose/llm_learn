# 从“画三角形”到“启动线程块”：Stanford CS149 Lecture 7 的 GPU 心智模型

## 导语

如果只看标题，CS149 第七讲似乎是在讲一门新语言——CUDA。但整堂课真正想传达的结论恰恰相反：**今天没有新概念**。多核、SIMD、多线程、SPMD，这些在前几周 CPU 编程中已经反复打磨的思想，只是换了一种规模、换了一套命名，被部署在现代 GPU 上。理解这一点，比记住 `blockIdx`、`threadIdx`、`__syncthreads()` 的拼写重要得多。

本文按课程的论证顺序重组这一讲：先看 GPU 如何从图形芯片演化为通用并行处理器，再看 CUDA 如何用 SPMD 抽象取代“画三角形”的 hack，接着深入内存层次与线程块设计，最后落到硬件实现——warp、隐式 SIMD、SM 的资源调度。理解这条链路，也就理解了本讲在本课程学习路径中的位置：它是把前半学期的并行编程原则，第一次完整地投射到一块真实的大规模并行芯片上。

## 一、起点：GPU 本来只会做一件事

课程的叙述从图形学开始，但只用“大概五张幻灯片”讲完 CS 248。GPU 最初的目标非常具体：给定场景的几何描述、灯光、相机位置，模拟光的弹跳与材质，输出一张真实相机会拍到的图像。核心表示是三角形网格——给 GPU 一个 3D 顶点列表和相机朝向，让它计算顶点投影到屏幕的位置，再为每个被三角形覆盖的像素计算颜色。

关键转折出现在材质上。现实世界的材质差异太大：竹纹理、闪亮的金属门把手、鞋上的闪光、光线进入皮肤内部弹射后再射出。与其把颜色写死，不如**写一段程序，对屏幕上的每个像素运行**。给定 2D 坐标、表面法线、纹理细节，这段程序返回一个 RGBA 颜色。课程展示的代码片段正是这个结构：输入是位置与法线，输出是 `vec3` RGB 加 alpha。

这就是 GPU 加入多核与 SIMD 的原因：一张 4K 图像有数百万像素，每秒要处理几十次，也就是每秒数亿到数十亿个像素。数据并行天然存在，加核心、加 ALU 就是最直接的加速方式。课程把它和第一讲的“晶体管越来越多、但单线程提频与超标量走到尽头”联系起来：GPU 选择了另一条路——随着晶体管数量上升，不断增加核心。

## 二、大 hack 与 Brook：通用计算的前史

在 CUDA 出现之前，想用 GPU 做非图形计算的人只能“hack”。课程举了一个极具画面感的例子：要渲染一张 512×512 的图像，就用两个三角形覆盖整个屏幕，从而强制产生 512² 次像素着色函数调用；然后把本该计算颜色的程序，改成做物理模拟的粒子时间步进、蛋白质折叠，甚至把 RGBA 输出当作流体模拟的 XYZ 位置。这个做法对用户来说很别扭，但性能确实比手写 C++ 多线程代码快得多。

2004 年斯坦福的研究项目直接指出：这是个 hack，很蠢。既然大家都知道数据并行，为什么不设计一个正经的编程系统，把 GPU 当作并行处理器对待？于是有了 Brook 这类流编程 / 数据并行编程模型：`scale` 这样的函数不是作用于标量，而是作用于一个集合——比如 1000 个数字的向量，对每个元素应用同样的操作。这段代码会被源到源编译成“画两个三角形”的图形程序。**对用户不再 hack，对实现仍然是 hack。**

这段历史解释了 CUDA 的设计动机：NVIDIA 受这类项目启发，决定让芯片支持通用目的代码。但要理解 CUDA 的接口为何长这样，需要先对比 CPU 上如何启动计算。

## 三、CPU 的启动方式 vs. GPU 的启动方式

课程让听众想象一台双核机器，操作系统要运行两个程序。做法是：编译出两条指令流，为每个核初始化寄存器状态，把下一条要执行的指令设为程序入口，然后让核开始跑。一次一个线程，这就是操作系统在 CPU 上运行代码的方式。

而早期 GPU 的软件接口是**图形流水线**：软件给 GPU 一个三角形列表、一个计算表面颜色的程序、一个相机位置，流水线自己决定何时为哪个像素运行那段程序。它不是“启动线程”，而是“描述一次渲染”。

2007 年 NVIDIA 提出计算模式，本质上是在两者之间取一个折中。新的接口是：你写一个小程序（**kernel**），然后说“运行这个 kernel 的 N 个副本”。GPU 自己想办法并行化这些副本。课程明确指出：**这是经典的 SPMD 编程模型**——代码里有一个线程 ID，系统启动 N 个副本。它非常像 ISPC：ISPC 里叫“一组程序实例（gang of program instances）”，CUDA 里叫“CUDA 线程”。课程特别提醒：本讲中说“线程”，除非特别说明“硬件执行上下文”，指的都是 CUDA 线程，即 NVIDIA 定义的那个抽象。

## 四、CUDA 编程模型：批量启动、多维 ID、越界检查

CUDA 的调用语法里，`<<<...>>>` 不是“运行 N 次”，而是“创建这么多实例”，并且实例数量可以是多维的。课程用矩阵加法举例：两个 12×6 的矩阵逐元素相加，需要 72 个线程；但程序员不必说“创建 72 个线程”，而是说创建若干**线程块（block）**，每块是 4×3 的线程网格。

在 kernel 内部，线程通过内置变量计算自己的唯一 ID：块内线程 ID、块 ID、块维度。课程给出一个清晰的类比：**块内线程 ID 类似 ISPC 的程序实例 ID，块 ID 类似 ISPC 的任务 ID**。ISPC 把东西组织成任务和任务内的 gang，CUDA 把东西组织成线程块，然后一次创建很多线程块。没有新概念，只是名字不同、细节略有差异。

为什么要有二维 ID？课程承认这在入门示例里并非本质必要，一维完全可行。但图像处理、张量处理、图形中，二维 ID 可以直接对应 I、J，避免在一维 ID 到 N 维张量之间做大量除法，从而更高效地计算内存地址。这是历史与实用性的产物，不是概念上的必需。

紧接着是一个重要的教学例子：矩阵大小改成 11×5，块大小仍是 4×3。55 个任务，却按 12 个线程一组创建，块数向上取整，于是创建的线程数超过 55。部分线程计算出的 I、J 会越界，代码里用 `if` 检查。课程借此强调：**这是 SPMD 编程模型**。你不是在说“对数组每个元素启动一个线程”，而是“为所有块的所有线程启动线程”，线程自己用程序算出该做什么。没有那个 `if`，就会读写数组末尾之外的内存，程序可能崩溃。抽象上是“创建 CUDA 线程”，实现上是“批量线程启动”——就像给标准线程创建 API 加上“我要 150 个线程块、每块 4×3”这样的参数。

## 五、内存模型：分离地址空间与三层局部性

CUDA 的内存模型在课程中被讲得非常直白：`void main` 跑在 CPU 上，有自己的地址空间；GPU 设备有自己的地址空间，被 CUDA 线程访问。在 C 里 `malloc` 的数组，直接在 CUDA 里解引用不会工作，因为不在同一个地址空间。标准做法是 `cudaMalloc` 在设备地址空间分配，用库调用把数据从 CPU 拷到 GPU，再把设备指针传给 kernel。课程提到现代系统可以直接传 C 指针，但那意味着 GPU 访存要走 PCIe 之类的总线，所以本讲坚持“分离地址空间”的直白版本。

课程还讨论了这次 `memcpy` 的本质：在独立显卡系统上，它通过 PCI 总线把字节搬进 GPU 的 DRAM，是两个不同 DRAM 之间的慢速拷贝。有异步方式可以隐藏延迟——这正好呼应之前讲过的消息传递：某种意义上，`memcpy` 就是从一个地址空间发往另一个地址空间的消息。

更细的层次是：每个线程有自己的局部变量和本地栈，只有自己能访问；每个线程块有一块只有该块线程能访问的地址空间；此外还有所有线程都能通过 load/store 访问的设备全局内存。课程点明这层组织的意图：**我们在给 GPU 提示，如何为了局部性把这些线程放在一起。**

## 六、一维卷积：从朴素版到共享内存版

课程用一维卷积作为最小的练习：输出是同一位置附近输入的平均值，也是深度神经网络卷积层的 1D 等价物。朴素版中，每个线程计算自己的索引，从全局内存加载三个值，相乘后输出。课程确认它正确，但指出问题：相邻线程读取的元素有重叠。每个线程各自发出加载指令，另一个线程对同样的数据再发一次，也许有缓存命中来放大效果，但这不是高效写法。

于是有了共享内存版。线程块大小 128，要计算 128 个输出，需要 130 个输入。线程分配一个 130 元素的 `shared` 数组——这个类型修饰符表示它不是每线程分配，而是每线程块分配，类似 ISPC 的 uniform 变量。接着是一段被课程自己称为“太丑了”的编排：每个线程把一个值从全局内存复制到共享数组；因为需要 130 个而不是 128 个，块中线程 0 和 1 额外搬最后两个元素。然后 `__syncthreads()`——块内屏障——等待所有线程完成各自那份加载。之后每个线程独立计算自己的输出，但访问的是本地共享内存，而不是全局内存。

为什么需要屏障？课程让全班一起想：如果去掉它，GPU 运行这些线程的顺序没有保证。某个线程可能加载完自己的数据就立刻开始计算，但我们不知道其他线程是否已经把数据搬进来。屏障保证越过它之后，共享本地内存已被正确初始化。

为什么值得这么编排？课程给出实现层面的解释：共享变量背后的存储可以认为是高性能的 L1 缓存；CUDA 会把同一个线程块中的所有线程放在同一个核心上，于是这些线程可以在有复用时访问这块快速本地内存。这段代码的洞察是：**没有单个线程重复使用数据，但一个线程使用了它的邻居也使用的数据**。所以协作地把数据一次性带入，再在快速共享内存上工作。

课程也澄清了几个常见混淆：线程局部变量是默认的，每个线程一份拷贝；每块一次的变量是额外的能力，具体分配由编译器决定。SPMD 是编程模型问题，与实现无关；ISPC 和 CUDA 都是 SPMD 编程模型，如何高效执行这些实例是另一回事——ISPC 用 SIMD 指令，GPU 也涉及 SIMD，但方式不同。块大小完全由程序员控制，但它不能超过单个核心能运行的线程数；可以更少，因为多个块可以放在一个核心上。访存是否连续会影响性能：连续地址对底层更友好，任意地址程序仍能工作，但缓存局部性等因素可能降低性能。`cudaMalloc` 给你一段连续地址空间，如何布局矩阵元素是程序员的选择。CUDA 还提供块内屏障、原子操作、主机与设备之间的同步等结构，课程预告这些会在作业 3 中遇到。

## 七、实现：线程块是调度的粒度

课程接着转向实现，用一个关键问题推进：如果主机代码决定创建大约一百万个线程，除以 128 约等于 8K 个线程块，NVIDIA 真的会去找一百万个线程上下文吗？当然不会，它可能根本没有这个能力。这个大批量启动让人想到什么？**任务**。就像 ISPC 任务分解为程序实例，CUDA 线程块分解为 CUDA 线程。这段代码应该无论有多少核心、SIMD 宽度是多少都能工作——大 GPU、中等 GPU、Grace Hopper 芯片都一样。

编译设备代码时，除了指令流，还得到元数据：每块需要 128 个线程，共享分配是 130 个元素宽，也就是需要 512 字节存储。于是运行一个线程块需要 128 个线程的资源和 520 字节（课程原话如此）的存储。想象一个四核的小 GPU，8K 个线程块就像任务一样被分发给工作器。课程提醒：CUDA 中某些线程块之间可以设置依赖，但作业 2 中你写的调度逻辑是嵌入在 GPU 硬件硅片里的。硬件接口不是“这是一个程序、这是一个 PC、在这个线程上开始运行”，而是“这是一个指令流、一个程序二进制，请运行它的所有这些线程块”。这是“声明独立工作、让调度器分配给工作器”这一设计模式的又一个实例。

然后课程给出 Volta V100 的图（并预告之后会讲现代 Grace Hopper 芯片，但结构非常相似）。一个 GPU 核心顶部是取指译码单元，旁边是 16 个必须以 SIMD 方式运行的 ALU，加上执行上下文存储。课程特意把执行上下文画成线程 0 的 r0、r1、r2、r3，线程 1 的，线程 2 的，一直到线程 31——这是 128 个线程的执行上下文，一个重度多线程芯片。

这里出现了本讲最重要的实现差异。CPU 上，一个线程运行 SIMD，是编译器生成 SIMD 指令；GPU 上面向硬件的 SPMD 接口让硬件知道它在运行程序的 N 个副本。每个线程有自己的程序计数器（PC），它本身就是寄存器之一。当 32 个连续线程处于相同的 PC 时，同一条指令由所有线程以 SIMD 方式执行。这就是**隐式 SIMD**：思路一样，只是 CPU 上由编译器生成 SIMD 指令，GPU 上由硬件发现“它们恰好都在同一位置”。NVIDIA 把这 32 个 CUDA 线程的执行上下文块称为 **warp**。warp 中的线程若处于程序相同位置，就及时地被一起执行；硬件基本就是比较 PC，全部相同就发出一条 SIMD 指令。

课程也坦白了细节上的“不整齐”：一个 warp 是 32 个线程，但只有 16 个 SIMD ALU，所以实际上每隔一个时钟周期运行一条指令，以 16 宽、16 宽在连续时钟周期上执行。取指译码并非空闲：在额外的时钟周期里它开始向其他单元分发指令，比如浮点、整数、加载存储、超越数学运算。调度器没那么动态，它只是知道发射一条浮点指令后可以两个周期后再发下一条。这些底层细节课程明确说不重要，但“可能觉得酷”。

关于 warp 与线程块的关系，课程澄清：warp 是硬件实现细节，你永远看不到；你只看到自己创建了 128 个 CUDA 线程，NVIDIA 用四个 warp 的执行上下文来运行它。线程块是编程模型的一部分。课程还提到 NVIDIA 在非常近的年代、非常有限的条件下才会真正重新组织线程以获得更好的 SIMD 一致性；99% 的时间里它表现得像一台 32 宽 SIMD、有四个独特 PC 的机器。若 warp 内 PC 不一致，就只运行 PC 相同的线程，再运行另一批——行为就像作业 2 中做的掩码，只不过硬件替你处理。NVIDIA 保留改变 SIMD 宽度的余地：Intel 改 SIMD 宽度你得重新编译，因为二进制里写着 AVX 指令的宽度；而 CUDA 代码只是标量指令，未来改成 64 宽仍能运行。

## 八、SM：把一切串起来

课程把核心图景组装起来：这个芯片的实际核心是四个“子核”的复制，所以执行上下文编号如此安排。这个大核心有 64 个 warp 的执行上下文，即 64×32 个 CUDA 线程；有四个不同的向量 ALU 组和四个不同的取指译码器。每个取指译码器只在自己的 warp 之间选择，所以一个时钟周期最多在四个 warp 上取得进展，但从 64 个 warp 中选择——大量延迟隐藏。课程强调：这里没有新概念，就是多线程、SIMD，以及指令发射层面的同时多线程和超标量。

于是调度图景清晰了：CUDA 说“我需要在一个核心上运行这个线程块”，硬件就从共享内存分配 512 字节，分配 128 个线程（四个 warp）的执行上下文，智能地分配到各切片上并发运行。这个块就是 NVIDIA 所称的**流式多处理器（SM）**。V100 上复制 80 次，每个 SM 有四列 16 宽浮点向量 ALU；课程给出“12.7 太浮点运算”的量和“163,000 个并发活跃 CUDA 线程”的估算——对比 Intel 处理器的两个超线程，这是数量级的差异。课程也提醒：这些线程不能同时全部执行，但同时都在芯片上。

共享内存是程序员开始对调度细节做出断言的地方，因此存在折中：CUDA 说“你只告诉我们运行多少块，我们按我们想要的方式运行”，但内存太重要，所以允许你断言“我需要 512 字节”。NVIDIA 要做的，是运行一个线程块时在同一个核心上选择 warp 执行上下文、分配那块存储让所有执行上下文读写。由于这些线程都在同一个核心上，屏障之类的操作非常快；如果部分线程被放到别处，屏障就会变成跨单元的通信。所以**线程块是同步和数据局部性的粒度单位**。

## 九、三个检验：为什么 CUDA 拒绝某些程序

课程最后用几张幻灯片检验理解，这也是全讲最精彩的推理部分。

第一张：一个核心只有 128 个执行上下文（四个 warp），线程块却有 256 个 CUDA 线程。NVIDIA 会说“抱歉，你没法运行这个”。为什么不能先跑前 128 个、完成后再跑后 128 个？因为程序员已经指定了数据局部性——但那只是表层答案。真正的理由在屏障：如果先运行 128 个线程，它们停在屏障处，仍然占着执行上下文，什么也不会发生，它们永远不会让出，另外 128 个线程永远没机会运行。除非引入抢占——把线程从处理器上剥离再换另一批——而那会非常没有性能。所以 NVIDIA 说：我们是高性能编程系统，程序员决定的事我们要尊重，不想为了“正确运行”而做疯狂的事、以糟糕方式影响性能。标准 CUDA 里应当认为没有抢占。线程块中的线程不只是 SPMD 线程，而是在同一时间并发运行、在同一个 SM 上同时存活，因为它们可能通过屏障或原子操作协作。

第二张：直方图。一堆线程，不管在哪个块里，计算某个值，然后 `atomicAdd` 递增一个 bin。不同线程块里的线程触碰同一块全局内存——这是合法 CUDA 程序。因为它没有对 CUDA 如何运行这些线程块做出任何假设：想什么时候运行就什么时候运行，可能争抢原子操作，但那又怎样。

第三张：两个线程块，一个更新内存变量，另一个等它被更新。在一个一次只能运行一个线程块的 GPU 上，如果先运行等待的那个块，它永远等不到，另一个块永远没机会执行。课程由此给出规则：**线程块之间可以通信，但不能对执行顺序做假设；线程块内部的线程可以假设同时运行，可以使用屏障。**

## 结语：这一讲在课程路径中的位置

回看整讲，CUDA 被讲成了一次“命名的迁移”：ISPC 的程序实例变成 CUDA 线程，gang 变成线程块，uniform 变量变成 `shared` 分配，任务调度变成硬件里嵌入的线程块调度器。真正新增的只有实现层面的图景——warp、隐式 SIMD、SM 的多级执行上下文与资源分配——以及由此推出的编程规则：线程块是同步与局部性的粒度，块间不假设顺序，块大小是对硬件的断言。

这正是本讲在 CS149 学习路径中的位置。前几周建立的多线程、SIMD、SPMD、消息传递、任务调度、局部性等原则，在这里第一次被完整地投射到一块拥有海量执行上下文、以吞吐量为先的芯片上。课程反复说“今天没有新概念”，不是降低难度，而是提高要求：你应当能把 GPU 当成同一组并行思想的另一种实例化来推理，而不是当成一堆 API。作业 2 让你亲手实现任务调度，作业 3 会让你遇到屏障、原子操作与主机设备同步——那时你会发现，这一讲给出的心智模型，正是后面所有 CUDA 编程的底座。
