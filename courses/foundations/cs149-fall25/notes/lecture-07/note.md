## 学习目标

学完本讲后，你应该能够：

- 说明 GPU 从图形专用芯片演化为通用并行处理器的历史脉络，以及 CUDA 出现要解决的核心问题。

- 解释 `__shared__` 变量、`__syncthreads()` 屏障的作用，以及为什么线程块是数据局部性与同步的粒度单位。
- 用“批量启动任务 + 硬件调度器分配资源”的框架解释 GPU 如何执行大量 CUDA 线程，理解 warp、隐式 SIMD、延迟隐藏与 SM 的组织方式。
- 判断一段 CUDA 代码是否对线程块执行顺序做了不被允许的假设。

## 课程主线

本讲的主线可以概括为一条因果链：

1. **GPU 的原始目标**是图形渲染：给定场景的几何、材质、光源与相机，计算出一张图像。渲染的核心计算是对每个像素运行一个独立的着色程序——天然的数据并行。
2. **渲染需求推动并行化**：为了每秒处理数亿像素，GPU 不断增加核心与 ALU，走上与 CPU 不同的道路（CPU 受时钟频率与 ILP 限制停滞，GPU 随晶体管增长持续加核）。
3. **早期 GPGPU 是 hack**：研究者用“画两个覆盖全屏的三角形”来诱发 N 次函数调用，把着色器程序挪作物理模拟等用途。
4. **Brook 等项目**提出用数据并行 / 流编程模型正经地使用 GPU，源到源编译回图形接口。
5. **NVIDIA 在 2007 年推出 CUDA**：保留“运行 N 份小程序”的 SPMD 抽象，但抛弃“画三角形”的接口，改为“这是 kernel 二进制，请运行它的 N 个副本（组织为线程块）”。硬件接口从此不再是“设置 PC 启动一个线程”，而是批量任务派发。
6. **实现层面**：GPU 用大量执行上下文、warp、隐式 SIMD 和多线程来高效执行这些 SPMD 线程；线程块被整体放到同一个 SM 上，以获得共享内存与快速屏障。

贯穿全讲的态度是：**今天没有全新概念**——多核、SIMD、多线程、任务调度都已在课程前几周出现过，CUDA 只是它们在现代 GPU 上的另一种实例化。

## 核心概念

### 1. 图形流水线与着色器的数据并行本质

GPU 的输入是三角形网格（顶点列表）、相机位置、以及一个计算表面颜色的程序。GPU 完成顶点投影，然后对每个被三角形覆盖的像素运行着色程序，输出颜色（如 `vec3` RGB 加 alpha）。这正是“对每个元素运行一个独立函数”的数据并行计算，与课程前面讨论的模式一致。着色器语言的出现（2000 年代初）让程序员写程序而非直接指定颜色，为后来的通用计算埋下伏笔。

### 2. 从 hack 到 CUDA 的抽象转变

- **hack 时代**：用两个大三角形覆盖屏幕，诱发 512×512 次着色器调用，把 RGBA 输出当作模拟状态。用户视角稍有改善，实现视角仍是 hack。
- **CPU 启动线程的方式**（对照）：操作系统为每个线程初始化寄存器状态、设置入口 PC，一次一个线程地交给某个核。
- **CUDA 的方式**：程序员写一个 kernel，声明“运行它的 N 个副本”（按线程块组织）；GPU 自行决定如何并行化。这是经典的 **SPMD** 编程模型。

课程明确要求思考：CUDA 该被理解为数据并行还是 SPMD？消息传递还是共享地址空间？答案是 SPMD +（主机/设备分离的）地址空间，块内可用共享内存与屏障通信。

### 3. CUDA 术语与 ISPC 的对应

| ISPC | CUDA |
|---|---|
| program instance | CUDA thread |
| gang of program instances | （隐式，见 warp） |
| task | thread block（以及 block 的批量启动） |
| `programCount` / `programIndex` | `blockDim` / `threadIdx` |
| uniform 变量 | `__shared__` 每线程块变量 |

注意：课程中说“CUDA 线程”时，除非特别说明，指编程模型意义上的线程，不是硬件执行上下文。

### 4. Kernel 启动语法与线程 ID 计算

主机代码用 `<<<numBlocks, threadsPerBlock>>>` 形式启动 kernel，例如为 12×6 矩阵加法创建 4×3 的线程块、共 12/4 × 6/3 个块。之所以支持多维线程 ID，是因为图像、张量、图形处理中直接用 (i, j) 寻址可以省去大量除法，更高效地计算内存地址——但这不是本质需求，一维也完全可行。

kernel 内用内置变量计算唯一 ID：

```
int i = blockIdx.x * blockDim.x + threadIdx.x;  // 一维情形
```

概念上：`threadIdx` 类似 program instance ID，`blockIdx` 类似 task ID。

### 5. 内存模型

- **主机（CPU）地址空间**与**设备（GPU）地址空间**分离。普通 `malloc` 得到的指针不能在 kernel 中解引用。
- 设备内存用 `cudaMalloc` 分配，用 `cudaMemcpy` 在主机与设备间搬运——在独立显卡上这通常经 PCIe 传输，是慢速拷贝，实际中会异步执行以隐藏延迟。它本质上就是两个地址空间之间的“消息传递”。
- 课程选择坚持讲分离地址空间的简化模型（现代系统可以把 C 指针直接传入 kernel，但访问会走 PCIe）。
- 在设备侧还有层次：每线程私有局部变量（自己的栈）、每线程块 `__shared__` 变量、所有线程可访问的全局设备内存。

### 6. 边界检查与 SPMD 的真正含义

矩阵加法示例改为 11×5、块大小 4×3 时，向上取整会创建多于 55 个线程，部分线程越界。kernel 内必须用 `if` 判断自己是否负责有效工作，否则会读写数组末尾之外的内存。

关键点：编程模型**不是**“对每个数组元素启动一个线程”，而是“启动你声明的所有块和块内所有线程”；线程自己用程序逻辑决定做什么。这正是 SPMD 的含义。

### 7. 一维卷积与共享内存优化

- **朴素版本**：每个线程从全局内存读 3 个元素算一个输出。相邻线程的读取有重叠，依赖缓存获得一定复用，但每个线程自身没有复用。
- **共享内存版本**：块大小 128，需要 128+2=130 个输入。每个线程先把一个输入装入 `__shared__ float` 数组（前两个线程额外搬运多出的 2 个元素），然后 `__syncthreads()`，之后所有线程从快速片上存储读取并计算。
- **为什么需要 `__syncthreads()`**：线程可能并发执行，某线程装完自己的数据后可能立即开始计算，但无法保证其他线程已把数据放入共享数组。屏障保证越过它之后共享内存已正确初始化。
- **为什么快**：同一个线程块的所有线程被放在同一个核心上，共享内存可视为高性能的片上暂存（课程类比 L1）；数据协作地一次性带入，然后在快速存储上复用。

### 8. 实现：warp、隐式 SIMD 与 SM

- kernel 二进制附带元数据：每块线程数、每块所需共享存储字节数（如 128 线程、512 字节）。这让硬件可以提前判断资源是否放得下。
- **执行上下文**：NVIDIA 线程的执行上下文是一组**标量寄存器**（含 PC）。这与 CPU SIMD 不同——CPU 上编译器生成向量指令；GPU 上每个 CUDA 线程有自己的 PC，当 32 个连续线程 PC 相同时，硬件用 SIMD 单元一次执行同一条指令，称为**隐式 SIMD**。
- **warp**：32 个 CUDA 线程的执行上下文块。warp 是硬件细节，程序员看不到；你只看到自己创建了 128 个线程，NVIDIA 用 4 个 warp 来跑。
- **分歧处理**：若 warp 内 PC 不一致，硬件用与作业 2 相同的掩码机制，只运行 PC 相同的线程，再运行其余分支。
- **SM（Streaming Multiprocessor）**：课程以 V100 为例描述其结构——包含多个子核（sub-core），每个子核有取指译码单元和一组 SIMD ALU（如 16 宽），以及大量 warp 执行上下文（图中一个 SM 有 64 个 warp，即 2000 个 CUDA 线程）。每个时钟周期最多从 64 个 warp 中选择 4 个推进——类似四路同时多线程加超标量发射，但调度逻辑比 CPU 简单得多（例如知道浮点指令两个周期后可以再发射）。大量 warp 提供**延迟隐藏**。
- 因为 SIMD 宽度由硬件在运行时决定，NVIDIA 保留将来改变宽度、重排线程的自由；而 CPU 的 SIMD 宽度写死在二进制里，改宽度必须重新编译。

### 9. 线程块调度与资源约束

批量启动的线程块像任务队列：硬件调度器逐个派发线程块到 SM，为其分配执行上下文和共享内存；资源不足时等待；某块完成后释放的资源恰好够启动下一个同质的新块。这依赖所有块资源需求一致，避免了复杂分配问题。

**为什么一个线程块的线程必须能同时驻留在一个 SM 上**：若块大于核心容量，且块内有屏障，先运行的线程会在屏障处永久等待未运行的线程——没有抢占就会死锁。CUDA 的立场是高性能系统应尊重程序员对并发与局部性的断言，不做昂贵的抢占魔法，因此直接拒绝这种程序。

## 关键公式与原则

- 全局线程 ID：`global_id = blockIdx * blockDim + threadIdx`（多维时逐维计算）。
- 启动线程总数 = `numBlocks × threadsPerBlock`；实际任务数常小于它，需在 kernel 内做边界检查。
- 共享内存版本卷积的片上存储需求：`threadsPerBlock + (卷积宽度 - 1)` 个元素。
- **原则一**：线程块内的线程可假设彼此并发存活，可用屏障、共享内存协作；不同线程块之间**不得对执行顺序做任何假设**。
- **原则二**：`__syncthreads()` 之前的协作加载与之后的独立计算之间必须有屏障分隔。
- **原则三**：手动指定块大小、共享内存用量，就是对硬件能力做出断言；超出目标硬件限制的程序无法运行。
- **原则四**：主机与设备地址空间分离，跨空间数据移动是显式、慢速的操作，应尽量摊薄或异步化。

## 常见误区

1. **把 SPMD 当成 SIMD**。SPMD 是编程模型（写一个程序，系统用不同线程 ID 运行多份），与实现无关；ISPC 用 SIMD 指令实现它，GPU 用 warp + 隐式 SIMD 实现它。二者不是同一层概念。
2. **以为在“为每个数组元素创建线程”**。编程模型是启动块和块内线程的批量集合；哪些线程做有效工作由 kernel 内逻辑决定，因此边界检查是程序员的责任。
3. **以为 warp 是编程模型的一部分**。warp 是硬件实现细节，CUDA 代码中不可见、不可直接控制。
4. **以为不同线程块可以互相等待**。不同块之间不得假设执行顺序；一个块等另一个块更新的代码在小 GPU 上可能死锁。（块内用屏障、跨块用原子操作都是合法的。）
5. **忘记 `__syncthreads()`**。协作加载共享内存后不设屏障，某些线程可能在数据就绪前开始计算，结果不确定。
6. **在 kernel 中解引用主机指针**。主机与设备地址空间分离，需 `cudaMalloc` + `cudaMemcpy`；课程坚持这一简化模型。
7. **以为块大小可以任意大**。块必须能整体驻留在一个 SM 上（执行上下文与共享内存都够），否则程序无法运行。
8. **忽视访存模式**。共享内存优化能成立，前提是线程访问连续、有邻域重叠的地址；任意地址访问程序仍正确，但性能会差很多。矩阵按行还是按列布局由程序员决定，直接影响性能。
