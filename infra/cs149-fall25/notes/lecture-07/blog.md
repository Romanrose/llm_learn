# 从像素着色到十六万线程：GPU 架构与 CUDA 编程模型

## 导语：GPU 并没有发明一种全新的并行计算

提到 GPU，人们很容易先想到庞大的核心数量、惊人的浮点运算能力，以及 CUDA 中数量动辄成千上万的线程。但 Stanford CS149 第 7 讲希望建立的第一个认识恰恰是：现代 GPU 并没有推翻此前学过的并行计算概念。

它仍然建立在多核、SIMD、多线程和超标量执行之上，只是把这些机制组合起来，并以比普通 CPU 更大的规模部署。理解 GPU 的关键，不是背诵一套孤立的新术语，而是把 CUDA thread、thread block、warp 和 SM 分别映射到课程此前讨论过的 SPMD、任务划分、SIMD 和硬件执行上下文。

这也解释了本讲在 CS149 学习路径中的位置。课程前几周已经讨论了多线程、SIMD、多核执行和 ISPC，学生也通过书面作业与 CPU 编程实践接触了这些概念。第 7 讲把同一套思维迁移到 GPU：先看一种面向程序员的并行抽象如何形成，再深入硬件，理解它为什么能高效执行，以及这种抽象对程序正确性和性能施加了哪些约束。

## 一、GPU 为什么从图形芯片变成了通用并行处理器

GPU 最初面对的是一个非常具体的问题：给定场景中的几何表面、材质、光源和虚拟摄像机，生成摄像机所能看到的图像。

在传统图形处理中，场景表面通常表示为三角形网格。GPU 首先计算三维顶点投影到屏幕上的位置，然后为三角形覆盖的每个像素计算颜色。真正棘手的地方在于材质：竹纹、金属、鞋面闪光和人体皮肤对光线的响应各不相同，很难用一种固定公式覆盖整个世界。

于是，图形系统开始允许开发者编写小程序，让它针对每个像素运行。程序根据表面坐标、法线和纹理等输入，计算一个 RGBA 颜色。这里天然存在数据并行：一张图像包含数百万个像素，每个像素都要执行结构相近、彼此大体独立的计算，而且这一过程每秒需要重复许多次。

因此，GPU 很早就走上了增加核心和 ALU 的路线。当提高 CPU 单线程性能的传统办法逐渐受阻——时钟频率继续提高会带来过高功耗，而单个线程中可挖掘的指令级并行也越来越有限——GPU 却可以把新增晶体管继续投入并行计算资源。图形工作负载已经提供了足够多的独立任务，更多核心可以直接转化为更高的像素处理吞吐量。

研究者很快意识到，这些芯片既然能运行每像素程序，就不必只计算颜色。大约二十年前，人们会在屏幕上画两个覆盖整个画面的三角形，借此触发大量函数调用，再把原本用于输出 RGBA 颜色的结果解释成粒子位置、流体状态或其他计算数据。比如，在一个 \(512\times512\) 的屏幕上覆盖所有像素，就相当于制造了 \(512^2\) 个程序实例。

这种办法证明了 GPU 的通用计算潜力，却仍然是对图形流水线的“借壳”。Brook 等研究项目进一步提供了流式或数据并行编程模型：程序员描述如何对一个集合中的每个元素执行函数，系统再把它转换为底层图形程序。对用户而言，这已经接近正规的并行语言；但实现层面仍然绕不开绘制三角形。

2007 年，NVIDIA 引入了更直接的计算抽象：程序员编写一个核函数，并请求 GPU 执行它的 N 个副本。至此，GPU 通用计算不再需要伪装成图形渲染。

## 二、CUDA 的核心不是“创建线程”，而是批量声明工作

CUDA 采用的是 SPMD，也就是单程序多数据编程模型。程序员只编写一份核函数，不同程序实例凭借各自的线程 ID 处理不同数据。

这与 CS149 此前讲过的 ISPC 很相似。在 ISPC 中，程序实例从逻辑上看像线程，底层则可能只是 SIMD 向量中的一条通道；在 CUDA 中，这种逻辑程序实例称为 CUDA thread。这里的“线程”首先是一种编程模型概念，不能直接等同于 CPU 上由操作系统逐个创建和调度的硬件线程。

CPU 通常从一个具体执行上下文出发：操作系统设置寄存器和下一条指令的位置，然后让某个核心开始执行。CUDA 则把更高层的接口暴露给硬件：这是一个核函数，请把它运行很多次。程序员描述工作规模，GPU 决定这些程序实例何时、在哪些计算单元上执行。

课程用矩阵逐元素相加说明了这种模型。假设 A、B、C 都是 \(12\times6\) 的矩阵，每个 CUDA 线程负责计算一个元素，那么总共需要 72 个线程。CUDA 不仅允许把线程排成一维序列，还可以采用二维或多维索引。这对图像和张量计算很方便：线程可以直接通过二维坐标确定自己负责的元素，避免反复把一维编号换算成多维位置。

CUDA 又把线程组织为 thread block。以 \(4\times3\) 的线程块为例，每块包含 12 个线程；若要覆盖 \(12\times6\) 的矩阵，就要启动相应数量的线程块。核函数中的线程根据 block index、block dimension 和 thread index，计算自己在整个数据结构中的唯一位置。

这种层次与 ISPC 的 task 和 task 内部的 gang 可以类比：线程块像任务，块内 CUDA 线程像一组程序实例。但线程块并非纯粹为了编号方便而存在，它稍后还会成为局部通信、同步和资源分配的边界。

批量启动也不等于“为数组中的每个合法元素自动生成一个线程”。课程把矩阵尺寸改成 \(11\times5\)，同时保留 \(4\times3\) 的线程块。由于工作只能按每块 12 个线程向上取整，实际创建的线程会多于 55 个。核函数必须自行检查坐标是否越界；否则，多出来的线程可能读写数组末尾之外的内存。

这个例子揭示了 CUDA 抽象的本质：系统只负责批量创建指定形状的程序实例，至于每个实例是否拥有有效工作、要访问哪项数据，仍由核函数决定。

## 三、主机、设备与三层内存可见性

在课程介绍的简化 CUDA 模型中，普通 C++ 主程序运行在 CPU 上，CUDA 核函数运行在 GPU 上，两者具有不同的地址空间。

在 CPU 中通过普通内存分配得到的指针，不能直接交给 GPU 核函数解引用；程序需要使用 `cudaMalloc` 在设备地址空间中分配数组，再通过库调用把数据从 CPU 内存复制到 GPU 内存。对于独立显卡，这次复制意味着数据要经过 PCIe，在两套 DRAM 之间移动，因此可能很慢，也可能需要采用异步复制来隐藏延迟。从并行模型的角度看，这种显式复制甚至带有某种消息传递的意味。

CUDA 设备内部还存在进一步的可见性层次：

- 每个线程拥有自己的局部变量和局部栈；
- 每个线程块可以拥有仅供块内线程访问的共享变量；
- 设备全局内存可以被所有 CUDA 线程通过加载和存储访问。

这种设计并不是随意添加的语言特性。它表达了一种重要的局部性提示：一批线程将协作完成某项工作，因此应当被放置在彼此靠近的位置，并共享一块快速存储。

## 四、一维卷积：线程块为何是性能抽象

课程用一维卷积展示了线程块的实际价值。最直接的实现是：每个线程计算一个输出元素，为此从全局内存读取相邻的三个输入值。问题在于，相邻输出的输入窗口彼此重叠，同一个输入元素可能被多个线程重复加载。

更精细的实现选择每个线程块包含 128 个线程。若要计算连续的 128 个输出，就需要 130 个输入。程序为每个线程块声明一个包含 130 个元素的共享数组：128 个线程各搬运一个输入，其中编号为 0 和 1 的两个线程再额外搬运最后两个元素。

数据搬运完成后，所有线程执行一次块内屏障。只有当整个线程块都到达屏障，线程才能继续使用共享数组计算各自的输出。

这道屏障不能省略。CUDA 不保证块内线程以怎样的先后顺序推进。某个线程可能已经写入自己负责的数据，并立刻开始卷积计算，而邻居尚未完成加载。此时，它会读取还没有正确初始化的共享位置。屏障的意义，就是把“协作加载”和“并行计算”分成两个明确阶段。

这段代码比直接读取全局内存复杂得多，却体现了 GPU 优化的核心方式：单个线程本身没有数据复用，但相邻线程之间存在复用。程序让线程协作，把全局数据只搬入一次，再从类似高性能 L1 缓存的共享存储中反复读取。

因此，线程块至少同时承担三种角色：

1. 它是批量工作划分的单位；
2. 它是共享内存与数据局部性的单位；
3. 它是屏障等快速同步机制的作用范围。

线程块大小也由程序员决定，但不能超过单个 GPU 核心所能同时容纳的线程数量。它可以更小，因为一个核心可以驻留多个线程块。

## 五、从 CUDA thread 到 warp：GPU 如何实现 SPMD

如果程序启动约一百万个线程，GPU 显然不会真的准备一百万套硬件执行资源。更合适的理解是：程序提交了大约八千个包含 128 个线程的线程块，GPU 像处理任务队列一样，持续把这些块分派给有限数量的核心。

核函数编译后不仅产生指令，还会附带资源需求。例如，一维卷积的每个线程块需要 128 个线程执行上下文，以及存放 130 个浮点数的共享存储。GPU 调度器根据这些元数据判断一个计算单元能同时容纳多少个线程块；某块完成后，释放出的执行上下文和共享内存就可以供下一个块使用。

课程随后以 Volta V100 为例解释单个 GPU 计算单元。NVIDIA 将这样的核心称为 Streaming Multiprocessor，简称 SM。SM 中包含多组取指与译码单元、SIMD ALU、大量线程执行上下文，以及由这些执行上下文共同访问的共享内存。

CPU 的 SIMD 通常由编译器显式生成向量指令。GPU 的接口却是一批看起来执行标量程序的 CUDA 线程：每个线程拥有自己的标量寄存器和程序计数器。当一组连续线程执行到同一条指令时，硬件把它们合并到 SIMD 单元上共同执行。这种方式被称为隐式 SIMD。

NVIDIA 把这样一组线程称为 warp。课程中的 warp 包含 32 个 CUDA 线程。可以把它近似理解为一个拥有向量指令的传统线程，但二者并不完全相同：每个 CUDA 线程确实拥有自己的程序计数器，硬件会检查 warp 内哪些线程处于相同位置，再决定哪些通道参与当前指令。

这也解释了分支发散。如果一个 warp 内的线程走向不同控制流路径，硬件只能先执行处于某一程序位置的线程，同时屏蔽其他通道，然后再执行另一条路径。其效果与此前课程作业中使用 SIMD mask 十分相似，只是掩码由 GPU 硬件动态决定。

CUDA 源程序没有把固定 SIMD 宽度直接写进指令，因此 NVIDIA 为硬件实现保留了更多自由；但在理解常见 GPU 执行时，把 warp 看作进行隐式 SIMD 的基本线程组仍然十分有效。

## 六、GPU 用“很多活跃线程”隐藏延迟

课程展示的 V100 SM 拥有足以容纳 64 个 warp 的执行上下文，并有四组向量 ALU和四个取指、译码单元。每个时钟周期最多推进 4 个 warp，但调度器可以从大量已经驻留、可运行的 warp 中选择。

这正是 GPU 高度多线程化的意义：不是让所有活跃线程在同一时刻都执行，而是让硬件始终拥有大量候选工作。当某个 warp 因内存访问或其他操作暂时无法推进时，调度器可以选择另一个就绪 warp，从而隐藏延迟。

V100 把 SM 复制了 80 次。课程根据约 1.2 GHz 的时钟频率、每个 SM 的四列计算资源以及每列 16 路浮点 ALU，给出了 12.7 TFLOPS 的浮点性能估算。按照 80 个 SM、每个 SM 64 个 warp、每个 warp 32 个线程计算，芯片上可以同时存在约 163,000 个活跃 CUDA 线程。它们不会全部在同一时钟周期执行，却都拥有驻留状态，成为调度器隐藏延迟的工作储备。

这里仍然没有新的基本原理：SM 只是把多线程、SIMD、同时多线程和一定程度的超标量发射组合在一起，并将规模推得远高于普通 CPU。

## 七、资源约束为什么也是正确性约束

线程块不仅影响性能，也定义了程序可以依赖的执行语义。CUDA 保证同一线程块中的线程同时保持活跃，并位于同一个 SM 上，因此它们才能安全使用共享内存和块内屏障。

课程设计了一个反例：某个核心只有 128 个线程执行上下文，程序却要求每个线程块包含 256 个线程。为什么不能先运行前 128 个，等它们结束后再运行后 128 个？

如果核函数中存在屏障，前 128 个线程会停在那里，等待块内其他 128 个线程到达；但后者尚未获得执行上下文。前一半不退出，后一半就无法运行，程序因而死锁。除非系统引入代价很高的抢占和状态换出机制，否则它无法偷偷把一个线程块分阶段执行。

因此，标准 CUDA 会直接拒绝超过硬件容量的线程块。程序员指定块大小，实际上是在声明：块内所有线程必须能够同时驻留，因为它们可能需要协作。

资源限制也决定一个 SM 能同时容纳多少个块。课程的简化示例中，每块需要 128 个执行上下文和 512 字节共享内存；一个 SM 即使还剩线程执行上下文，也可能因为共享内存不足而无法接纳更多块。只有已有线程块完成、释放资源之后，新块才能进入。

## 八、块内可以等待，块间不能假设顺序

CUDA 允许不同线程块访问同一设备全局内存。课程以直方图为例：许多线程计算各自的值，再通过全局内存上的原子加更新某个 bin。即使这些线程属于不同块，这仍然是合法程序。原子操作保证更新安全，而程序没有要求某个块必须先执行。

危险的是跨块等待。假设启动两个线程块：块 0 更新一个变量，块 1 循环等待该变量变化。如果 GPU 一次只能容纳一个块，而且恰好先调度块 1，那么块 1 会永远占住资源等待，块 0 则永远没有机会执行。

由此可以得到一条清晰的边界：

- 同一线程块内部，可以依赖共同驻留，并通过共享内存和屏障协作；
- 不同线程块之间可以通信，也可以使用全局原子操作；
- 但普通核函数不能假定线程块的执行次序，更不能用这种假设构造跨块等待。

这条边界让 GPU 得以自由地把大量线程块分配到不同规模、不同数量的 SM 上。同一份 CUDA 程序因而能够从较小的 GPU 扩展到拥有更多核心的大型 GPU，而不要求程序员手工安排每个块运行在哪里。

## 结语：CUDA 是程序员与硬件之间的一份并行契约

从表面看，CUDA 提供的是一套线程、线程块和共享内存语法；从更深层看，它定义了程序员与 GPU 之间的一份契约。

程序员负责暴露大量结构相似的工作，决定线程如何映射到数据，并指出哪些线程需要共享数据、共同同步。硬件负责把线程块分发到 SM，把连续 CUDA 线程组织成 warp，以隐式 SIMD 执行，并从大量驻留 warp 中选择可运行者来隐藏延迟。

线程块正是这份契约的关键边界：块内允许程序表达紧密协作，块间则必须保持足够独立，让调度器拥有自由。共享内存能够提高数据复用，却也消耗驻留资源；更大的线程块提供更多协作线程，却必须能整体容纳在一个 SM 中。性能、可移植性与正确性，在这里并不是三个互不相关的问题，而是由同一种资源与调度模型共同决定的。

第 7 讲最终完成了 CS149 学习路径中的一次重要连接：GPU 并非一块只能靠经验调参的神秘加速器。只要沿着课程已经建立的多核、SPMD、SIMD、多线程、局部性和任务调度框架逐层分析，CUDA 的抽象和 GPU 的硬件行为就能被放进同一幅图景之中。
