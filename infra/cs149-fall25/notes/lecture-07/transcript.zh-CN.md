[04:56.860] 知道它们在屏幕上的位置之后，对于图像中被这些三角形覆盖的每一个像素，我都需要计算那个三角形的颜色。如果我想计算三角形的颜色，那么看看这间教室，教室里各个表面的颜色取决于它们是由什么材质制成的。如果我们必须模拟光线如何从这些椅子、这片竹纹表面或者门把手的光亮金属上反射，你很快就会意识到：“哇，世界上有太多不同的材质了。”早期的图形学研究者对此的看法是——这里就是一组不同材质的例子。它们看上去都很相似。但我们的材质可以做得非常复杂：看看鞋子上的闪光；再考虑到光线会进入人体皮肤，在里面反弹许多次，然后从其他位置射出。为了仅仅计算这些三角形的颜色，我们就需要模拟光线如何从这些材质上反弹。

[05:56.080] 人们当时想：“世界上的材质差异实在太大了，我们只想写一个程序来做这件事。”我们不会直接说颜色是红色或蓝色，而是直接编写一个程序。于是，在 21 世纪初到中期，人们开始开发这些小型编程语言，让程序针对屏幕上的每一个像素运行，并且接收当前材质和表面朝向等信息。代码的具体细节并不重要，但大致来说，其中有一个坐标，也就是我在表面上所处位置的二维坐标；还有表面的法线，也就是从表面向外指的向量。另外还有纹理贴图（texture map）的细节。只要做一点工作，我们就有相应的算法，可以根据表面的朝向，以及比如说我希望把这张图像包裹到椅子表面上的需求来完成计算。如果我针对屏幕上的每一个像素运行这段代码，就可以计算出一种颜色。

[07:02.020] 如果你们看输出，返回的向量就是一种颜色。这里的 `KD` 是一个表示 RGB 的 `vec3`，最后那个分量是 alpha。对每个元素，也就是每个像素运行这个函数，就会得到一张这样的图像。所以，这就是我们之前讨论过的基本数据并行计算：为每个像素计算一些输入，然后在每个像素上运行这个完全独立的函数，从而计算出颜色。这基本上就是对 CS 248 的概括。因此，GPU 开始加入多核和 SIMD 的原因是，他们当时想：“我得处理一张 4K 图像，其中有数百万个像素，而且每秒要处理 60 次甚至更多。”我每秒必须处理数亿乃至数十亿个像素。因此，他们开始加入越来越多的 GPU 来更快地计算颜色——准确地说，是加入越来越多的核心和越来越多的 ALU，以便更快得多地计算颜色。

[08:06.310] 如果我们回到差不多整整 20 年前，再回想一下第一讲：还记得我们说过，晶体管越来越多，绿色曲线表示每块芯片上的晶体管数量。但所有那些把这些晶体管转化为更快的单线程处理器的方法，都已经渐渐行不通了。我们无法继续提高时钟频率，因为采用 4 GHz 处理器时，功耗会急剧上升。我们也无法再继续依靠超标量执行，因为在线程中已经找不到更多的指令级并行性（ILP）。但这些 GPU 早已转向了并行计算。随着绿色曲线上升，它们只需要加入越来越多的核心。因此，美国各地的一些人——包括斯坦福的一些人、北卡罗来纳大学的一些人，以及其他几个地方的人——就想：英特尔的处理器并没有变得更快，但这些 GPU 每次在晶体管数量翻倍时，都会增加更多核心。

[09:05.700] 而且它们能够运行代码。它们会运行一些小程序，用来计算物体的颜色。于是，有些人开始尝试各种 hack。他们采用了下面这种做法：假设你要把一幅图像渲染到一个 512×512 的屏幕上，他们说，我们要这样做——用三角形覆盖整个屏幕。然后，我们不再运行一个计算某个物体颜色的程序，而是直接让这个程序做些有意思的事情，比如在物理模拟中将粒子推进一个时间步，或者做蛋白质折叠之类的计算。于是就有了这样一种很大的 hack：实际上在屏幕上绘制两个三角形，基本上借此创建 \(512^2\) 次函数调用。接着，在这个原本应该计算表面颜色的程序里，你只需说：“嘿，做一些我希望它做的事情。”于是就出现了这些 hack。如果你看看这些工作的日期，大约是在 20 年前。当时人们说，我可以把 RGBA 输出当作流体模拟中的 XYZ 位置，或者诸如此类的数据。

[10:12.910] 所以人们开始进行各种 hack。他们发现：“这些 GPU 真的非常非常快；相比用 C++ 运行多线程代码之类的方法，我们实际上可以快很多。”2004 年，斯坦福有一个研究项目提出：等一下，这只是一种 hack。这实在很蠢。如果我们要把这些东西当作并行处理器使用，而且我们都了解数据并行（data parallelism）以及其他相关概念，那能不能直接提供一个正规的编程系统，把它们当作并行处理器来使用？于是就有了这样一个项目，其中研究人员使用了数据并行编程模型。我们会在周四更详细地讨论这个模型。

[10:56.900] 但它的核心思想是，这里有某个函数，比如这个例子中的 `scale`。它接受 A 和 B 作为输入，并把 A 缩放相应的量。不过，`scale` 的求值对象不是标量值，而是集合。我这里虚构了一些语法。你可以把它想象成一个包含 1,000 个数字的向量，然后对这个集合中的每个元素应用 `scale`。这称为流式编程模型（stream programming model）或数据并行编程模型（data parallel programming model）。这段代码实际上是一个名为 Brook 的语言中的合法代码，它会通过源到源编译，转换成那个绘制两个三角形、然后使用 GPU 的图形程序。

[11:34.720] 同样，对用户来说，这不那么像一种 hack 了；但从实现角度来看，它完全还是一种 hack。大约在这个时期，NVIDIA 正在制造越来越快的处理器。他们开始思考：既然这些东西能够运行代码，也许它们不只能用于图形处理。因此，受到这类项目及其他项目的启发，NVIDIA 说：“这样吧，我们干脆自己来做，让人们可以为这些东西编写通用代码，因为芯片其实已经能够做到这一点了。”如果我们稍微回忆一下 CPU 的工作方式，假设这里有一个多核 CPU，它有两个核心，也就是总共两个执行上下文。你要怎样在这个处理器上运行一些代码？或者换句话说，操作系统会做什么？我们可以实际推演一下。假设你正在上——我们先做个假设，你们中的许多人可能并没有上过——但想象一下，你正在上一门操作系统课程。

[12:35.940] 作为操作系统，你应该——假设我们想在这台双核机器上运行两个不同的程序。你要怎样启动这些程序？如果有两个不同的程序，理想情况下就有两条指令流。所以，我有两个程序。我编译了自己的程序。然后，作为操作系统，如果我想让那个程序运行起来，会发生什么？我要做什么？“嘿，核心，让我初始化一下你的寄存器值。我会把下一条要执行的指令设置为这个程序开头的指令。”然后你只要告诉它开始运行。因此，它会在这里运行这个线程。如果你想运行另一个线程，操作系统可能会说：“我还有来自另一个程序的这个线程。”“我要在零号核心上运行它。这里是你的程序二进制文件，初始化这个线程的状态，然后开始运行。”你每次处理一个线程。如果你上过操作系统课程，就会知道，这正是操作系统所做的事情。这就是我们在 CPU 上运行代码的方式。

[13:44.680] 但在 NVIDIA 说“嘿，我们需要向你们开放访问方式”之前，我们在 GPU 上运行代码的方式并不是“运行一个线程”。你发送给 GPU 的命令实际上是：绘制这些三角形；在确定哪些像素需要着色之后，使用这个程序计算这些像素的颜色。因此，GPU 的接口就是我们所说的图形流水线（graphics pipeline）。它包含 CS 248 中的所有算法，但它面向软件的接口实际上是：软件向 GPU 提供一个三角形列表、一个用于计算表面颜色的程序，以及摄像机的位置，然后流水线就会直接开始运行。每当它需要计算某个像素的颜色时，就会运行那个程序。这是一种非常非常不同的启动计算的思维方式。所以在 2007 年，NVIDIA 说，我们需要一种介于这两种方式之间的东西。为了让处理器执行与图形完全无关的任务，却还要绘制三角形，这看起来很蠢。

[14:45.820] 与此同时，我们也并不真的希望用户创建所有这些不同的线程，因为在我的 GPU 上，这些不同的线程运行起来并不会很好。我的 GPU 具有 32 路 SIMD，单线程性能又很差，诸如此类。因此，他们创建了一种名为计算模式（compute mode）的新抽象，这种抽象一直存在至今。现在，它面向硬件的接口如下：你自己编写一个小程序，比如某个函数 `foo`。在这个例子中，我把它称为 `my kernel`，因为在数据并行的语境下，我们通常把要运行的代码称为核函数（kernel）。然后你说：“我想调用这个核函数的 N 个副本。”

[15:29.580] “GPU 芯片，你自己决定怎样实现。我只是想让这个核函数运行 N 次。”那么，这是什么编程模型？这是经典的单程序多数据（SPMD，Single Program, Multiple Data）编程。我要给你一段代码，其中某处会有一个线程 ID，然后我们启动 N 个副本，并运行这 N 个副本。所以，你可以把它看作一种与 ISPC 类似的编程模型。这个编程模型体现在所谓的 CUDA 编程语言中。在现代 GPU 编程里，CUDA 基本上就是 C、C++，唯一的区别是你不需要创建线程。你只需要说：“这是我的程序，请运行它的 N 个副本。”然后 GPU 会说：“好的，我会自行决定如何并行执行这些副本。”是的？

[16:25.780] 是的。我的意思是，之前的区别在于，你真的会打开 OpenGL，然后对它说：“OpenGL，在这些位置绘制这些三角形。”你还要非常仔细地设置这些位置，确保屏幕上的每个像素都被覆盖。那确实是一种 hack。所以现在，他们就是在说：“让我们使用正规的 SPMD 编程抽象，本质上完成同样的事情。”在你思考这个问题的同时，我希望你想一想：我应该把它看作数据并行（data parallel），还是把它看作 SPMD？这是消息传递（message passing），还是共享地址空间（shared address space）？如果必须在头脑中整理这些概念，你会如何把它与 ISPC 以及你已经了解的一些东西进行类比？

[17:22.630] 今天我们讨论的是 CUDA，所以我会使用 CUDA 的术语来讲解。还记得我讲 ISPC 时说过，有一组程序实例（gang of program instances）吗？从逻辑上说，你会把程序实例看作一个线程，但你知道在底层，其实现并不像一个硬件执行上下文。它其实是一条小小的向量通道（vector lane）。在 CUDA 中，ISPC 里的程序实例称为 CUDA 线程（CUDA thread）。所以，在这节课中，当我说“线程”时，除非我特意明确说的是硬件执行上下文，否则我指的就是 CUDA 线程。而 CUDA 线程就是 NVIDIA 所定义的那种东西。

[18:09.180] 好，我们开始。就像在 ISPC 中一样，当你调用一个 ISPC 函数时，会启动一组程序实例，这组实例的数量是 N。这个数量通常在编译时设定，一般是 8 或类似的数值。而当你调用 ISPC task 时，你表达的是：“我要运行这个函数、运行这段代码，并且需要运行 N 次。”因此，在进行 CUDA 编程时，基本上也会用同样的方式来思考。这里有一个来自普通 C++ 代码的调用，它表示：“我要你运行 CUDA 函数 `matrix add`。”更准确地说，我希望你以这些数组作为输入参数来运行它。A、B 和 C 都只是普通的 C 风格数组。这里唯一有些特别的是这种奇怪的尖括号语法：你不是直接说“我要你运行 N 次”，而是用一个多维数值来指定要创建的实例数量。之所以使用多维形式，只是因为这对图形和张量运算来说比较方便。

[19:17.190] 有时我们可以说“创建 N 个线程”，但将它们组织成一个 4×3 的网格之类的形式会很有帮助。换句话说，线程 ID 将是多维的。另外还有一个细节：这些实例会被组织到线程块（block）中。因此，这段代码所做的是创建大小为 4×3 个线程的线程块，也就是每个块有 12 个线程；而我总共创建了——我创建的块数是 12 除以 4，以及 6 除以 3。换句话说，假设我要对两个大小均为 12×6 的矩阵逐元素相加，并且希望每个 CUDA 线程负责将一个元素相加，那么我需要创建 72 个线程。这里，我没有直接创建 72 个线程，也没有直接说“创建 72 个线程”，而是选择创建若干线程块，每个线程块的大小为 4×3。我现在之所以这样说明，只是希望你先了解线程块这个概念，因为我们之后还会再次用到它。
