# 从上下文窗口到技能库：CMU 11-768 Lecture 4 中的智能体技能与记忆

> 待审核候选稿 · 来源：平台字幕与官方 Slides · 尚未发布。

## 一、一个反复出现的问题：智能体为什么总要"重新学"同一件事

想象一个 GUI 智能体被要求"把 Sony 耳机加入愿望清单"。它需要打开购物网站、找到搜索框、输入关键词、点击搜索、打开某个结果、点击"加入愿望清单"。下一次任务变成"查询无线键盘的价格区间"，它又要打开同一个网站、找到同一个搜索框、输入不同关键词、点击同一个搜索按钮——只是最后几步不同。

Slides 第 2 页把这种结构总结为"共享搜索流程 + 任务专属收尾"：TASK 1 与 TASK 2 共享 `goto store → find search box → fill(...) → click Search`，随后才分叉。这带来 Lecture 4 的核心问题：**智能体如何在不重训模型的前提下，把这类可复用的结构从一次任务迁移到后续任务？**

讲者在开场明确说，上一讲讨论的是"上下文窗口内保留什么"，而本讲的重点是"如何超越上下文窗口，在外部存储中跨任务保存信息"（逐字稿 00:01–00:56）。这就是 Lecture 4 的主线：技能归纳（skill induction）与记忆（memory）。

## 二、三种更新智能体的位置：一张表撑起整讲的框架

Slides 第 3 页给出一个三行表格，几乎是最重要的"路线图"：

| 位置 | 代表方法 | 优点 | 缺点 |
|---|---|---|---|
| 上下文窗口 | 上一讲 | 对发生过的事高保真 | 昂贵、噪声大、不会判断什么重要 |
| 外部产物 | 本讲 | 可检查、可编辑、可检索、可移植 | 必须被归纳、筛选和维护 |
| 模型权重 | 后续 SFT 讲 | 推理更快、行为改变更广 | 更新慢、不透明、模型专属 |

其中"外部产物可移植"这一点讲者特别强调（逐字稿 06:21–06:49）：描述"如何在某网站搜索商品"的文本可以被多个模型共用；而权重更新只对那个特定模型有效，且难以被人检视和修改。这也解释了为什么本讲大量篇幅花在文本技能与代码技能上——它们是人与系统之间的接口。

【学习者解释】这张表之所以关键，是因为它把"agent 如何变强"从单一维度（改权重）变成了三维坐标。Lecture 4 关心的不是"哪种最好"，而是"给定当前任务分布和数据量，应该把经验放在哪一层"。

## 三、经验的三种粒度：Episode、Fact、Skill

Slides 第 4 页将"什么经验值得留下"分为三类：

- **Episode（情节）**：完整轨迹，包含每一步观察和动作。当确切商品、确切价格、确切顺序在未来仍会重现时有用。
- **Fact（事实）**：例如"这家店只在商品页显示价格"。当该事实会在未来反复出现、而且可能被更新时有用。
- **Skill（技能）**：例如"填入搜索框 → 点击搜索 → 打开结果"。当后续任务会重复同一模式时有用。

讲者在逐字稿 09:10–11:35 的对应讨论里补充了两点：Episode 保真度最高但 token 最贵；Fact 类记忆是早期记忆系统（例如 ChatGPT、Anthropic 的记忆设置界面）的主要形态，本质是"从交互中由 LLM 生成的一段文本，被存在外部"。

Slides 第 5 页进一步区分了 Memory 与 Skill：**Memory 是从智能体自身交互中保存下来的内容**（比如上次买过的商品），**Skill 是"如何行动"的可复用知识**，可以是代码、文本或两者。这两者会交叉——"agent 从自己成功的搜索里归纳出的技能"就是交叉点。

【学习者解释】把经验拆成这三类，实际是在回答一个工程问题：**你希望未来的智能体在多大程度上"记起具体细节"，又在多大程度上"学会方法"？** 前者容易过拟合到某个站点某次版本，后者容易抽象过头而失效。这组张力贯穿整讲。

## 四、人来写技能：Agent Skills 的标准结构与渐进式披露

### 4.1 什么时候应该写技能

Slides 第 8 页给出一个很具体的判定："当你想要反复做同一件遵循固定规范的事"——例如加测试、审 PR、升级依赖。页面上展示的反例是一段每次都粘贴到 PR 对话里的指令：Black 88 字符、Ruff 自定义规则、公共 API 类型注解、Google 风格 docstring、新函数用 Pytest。

【学习者解释】这个例子的说服力在于：它**先给出"笨办法"**——每次都手打一遍。技能的价值不是让模型变聪明，而是把"固定规范"从重复劳动变成一份可维护的产物。

### 4.2 三层的目录结构与 YAML 头部

Slides 第 9 页展示了一个 Python review 技能的目录：

```
python-review/
├── SKILL.md          # 必需：指令 + 元数据
├── scripts/          # 可选：可执行代码
├── references/       # 可选：文档
└── assets/           # 可选：模板、资源
```

`SKILL.md` 是必需文件，开头是 YAML 元数据，包括 `name`、`description`、`triggers` 等。讲者在 15:31–17:28 补充：`description` 的作用是"告诉语言模型什么时候应用这个技能"，因此必须简洁；`references/` 是补充文档，agent 按需加载；`assets/` 存放模板等资源。

### 4.3 渐进式披露：三层按需加载

Slides 第 9 页表格把加载分为三层：

1. **层 1**：`SKILL.md` 的 YAML 元数据——始终加载。
2. **层 2**：`SKILL.md` 正文（Markdown）——当 agent 触发该技能时加载。
3. **层 3**：打包文件（文本、脚本、数据）——当 agent 主动去读时加载。

Slides 第 10 页展示 Hermes Agent 的系统提示词片段，里面有一份 `<available_skills>` 索引，只列出技能名与描述。Slides 第 11 页把一次典型交互拆成四步：

1. 系统提示词含技能索引（Hermes 中约 3k token）；
2. `skill_view('python-review')` 返回 `SKILL.md` 正文；
3. `python scripts/run_checks.py src/` 只把脚本输出放进上下文，被检查的代码本身不进入；
4. 需要时再 `skill_view('python-review', 'references/docstring-style.md')`。

讲者在 18:41–19:36 明确说明："你们会在作业一中实现这个"——这是课程与 Slides 第 11 页的直接对应。

【学习者解释】渐进式披露是技能系统里最容易被低估的设计。它的真正含义是：**技能不是"一段长的系统提示"，而是一份可被模型主动检索的文档索引**。因此"技能写得好不好"不仅是文本质量问题，也是"模型能不能判断何时该打开它"的检索问题。这也直接引出讲者在 19:36 之后的提醒：技能越多，元数据总量越大，性能会受影响。

## 五、SkillsBench：人类写技能到底有多大用？

Slides 第 12 页介绍了 SkillsBench：**8 个领域、87 个真实工作任务**，人工为每个任务挑选技能包，主实验在 **18 个模型-框架组合 × 87 个任务**上对比"无技能 vs 精选技能"。

Slides 第 13 页给出几个关键结果：
- 平均通过率从 **33.9% 提升到 50.5%**；
- 任务仅配 1–3 个技能时增益更大，≥4 个技能时增益更小；`SKILL.md` 更短的一组增益也更大；
- **87 个任务中有 13 个，技能反而使性能下降**——技能可能"挤掉更好的默认策略"。

【学习者解释】最后一行的意义常被忽视。它说明技能不是纯收益，而是一种**注意力与行为的重分配**：一旦模型开始遵循某份技能，"更好的默认策略"反而被压制。这与讲者 07:59 之后现场提问得到的学生反馈一致：模型常会"过度推断"，把技能写得比实际需要更宽。

## 六、技能的来源与维护

Slides 第 14 页列出三种来源：随框架捆绑、人工安装或写入（常放在 `.agents/skills/`）、由 agent 自己创建（Hermes 有 `skill_manage`，OpenHands 有 `/skill-creator`）。页面上的 OpenHands 建议是："**不要从零写技能**，在 agent 刚完成一个你想重复的工作流之后立刻创建，然后测几次"。

Slides 第 15 页给出一个具体案例：OpenHands 在自己的仓库里对每个 PR 跑 `python-review` 类技能，然后：
- 用模型判断"人类保留了多少建议"来评估；
- 让模型分析失败模式，识别出"忽略仓库约定（约 15%）"和"批准了含严重缺陷的 PR（约 10%）"；
- 据此更新 `SKILL.md`：发现严重问题时一律要求改动，发建议前先对照仓库。

这一部分的"数值"来自 Slides 第 15 页原文，属于课程材料中的例子，而非本讲新做的实验。

## 七、从"人工写"转向"自动归纳"：记忆的四条基础线索

进入归纳技能之前，讲者先交代了几类外部记忆的基础工作：

- **MemGPT（Slides 第 17 页）**：把读写记忆变成 agent 自己发起的函数调用，把"工作上下文"和"外部事实存储"分层。
- **Mem0（Slides 第 18 页）**：处理记忆冲突，操作分四类——ADD / UPDATE / DELETE / NOOP（无相关就丢弃）。
- **Reflexion（Slides 第 19 页）**：把"对轨迹的自然语言反馈"作为下一次尝试的条件。页面上的例子是：第一次回答"Battle of White Plains"被判错，反馈说"问题问的是一系列战役，我只给出了一场"，第二次改为"The New York and New Jersey campaign"即正确。
- **相似轨迹条件化（Slides 第 20 页）**：把整条轨迹（成功和失败都算）存进经验池，用文本 embedding 检索出与新任务最相似的几条，作为少样本示例。

讲者在 37:18–38:47 现场引导学生回忆上一讲的"Delta"方法，把"文本级事实更新"与"线性注意力中的键值更新"类比对——【学习者解释】这个类比是"记忆在符号层和向量层是同构问题"的一个直观入口。

## 八、把技能当作任务中的可复用块

Slides 第 22 页把"搜索商品"这个子任务抽象成：

```
# To find {query}, I will type it into the store's search box and submit.
fill('element145', {query})
click('element147')
```

同一段动作在"报告价格区间"任务里又被复用，然后追加报告步骤。Slides 第 23 页把这条线追到更早的工作：Voyager（Minecraft 里逐层制造函数）、DreamCoder（压缩程序语料归纳函数）、Stitch、LAPS、LILO——它们共同构成"技能归纳/程序归纳"的前史。

Slides 第 24 页给出评估设定：任务按顺序到达，**某个成功任务更新记忆，然后影响之后的任务**，最终衡量"累计成功率"。Slides 第 25 页将这一生命周期抽象为三段：**LEARN（判断→归纳→准入→入记忆）→ USE（检索→行动→产出）→ MAINTAIN（新增→修复→淘汰→回记忆）**。

## 九、文本技能与代码技能：本讲的核心对比

### 9.1 文本+动作示例（AWM）

Slides 第 26 页展示 Agent Workflow Memory（AWM）的流程：NL 查询 + 动作轨迹 → 判定器判断最终状态是否正确 → 少量样本提示 LM 归纳 → 得到"任务描述 + 模板化动作序列"。Slides 第 27 页给出归纳提示词原文，其中值得注意的要求包括：**每个工作流至少两步**、**不要生成相似或重叠的工作流**、**用描述性变量名表示非固定元素**。

Slides 第 28 页展示跨任务记忆复合带来的收益：随着任务流推进，带子任务记忆的 agent 解决问题数量显著高于无记忆基线，并能执行更复杂的任务。

### 9.2 代码技能（ASI）

Slides 第 29 页做了一个清晰对比：

- **文本 + 示例**：灵活（模型可解释、可适配当前页面），但每个底层动作仍需模型自己发出；
- **代码**：可用作工具、可测试、可分层（技能调用技能）、高效（一次调用取代许多模型步骤），但**僵化**——"即使页面已经变了，它仍会照字面执行"。

Slides 第 30 页展示 ASI 的代码技能归纳：从同一条轨迹里生成 `search_reviews` 与 `open_marketing_reviews` 两个函数，并给出用函数重写的轨迹。Slides 第 31 页给出"代码技能可被单独测试"的例子：SkillWeaver 中归纳出的 `identify_pill` 函数定义了 `color` 参数却从未使用它，被 linter 抓到后补上实现。

### 9.3 效率与成功率的量化

Slides 第 32 页给出一个直观对比：同一任务在无记忆情况下 50 步触顶，代码技能下 4 步完成。Slides 第 33 页在五个 WebArena 站点上取平均：

- **checkpoints reached**：无记忆 41.3、文本技能 59.5、代码技能 80.2；
- **steps per task**：24.5 → 20.6 → 15.0。

（这些数值来自 Slides 第 33 页原文，属于课程对该论文的引用，本讲没有新增实验。）

### 9.4 泛化问题与 PolySkill

Slides 第 34 页给出失败案例：在一个站点归纳的 `sort_listings`（点击下拉菜单）到 Target 上失效，因为 Target 的排序展开的是一个侧边栏。Slides 第 35 页给出 PolySkill 的应对方案：**抽象类 + 每个网站的具体实现**——组合逻辑写一次，网站只实现底层浏览器动作。这同时也是"同一时间只有一小部分技能是活跃的"的机制。

Slides 第 36 页总结三种表示的强弱点：检索到的 episode 保真但难迁移；文本技能提供灵活指导但不提升效率；代码技能可执行、可组合、高效但可能脆弱。

【学习者解释】第 36 页最后一句话"**多少行为留给模型，多少固定在产物里**"，是整讲的元问题。文本技能把决定权留给模型但牺牲效率；代码技能把决定权固定下来但牺牲鲁棒性。PolySkill 之类的方案本质上是在这两端之间寻找一个可维护的中间层。

## 十、从失败中学习、过度检索与记忆合并

Slides 第 38 页给出 ReasoningBank 的一个案例：查询"列出 Sony 蓝牙耳机的完整名称和价格区间"返回 5,578 条结果、每页 12 条，agent 一路翻页直到触顶失败。归纳出的策略是"收紧查询"、"提高每页显示数"、"使用筛选器"。Slides 第 39 页给出一个反直觉的结论：**失败经验对"策略归纳"很有帮助，但对"轨迹型/工作流型记忆"帮助较小**——后者本质上是把"不该做什么"作为示例，效果有限。

Slides 第 40 页讨论"判定器准确率有多重要"：他们用真实标签加固定概率翻转来模拟不同质量的判定器，结论是**性能依赖判定器质量，但在相当宽的准确率范围内，记忆仍然带来改进**。

Slides 第 41 页给出过度检索的代价：**检索更多经验反而会使性能下降**，SkillsBench 对人类精选技能也观察到同样现象。原因可能是经验本身不相关，也可能是模型无法区分哪些上下文真正相关。

Slides 第 42 页给出记忆合并的机制：TroVE 会丢弃使用频率低于 ½·log₁₀(n) 次（n 是迄今见过的样本数）的函数；并提示"**并非所有技能都帮忙**——对某类任务有用的技能可能对另一类有害"。

## 十一、训练"技能归纳器"本身

Slides 第 43 页是本讲的前沿部分：把技能归纳过程直接放进 RL 训练。关键洞察是：**任务 1 的奖励只说明任务 1 成功，并不能说明"保存这个技能"是否值得——只有后续任务才能证明。** 所以把两个相关任务放进同一次 rollout（SAGE）或一条长轨迹（AgeMem）里训练。页面上给出的对照是（AppWorld test-normal，Qwen2.5-32B）：

- 仅结果奖励：55.4
- 两个任务都成功：56.6
- 成功复用技能：60.7

Slides 第 45 页给出一张"谁来做决策"的对照表：技能/策略已知时人工更划算，需要从交互中发现时 agent 更划算；正确性规范或高风险时人工更划算，结果可执行且测试便宜时 agent 更划算。
