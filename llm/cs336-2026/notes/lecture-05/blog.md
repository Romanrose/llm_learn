# GPU 与 TPU：从硬件心智模型到 FlashAttention 的系统之旅

> CS336 Language Modeling from Scratch 第五讲深入探讨了 GPU 和 TPU 的硬件架构、性能优化技巧，以及如何将这些知识整合起来理解 FlashAttention。本文基于课程逐字稿整理，带你建立从硬件到算法的完整认知链条。

## 引言：当魔法遇见工程

深度学习模型常常被形容为“魔法”，但 GPU 同样如此——尤其是当你第一次接触它的时候。一张展示矩阵乘法吞吐量随矩阵维度变化的图表可能看起来令人困惑：为什么在某些特定规模下，性能会突然暴跌？为什么增加一个维度会导致吞吐量显著下降？这些“魔法”背后其实都有清晰的工程原理。

在 CS336 的学习路径中，前两讲专注于神经网络本身的理论基础。而本讲标志着课程进入系统部分——这是整个技术栈中最容易理解的部分之一，因为你可以推理所有的组成部分，并有合乎逻辑的步骤引导你得到结果。但正如课程讲师所说：“当你第一次接触 GPU 时，感觉可能会有点像在跟一个既神奇又非常奇怪的设备打交道。”

理解硬件不是系统方向研究者的专利。即使你只关注架构设计或一般性地推理这些事，也需要理解模型将如何在硬件上执行，才能设计出有效的模型。正如 Percy 在第一讲中提到的，扩展的一个关键部分就是确保你有效地利用资源——不理解你的系统，你就永远无法高效地使用资源。

## 从 CPU 到 GPU：设计哲学的转变

### 为什么频率提升不再有效

回顾计算历史，大约在 2000 年代之前，让计算机变快的主要方式是提高时钟速度——晶体管变小，时钟速度变快，这种被称为“丹纳德缩放”的规律在一段时间内表现良好。但随后这种扩展方式达到了极限：晶体管变小的速度仍在持续，但让晶体管变小并不一定意味着运行得更快，其中有根本的物理原因。

那么，在这个无法单纯通过频率提升来加速的世界里，我们如何让大语言模型继续扩展呢？答案是并行性。这不仅是 GPU 的故事，也是并行计算范式的核心：不再通过让时钟越来越快来串行地加速事情，而是横向扩展，让更多的东西并行地执行指令。

### GPU 的硬件心智模型

CPU 是为快速、串行执行而设计的，适用于有复杂分支逻辑和控制流的场景。它拥有非常大的控制单元，但只有少数几个 ALU（算术逻辑单元）。它的设计目标是低延迟——从收到指令到完成指令之间的时间应该非常短。

GPU 则完全不同。它更看重吞吐量——也许单个任务完成得并不快，但所有任务的总吞吐量非常大。实现这一点的关键在于拥有海量、轻量级的核心。GPU 拥有成百上千个计算单元，集成在一个芯片上，可以并行执行。

在 GPU 中，基本单元是 **SM（Streaming Multiprocessor，流式多处理器）** 。每个 SM 都不是一个单一的计算单元——它内部包含流处理器（Stream Processor），这些流处理器可以并行地执行不同的线程。一个 A100 有 128 个 SM，每个 SM 都可以独立编程并执行不同的任务。

但 GPU 的故事中非常重要的部分不仅仅是计算部分，还有内存部分。现代硬件和 LLM 优化实际上是由内存来定义的。

### 内存层次结构：速度与容量的权衡

GPU 中有不同级别的缓存和内存：

- **寄存器（Registers）** ：容量最小但速度最快
- **L1 缓存和共享内存（Shared Memory）** ：非常快，大约 20-30 个周期即可读取
- **L2 缓存**：速度慢得多
- **全局内存（Global Memory）或高带宽内存（HBM）** ：比 L1 缓存慢约 10 倍

当 H200 宣称“我有 144 GB 内存”时，它指的是全局内存。物理上，全局内存是位于计算单元之外的内存芯片，而 L2 和 L1 缓存位于芯片本身内部——这就是为什么它们的延迟要好得多。

你可能会问：既然共享内存这么好，为什么不把整个芯片都做成共享内存呢？答案是成本：贵几百倍，而且更耗电。你需要这种内存层次结构，并有效地利用它。

需要注意的是，共享内存和 L1 缓存虽然物理上接近，但工作方式不同。L1 缓存是自动运行的，用于存储最近访问的数据元素；而共享内存是可编程的——你实际上会与它交互，可以往里面放东西，也可以从里面取东西。

## GPU 的编程模型：线程、Block 和 Warp

GPU 的执行模型中有三个重要的角色：

**线程（Thread）** 遵循 **SIMT（Single Instruction, Multiple Threads，单指令多线程）** 模型——所有线程执行完全相同的指令，但可以有不同的输入。这对代码效率有重要影响：如果线程可以做各种各样不同的事情，编程就会变得非常困难。GPU 实际上是在可编程性和效率之间的一种权衡。

**Block（线程块）** 是一组线程，保证在单个 SM 上运行。Block 可以访问一个共享的内存池，这在我们讨论 tiling（分块）时变得非常重要。

**Warp（线程束）** 是 GPU 内部运行时的调度单元，由 32 个连续编号的线程组成。这减少了调度器决定运行哪些线程的开销。

### 控制发散：if 语句的代价

由于 SIMT 模型的限制，在 GPU 代码中写 if 语句会有意想不到的代价。每个线程必须执行相同的指令，所以实际上每个线程都会执行 if 和 else 两个分支——但如果你不属于某个分支，你只会屏蔽掉那个计算，处于闲置状态。这被称为**控制发散（Control Divergence）** 。

这就是为什么 GPU 代码中实现 ReLU 时，你通常会看到在乘以零或者乘以掩码，而不是写一个只更新一半的 if 语句——因为乘法是同时全部进行的，而 if 语句可能需要等待两个时钟周期来执行两个分支。

## TPU：趋同进化的另一种路径

TPU 在高层次上与 GPU 非常相似——这有点像是趋同进化：如果你想构建一个能效高的机器学习加速器，你最终会到达同样的设计方向。

TPU 更加针对机器学习工作负载进行了优化，有更轻量级的控制单元和更大的矩阵乘法单元。它们的内存结构与 GPU 非常相似：包含慢速的**高带宽内存（HBM）** 和一个更快的本地内存称为 **SMEM（共享内存）** 。

真正有趣的是，GPU 中的每个概念在 TPU 中都有一个对应的概念。GPU 中的张量核心（矩阵乘法单元）几乎与 TPU 中的 **MXU（Matrix Multiply Unit）** 完全对应——它们实际上使用相同的底层电路，都是所谓的**脉动阵列（Systolic Array）** ，通过流式输入输出来执行矩阵乘法。

但有一个令人困惑的命名问题：TPU 称它们的流式多处理器为“张量核心”，而 GPU 称它们的矩阵乘法单元为“张量核心”。如果你听到“TPU 的张量核心”，那指的是处理器；如果听到“GPU 的张量核心”，指的是矩阵乘法单元。

设计上的主要区别在于规模与数量的权衡：一个 A100 可能有约 128 个 SM 和 528 个矩阵乘法单元，而一个 TPU 只有 2 个处理器和 8 个矩阵乘法单元，但每个单元规模更大。这给了 GPU 更多灵活性——可以编程让它们做不同的事情——而 TPU 则被锁定在做大型矩阵乘法上。课程中提到了一个实际例子：在做批次大小扫描时，批次大小降到 64 就停止了，因为 TPU 的张量核心拒绝接受任何小于 64 维输入的矩阵乘法。

## 为什么矩阵乘法是特权操作

从 V100 开始，NVIDIA 决定在硬件中直接加入矩阵乘法单元（张量核心）。一旦那个硬件存在了，矩阵乘法就成为机器学习中一个享有特权的操作：在可并行化但非矩阵乘法的操作与矩阵乘法能完成的操作量之间，存在巨大的吞吐量差距（超过 10 倍）。这就是为什么任何能随计算规模扩展的机器学习架构都必然包含矩阵乘法——这是你能够真正有效获得大量计算吞吐量的唯一方式。

## 计算的戏剧性变化：不同组件的非同步扩展

GPU 的不同组件随着时间以不同的速度扩展。总体的计算吞吐量（灰色线）增长最快；内存带宽（绿色线）是数据传输速度，增长相对缓慢；并行性（蓝色线）是连接不同 GPU 设备的速度，也增长得非常慢。

这意味着什么？在 GPU 编程的早期阶段，你可能不会太多考虑内存问题，因为计算速度不比内存传输快多少。但如今，计算和内存之间的差距越来越大——这就是为什么本讲要讨论的很多优化都是内存优化。

## 六个关键技巧：让 GPU 跑得更快

### 技巧一：低精度计算

算力扩展中相当重要的一部分来自数字表示的精简。从 FP32 到 BF16 再到 INT8，你一直在降低数字精度。少了一半的比特，移动的比特也就少了一半，内存移动量就减少了。

一个简单的例子：在大小为 n 的向量上做 ReLU，如果用 FP32，读取需要 4 字节，写入需要 4 字节，总共 8 字节内存访问，却只有 1 个 FLOP 的工作量——8 字节每 FLOP。降低精度直接减半了这个比例。

但低精度在实际中如何工作？当你做矩阵乘法时，你会在取乘积之前进行降精度转换，而在累加部分和时以全精度进行累加。真正让低精度训练成熟的关键在于弄清楚哪些操作需要使用哪种数字格式：矩阵乘法中的权重和激活可以低精度，但 softmax 可能需要 FP32。

FP8 是低精度领域的下一个前沿。一旦到了 FP8，不再有一个“标准”格式——有 **E4M3**（4 位指数、3 位尾数）和 **E5M2**（更多指数位、更少尾数位）等不同选择。

更先进的 **MXFP8** 格式使用多个缩放因子：矩阵中的每 32 个元素对应一个缩放因子。这带来了一个有趣的问题：矩阵转置变得非常复杂，因为需要重新量化。实践中，训练时会为每个量化矩阵创建两份拷贝——一份给原始矩阵，一份给转置矩阵。这就是绕过问题的方式。

### 技巧二：算子融合（Operator Fusion）

想象 GPU 是一个工厂：内存仓库、小型计算工厂、传送带在来回运送东西。如果有许多不同的操作需要顺序执行，就要反复运送中间数据，产生大量内存瓶颈。如果只有一个巨大的工厂，能接收所有原材料然后输出成品，就只需要为内存带宽付两次费用。

这就是算子融合。一个简单的例子：计算 sin² + cos²。朴素实现中每个操作（sin、cos、平方、加法）都相当于一个工厂，每次调用都从全局内存读写数据。融合后的单个 GPU 内核只从全局内存读取一次，在 SM 内部完成所有操作后写回一次。

编译器（如 Torch Compiler 或 JAX Compiler）可以自动完成这类基础操作的融合。高级版本的融合有时需要手动干预。

### 技巧三：重计算（Recomputation）

通常在反向传播中，我们向前传播时保存激活值，然后在反向传播时使用这些激活值。但如果我们扔掉所有激活值，在反向传播时重新计算它们呢？

想象一个由三个 sigmoid 组成的简单计算图。朴素实现需要读取 x 一次，写入 S2、S1、out 三次，然后反向传播再读取三次、写入一次——总共八次内存访问。如果丢弃所有中间激活值，只存储最终输出，反向传播时临时重新正向传播并即时计算激活值，那么只需要两次内存读取和一次写入——总共五次内存访问。

用额外的计算换取更少的内存访问。在计算资源充裕但内存昂贵的情况下，这是很有价值的技巧。

### 技巧四：合并内存访问（Coalesced Memory Access）

全局内存是 DRAM，由于结构原因以突发（burst）模式工作。访问某个位置时，同一突发段（burst section）内的其他位置也可以免费读取。这意味着，如果读取是连续排列的、彼此紧挨着，速度会快得多。

对于行主序（row major）的矩阵，如果线程试图在每个时钟周期读取每一列，每个元素都会落在不同的突发窗口内——非常低效。但如果翻转过来读取行，每个线程都可以在一次内存读取中获得需要的数据。

这就解释了为什么矩阵的大小和排列方式如此重要。理解这一点，你就能明白为什么 Karpathy 的 nanoGPT 在把词汇表大小从 50,257 增加到 50,304 时会获得 25% 的加速——因为填充（padding）可以让突发传输段的边界与分块大小对齐。

### 技巧五：分块（Tiling）

这是最重要的一个技巧。核心思想是：利用内存层次结构，尽可能多地完成工作。把你需要的东西切分成块（tile），每个块加载到共享内存中，一旦加载完成就反复从该块读取，尽可能多地做计算。

在朴素的 N×N 矩阵乘法中，每个输入元素会被从全局内存读取 N 次。使用大小为 T 的分块后，每个输入元素只需从全局内存读取 N/T 次，然后在共享内存中被访问 T 次。全局内存访问量减少了 T 倍。

但分块也有微妙的问题。想象一个 128×128 的分块，如果矩阵是 256×256，一切完美——四个分块完美切割。但如果矩阵增加 1 个维度，就会产生两个非常细长的、几乎什么都没有的分块。分块大小的选择非常复杂，需要优化。

PyTorch 的 max-autotune 编译器选项就是干这个的：尝试所有不同的分块大小应用到你的矩阵上，找出哪个实际上更快。

### 技巧六：处理波次量化（Wave Quantization）

回到那个神秘的性能下降图表。为什么从 1792 到 1793，矩阵乘法吞吐量会暴跌？

使用 256×128 的块大小，1792 时有 98 个块。但 1793 时，两个维度上的块数都增加了一个，变成 120 个块。A100 有 108 个 SM——98 个块可以放进去，但 120 个块放不进去。处理完 108 个 SM 的活儿后，还剩 12 个块要处理，而此时大部分 GPU 都空闲着。仅仅因为你把块的大小增加了一，就需要再等一整轮循环来处理新一批块——这就是波次量化。

## 整合：FlashAttention

现在我们有了理解 FlashAttention 的所有元素。FlashAttention 是注意力机制方面的一大改进，而且完全是系统层面的改进——它把 PyTorch 简单的注意力实现变成了一个单一的、非常巧妙融合的内核。

注意力计算包含几个部分：Q、K、V 三个矩阵乘法和中间的一个 softmax。矩阵乘法我们知道怎么做——分块矩阵乘法。但 FlashAttention 的棘手之处在于 softmax 是全局操作，把所有元素都联系在一起。

关键技巧在于**在线计算 softmax（Online Softmax）** ：你一边计算一边计算归一化的 softmax。每次遇到一个比以前见过的更大的数字，就交换出最大值并修正之前的结果。除此之外，就是对之前所有内容进行在线的、累积的指数求和。因为 softmax 可以在线地、逐块地计算，我们就可以一个块一个块地处理注意力计算，而无需看到其余的分块。

FlashAttention 还包含重新计算的部分：不保存 N×N 大小的注意力激活值，而是在反向传播时逐个分块重新计算。

正如论文所述，他们只做了两件事：应用了分块和重计算，以在内存访问次数上达到次二次级别。

## 结语：为什么硬件理解至关重要

理解硬件，也就是 GPU，是支撑规模和算力的基础。不透彻理解到最底层的细节，就无法完全掌握为什么我们会做出某些决策。课程讲师强调：“我不希望你们成为那种机械照搬、盲目给矩阵配 32 个乘法器的人。我希望你们真正理解我们为什么这样做。”

当前算力增长的方式意味着我们需要思考矩阵乘法——这些是算术密度非常高的核心操作。由于计算与内存之间的差距，我们需要非常仔细地考虑数据移动。像 FlashAttention 这样的东西，以及一些非常硬件感知的架构工作，在做架构设计时，仔细考虑硬件对未来系统获得良好性能至关重要。

本讲在课程中的位置很特殊：它从神经网络的理论基础转向了系统实现，为后续的并行化、扩展和推理优化打下基础。Percy 的下一讲将涵盖并行化的更高级主题，但 GPU 的底层理解是所有上层优化的根基。理解这张图是什么、为什么看起来是那样的——每一处奇怪的凹陷和隆起背后，都是内存层次结构、分块策略和硬件特性的具体体现。
