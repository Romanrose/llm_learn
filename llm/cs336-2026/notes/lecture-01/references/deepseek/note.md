## 课程主线

### 为什么开设这门课？

**问题**：研究人员正在与底层技术脱节。

- 2016 年：研究者自己实现并训练模型。
- 2018 年：下载 BERT 等预训练模型进行微调。
- 今天：通过 API 提示（prompt）模型。

提升抽象层次本身是好事，但抽象是有漏洞的（leaky）。当你需要做基础研究时，仅仅通过提示模型会极大限制你探索的设计空间。**完整理解语言模型工作原理，是进行基础研究的必要前提。**

**课程哲学**：通过构建来理解（understanding via building）。但有一个现实约束——前沿模型的工业化：

- GPT-4（2023）据称训练成本达 1 亿美元；2025 年 xAI 构建 23 万 GPU 集群训练 Grok。
- 前沿模型不公开构建细节（GPT-4 技术报告明确声明不分享）。
- 我们可以构建小模型（<1B 参数），但小模型可能不代表前沿模型。

**两个例子说明小规模与大规模的差异**：

1. **FLOPs 分布随规模变化**：MLP 层在小规模时约占 44% FLOPs，在 175B 规模时上升到 80%。在小规模优化的注意力机制，在大规模可能没有同等收益。
2. **涌现行为**：某些能力只在达到临界规模后才出现。

### 什么知识可以迁移？

将知识分为三类：

| 类型 | 定义 | 能否跨规模迁移 |
|------|------|----------------|
| **机制（Mechanics）** | 事物如何运作：Transformer 是什么、模型并行如何工作 | ✅ 可以教授 |
| **思维方式（Mindset）** | 如何从硬件榨取最大价值、认真对待扩展 | ✅ 可以教授 |
| **直觉（Intuitions）** | 哪些数据/建模决策带来好性能 | ⚠️ 不完全可迁移 |

关于直觉，一个经典例子：Noam Shazeer 引入 SwiGLU 激活函数的论文，结论最后一句话是"我们不提供任何解释……归因于神圣的恩赐"。**有些设计决策纯粹来自实验经验，无法理性解释。**

### 苦涩的教训（The Bitter Lesson）

**常见误解**：规模就是一切，算法不重要。
**正确理解**：**能够扩展的算法**才是重要的。

核心公式：

```
模型精度 ≈ 效率 × 资源
```

其中，效率 = 产出/投入，资源 = 投入。

**效率在更大规模下反而更重要**：小规模实验运行时间翻倍，多等一等即可；大规模训练是数亿美元的投入，5% 的改进都是大事。实证数据：OpenAI 2020 年论文显示，2012–2019 年 ImageNet 上有 44 倍算法效率提升。

**课程框架问题**：在给定数据和计算预算下，能构建的最佳模型是什么？预训练阶段通常假设计算受限（数据多于计算能力），因此核心任务是**最大化效率**。

## 语言模型发展简史

### 前神经时代
- **香农（1950s）**：用语言模型测量英语熵。
- **N-gram 模型**：长期用于机器翻译和语音识别系统。

### 神经组件（2010s）
- LSTM（1997）
- 第一个神经语言模型：Yoshua Bengio（2003），前馈网络，只看小段上下文。
- Seq2Seq 建模：将整个句子压缩成向量。
- 注意力机制：为机器翻译开发。
- Transformer 架构：建立在注意力之上，同样为机器翻译设计。
- 混合专家（MoE）并行化、Adam 优化器、模型并行。

### 早期基础模型（2010 年代末）
- **ELMo**、**BERT**：在大量文本上预训练，微调后大幅提升下游任务。
- **T5（11B）**：将所有任务统一为 text-to-text。

### 拥抱扩展
- **GPT-2（1.5B）**：流畅文本，首次出现 zero-shot 迹象。
- **Scaling Laws**：为扩展提供可预测性。
- **GPT-3（175B）**：上下文学习（in-context learning），几乎是当时最大模型的 10 倍以上。
- **PaLM（540B）**：大规模但欠训练。
- **Chinchilla（70B）**：计算最优扩展定律，同一时期 DeepMind 已搞清最优计算扩展。

### 开放模型生态
- **早期复现尝试**：EleutherAI（开放数据集 The Pile + GPT-J）、Meta OPT（175B，硬件问题多）、HuggingFace BigScience BLOOM（176B）。
- **开放权重（weights + paper）**：Llama 系列、Mistral、DeepSeek、Qwen、Kimi、GLM、Minimax、小米 MIMO。已接近闭源模型水平。
- **完全开源（weights + paper + code + data）**：AI2 的 OLMo、NVIDIA Nemotron、**Marin 项目**（Percy 参与）。

**为什么强调开放生态？** 没有这些模型，这门课不可能存在——正是开放论文让我们能窥见前沿模型如何构建。

### 语言模型的概念演变

```
2018 (BERT) → 需要微调
2020 (GPT-3) → 可以提示（prompt）
2022 (ChatGPT) → 可以对话
2026 (agents) → 可以自主行动
```

**核心判断**：基本原理没变（GPU + kernel、梯度优化、Transformer + attention），变化的是规格——**更长的上下文长度，推理效率变得更重要**。

## 五个单元概览

### 1. 基础（对应作业 1）
**目标**：从头构建并训练一个语言模型。

**Tokenization**：模型操作的原子单位是什么？在字节和整数序列间转换。BPE 将输入拆分成高频块。效率视角：压缩长序列（1000 字节 → ~250 token），且允许**自适应计算**——某些部分压缩成一个 token，稀有部分保留多个 token。

**为什么还要教 tokenization？** 理想方案是端到端直接操作字节（ByteNet、Megabyte、BLT 等已在探索），但尚未扩展到前沿模型，前沿模型仍在使用 tokenizer。

**模型架构**：
- 起点：原始 Transformer。
- 演进方向：激活函数（ReLU → SwiGLU）、位置编码（sinusoidal → RoPE）、归一化（LayerNorm → RMSNorm、QK-norm、pre/post-norm）、注意力变体（稀疏注意力、GQA、MLA）、状态空间模型（Mamba、Gated DeltaNet）、MoE、模型形状。
- **关键认识**：模型形状（层数、头数、隐藏维度、专家数）看似只是超参数，但对扩展和性能有巨大影响。

**训练**：
- 损失函数：下一个 token 预测是默认；多 token 预测（MTP）有改进效果。
- 优化器：AdamW 为主流，Muon 新兴（Kimi K2 使用）。
- 初始化、学习率调度（cosine、WSD）、正则化、批大小、MoE 特有负载均衡。
- **核心原则**：这些"超参数"以原则性方式设置，将决定训练是崩溃还是达到 SOTA。

**作业 1 内容**：实现 BPE tokenizer、Transformer、损失函数、优化器、训练循环；资源核算（FLOPs 花在哪里）；在 TinyStories 和 OpenWebText 上训练；排行榜目标：给定 45 分钟 B200 算力最小化困惑度。

**高层原则**：一切围绕平衡三个方面：
- **表达力**：能表示数据复杂性。
- **稳定性**：参数范数和梯度范数保持在"金发姑娘区"（不爆炸不消失）。
- **效率**：在硬件上运行快。

### 2. 系统（对应作业 2）
**目标**：最大化硬件利用率。

**资源核算**：追踪 FLOPs 和内存去向。核心公式：训练 1T token 的模型需要约 `6 × 模型参数量 × 数据量` FLOPs。

**硬件约束**：内存与计算单元分离，参数/激活值必须在 HBM 和 SM 之间移动，这往往成为瓶颈。例：B200 在 bf16 下 2.25 PFLOP/s 计算速度、8TB/s 内存带宽。**Roofline 分析**：判断计算是受计算限制还是内存限制——通常后者。

**内核（Kernels）**：
- 内核就是 GPU 上运行的函数；PyTorch 每个原语都对应启动预设内核。
- **核心原则：最小化数据移动**。算子融合（fused）：读取一次数据，完成多个计算，写回一次。
- 相关概念：tiling（FlashAttention）、warp divergence、memory coalescing、occupancy。
- 工具：CUDA、Triton、CUTLASS、ThunderKittens。

**并行（Parallelism）**：上千 GPU 时，GPU 间数据移动更昂贵。
- 基础操作：gather、reduce、all-reduce。
- 分片方式：数据、张量、流水线、序列、专家并行，各有权衡。

**推理**：
- 两个阶段：**prefill**（类似训练，可并行处理，计算受限）和 **decode**（逐个生成，内存受限）。
- 加速方法：剪枝、量化、蒸馏、**推测解码**（draft 模型生成候选 token，完整模型并行验证，可精确解码）、系统优化（fused kernels、continuous batching）。

**作业 2 内容**：Triton 实现 fused RMSNorm kernel、分布式数据并行、优化器状态分片、基准测试与性能分析。

**推荐读物**：《How to Scale Your Model》（Google 出品，讲 TPU 但高层概念相似，新增了 GPU 章节）。

### 3. 扩展定律（对应作业 3）
**场景**：如果有 1e25 FLOPs（数千万美元算力），该用什么超参数训练？一次训练失败损失巨大，且无法在大规模做超参调优。

**关键思维转变**：训练配方（scaling recipe）= FLOPs 预算 → 超参数的映射。方法：
1. 小规模实验（≤1e24 FLOPs）计算损失。
2. 拟合扩展定律，预测目标规模（1e25 FLOPs）的损失。

**用途**：
1. 用小规模实验优化大目标的训练配方。
2. 预测目标规模损失 → 可用于筹集资金（"我能得到 GPT-5 级别模型，请给钱"）。

**重要纠正**：扩展定律不是自然法则，不会自动出现，必须通过精心构建训练配方"召唤"出来。且配方必须能够外推——需要**超参数迁移**（如 μP），从小规模到大规模超参数要么相同要么是预测函数。

**核心权衡**：可预测性 ≥ 最优性。

**经典扩展定律**：给定 FLOPs 预算 C，应该用更大的模型（N）还是更多 token（D）？Kaplan 和 Chinchilla 的结论：**D ≈ 20N**（70B 参数模型应训练 ~1.4T token）。注意：这未考虑推理成本——现在很多模型训练 token 远超计算最优，因为推理时想要更小模型。

**Marin 项目实例**：预先注册不同计算预算下的损失预测，外推到 1E22 FLOPs，实时跟进训练是否匹配预测。

**作业 3 内容**：给定训练 API（超参数 → 损失），提交训练任务收集数据点，拟合扩展定律，外推提交预测，排行榜最小化给定 FLOPs 预算下的损失。

### 4. 数据（对应作业 4）
**核心**：数据质量决定模型上限。数据反映你希望模型拥有的能力（多语言？对话？智能体编码？）。

**评估**：先定义能力，才能谈数据。
- 两类评估指标：
  - **内部指标**（模型开发）：困惑度，需要跨规模平滑性，相对性能重要。
  - **外部指标**（报告结果）：生态效度重要，如 GPQA、SWE-Bench。
- 必须多样化评估——语言模型是通用系统，平均值会掩盖差异。
- 困惑度仍是捕捉模型本质质量的好指标；评估数据最好不来自互联网，避免污染。

**数据获取与处理**：
- 来源：网页爬取、书籍、arXiv、GitHub、The Pile 等。
- 法律问题：合理使用（fair use）争议、GitHub 代码许可证问题、数据授权（Google 与 Reddit 交易）。
- 处理步骤：
  1. **转换**：HTML/PDF 转为文本。
  2. **过滤**：分类器去除低质量/有害内容。
  3. **去重**：Blom filter 或 MinHash，节省计算、避免记忆化。
  4. **数据混合**：各来源权重调整（RegMix、OLMo Mix）。
  5. **合成数据**：LM 改写真实数据，更接近下游任务（WRAP）。

- 数据类型：预训练数据（大规模多样）、中训练数据（高质量、长上下文的最后阶段）、后训练数据（对话、工具调用的智能体轨迹）。

**作业 4 内容**：从原始 Common Crawl 开始，完成 HTML→文本转换、质量过滤分类器训练、MinHash 去重；排行榜最小化给定 token 预算下的困惑度。

### 5. 对齐（对应作业 5）
**为什么弱监督**：批评比生成更容易——你未必有"正确回应"的数据，但可以定义"好的表现"。

**基本模板**：
1. 模型生成回应。
2. 用人类/验证器/LM 裁判打分。
3. 更新模型偏好更好回应。

**算法**：PPO、DPO（偏好数据简化版）、GRPO（去掉价值函数）。

**挑战**：RL 算法不稳定、难调参；大规模 RL 有系统层面挑战——推理服务器生成 rollout，训练服务器更新，需要持续平衡系统效率和策略一致性（on-policyness）。

**作业 5 内容**：去年实现 DPO 和 GRPO（在数学基准上），今年可能向更真实方向推进。

## Tokenization 详解

### 基本定义

```
Tokenizer: 原始输入（字节） ↔ 整数序列（tokens）
```

出发点：原始文本是 Unicode 字符串；语言模型在 token 序列上放置概率分布。

**关键观察**：
- "hello" 和前面带空格的 " hello" 是两个完全不同的 token，索引无关联。
- 数字可能每几位 digit 一个 token。
- tokenizer 必须保证往返一致性（encode/decode 不丢失信息）。
- 压缩比 = 字节数 / token 数。压缩比越大序列越短（注意力是二次复杂度），但增大词汇量会导致稀疏性（每个词元被独立处理，越来越多的元素变罕见）。多语言 tokenizer 词汇量常达 10–20 万。

### 三种朴素方案的缺陷

| 方案 | 思路 | 缺陷 |
|------|------|------|
| **字符级** | 每个 Unicode 字符 = 一个 token | ~15 万词汇量太大；许多字符稀有；压缩比差 |
| **字节级** | 每个 UTF-8 字节 = 一个 token | 压缩比 = 1，序列过长；注意力二次复杂度下不可接受 |
| **词级** | 按空格/正则切分 | 词汇量可能无界；新词需 UNK token，破坏困惑度计算 |

### BPE 算法

**起源**：1994 年 Philip Gage 提出用于数据压缩；2016 年 Sennrich 引入 NLP（神经机器翻译）；GPT-2 首次用于 LLM。

**核心思想**：在原始文本上训练 tokenizer，构建定制词汇表。**任何内容都可以被分词**——常见序列一个 token，稀有序列分割成多个 token。

**训练流程**（以 "the cat in the hat" 为例）：

```
1. 初始：每个字节 = 一个 token（0-255）
2. 循环 num_merges 次：
   a. 统计相邻 token 对出现次数
   b. 找到最高频 pair（如 (116, 104) = "th"）
   c. 创建新 token（如 256），加入词汇表
   d. 将序列中所有该 pair 替换为新 token
```

**编码流程**：对每个新字符串，遍历所有已学习的 merge 操作，依次应用。

**作业 1 效率改进方向**：
1. **当前 encode() 遍历所有 merges（≈ vocab_size - 256）非常慢** → 只遍历相关的 merges，需要构建索引。
2. **特殊 token**（如 `<|endoftext|>`）的检测与保留。
3. **预分词**（pre-tokenization）：真实实现将文本先按正则切块，再对每块应用 BPE，大幅加速。
4. **考虑用 Rust/C 实现**——Python 不够快。

### Tokenization 的未来

**理想**：真正的端到端字节级建模（ByteNet、Megabyte、BLT、TFREE 等已有探索），但尚未扩展到前沿规模。

**任何替代方案必须满足**：
1. 模型应该在序列的块/抽象表示上操作（不仅针对文本，也针对视频、DNA 序列——单字节信噪比太低）。
2. 分块应该是**可变**的（自适应计算），不是所有字节一视同仁。

## 常见误区

1. **"苦涩的教训 = 规模决定一切"** → 正确理解是"能扩展的算法才重要"，效率在规模越大时越关键。
2. **"小规模实验的优化在大规模同样有效"** → FLOPs 分布（注意力 vs MLP）和涌现行为都随规模变化，直觉不完全可迁移。
3. **"扩展定律会自动成立"** → 需要精心构建训练配方并保证超参数可迁移，否则预测不可靠。
4. **"困惑度是唯一有效的评估指标"** → 困惑度适合内部开发，外部使用需要生态效度高的基准，且两者不能混为一谈。
5. **"字符级或字节级分词方案可行"** → 压缩比太差，注意力二次复杂度下序列过长不可接受。
6. **"BPE 实现正确即可"** → 朴素实现遍历所有 merges，效率极低，真实场景需要索引化和预分词。
