# 从单个 GPU 到千卡集群：语言模型训练的并行化之路

## 导语

当我们在单块 GPU 上训练语言模型时，关注的是如何通过融合（fusion）、分块（tiling）等技巧减少内存访问。但如果目标是一万亿参数规模的模型，或者我们希望利用更多 GPU 来加速训练，问题就变成了：如何让成百上千块 GPU 协同工作？

这正是 CS336 Lecture 7 的核心议题。在上一讲中，我们深入 GPU 内部，理解了流式多处理器（streaming multiprocessors）、高带宽内存（High Bandwidth Memory）和缓存层级。现在视野要放宽——从单 GPU 扩展到多 GPU，甚至多节点集群。课程明确指出，这两种情况遵循同样的原则：计算单元与数据相距遥远，核心目标是编排计算，避免数据传输瓶颈。

本文将从集合通信原语出发，介绍 GPU 互联的硬件基础，然后逐步剖析三种基本的并行化策略：数据并行、张量并行和流水线并行。通过这些内容，你将理解分布式训练的核心计算模式，为后续学习更高级的 FSDP/ZeRO 技术打下基础。

## 第一部分：分布式通信的构建模块

### 集合通信：分布式编程的经典原语

并行编程并非为语言模型训练而发明。课程强调，集合通信操作（collective operations）的历史可以追溯到 1980 年代，它们是分布式编程的基本原语，今天依然是我们使用的核心工具。所谓"集合"，意味着你指定的是跨多个设备的通用通信模式，而不是管理某块 GPU 如何与另一块 GPU 点对点通信。这让系统能自动完成大量工作。

在描述这些操作前，需要明确两个基本概念：**秩（rank）** 指一个特定设备（这里是 GPU），**世界大小（world size）** 指设备总数。假设我们有四个秩，世界大小为 4。

课程将集合操作分为两类：前四个——广播（broadcast）、散射（scatter）、收集（gather）、归约（reduce）——是理解后续操作的基础；后四个——全收集（all-gather）、归约散射（reduce-scatter）、全归约（all-reduce）、全对全（all-to-all）——才是语言模型分布式训练中反复出现的核心操作。

**广播（Broadcast）** 是最简单的操作：秩 0 拥有某个张量 [0, 1, 2, 3]，广播后将这个张量复制到所有秩上。广播不直接出现在训练核心路径中，但常用于初始化——例如秩 0 加载初始检查点后广播给所有秩。这类操作只需执行一次。

**散射（Scatter）** 将秩 0 上的大张量按照世界大小分割，然后分发到不同秩上：秩 0 得到第 0 个分量，秩 1 得到第 1 个分量，依此类推。课程指出，散射本身不直接使用，但理解它是理解归约散射的关键。散射的直觉是：让被散射到的 GPU 各自在不同数据部分上做本地计算。收集（Gather）是散射的逆操作——把所有分片拼接回一个秩上，它是理解全收集的基石。归约（Reduce）则对分布在各秩上的数据应用某种结合律和交换律的操作（求和、最大值、最小值），结果放到秩 0。

如果对 NumPy 的广播概念感到熟悉，课程也专门澄清了这一点：概念上都是"一个东西变成很多东西"，但集合通信实现的是跨设备的通信模式，与 NumPy 的数组广播有本质区别。

### 真正驱动训练的核心操作

**全收集（All-gather）** 对所有秩执行收集操作，而不仅是秩 0。这是后面反复出现的模式：每个秩持有参数的一部分分片，真正做前向传播时，需要先全收集这些分片，得到完整参数。课程预演了训练中的典型模式：先 gather 做点事情，然后 scatter，再 gather，再 scatter。

**归约散射（Reduce-scatter）** 在每个维度上执行归约，然后把结果散射到不同的秩。具体来说，假设四个设备分别拥有向量，第一个维度求和得到 6 放到秩 0，第二个维度求和得到 10 放到秩 1，依此类推。课程预告了它的应用场景：反向传播后，不同 GPU 处理了不同数据，需要对梯度分片求和，然后重新分配存储。

**全归约（All-reduce）** 可以看作归约散射加上全收集的组合：对所有张量做归约（求和），然后把结果复制到所有秩。这是数据并行中最直接的操作。课程指出，更高级的技术如 ZeRO 或 FSDP 需要把全归约拆分成归约散射和全收集，这样才能介入中间过程，精细管理内存。但对基础版本来说，全归约就足够了。

**全对全（All-to-all）** 是最通用的操作。它精确指定每个秩如何向其他秩发送特定消息，本质上可以理解为矩阵转置（当切分均衡时）。全对全在混合专家模型（MoEs）中至关重要：每个秩既有数据切分，又有一组专家子集，需要根据动态路由将激活值发送到正确的专家。课程强调了负载均衡的重要性——回忆 MoE 那一讲的内容，理想目标就是让 all-to-all 看起来像均等的转置操作。

理解这些术语有个技巧：归约就是对结合律交换律的操作（求和、最值）进行归约；散射是收集的逆操作，散射是分发，收集是集中；"全"（all）意味着目的地是所有设备。

### GPU 互联的硬件现实

课程从一张"老旧的经典图片"讲起传统服务器架构：CPU 通过 PCIe 总线连接 GPU 和内存，不同计算机通过以太网相连。这种拓扑下，同一节点的 GPU 走 PCIe 通信，跨节点必须经过以太网——这一切就像买了游戏 GPU 后和朋友组网来训练大模型。

认真做训练的数据中心则完全不同。典型设置是每个节点有 8 块 GPU，通过 NVIDIA 的 NVLink 连接到交换机（NVSwitch）。课程给出了参照：NVLink 5.0 能提供每秒 1.8 TB 的总带宽，而 B200 的 HBM 是每秒 8 TB——大约慢了 4 倍。这仍然很快，但绝对不如 HBM，更远不及共享内存或 L1 缓存。

从编程角度看，NVLink 连接到交换机意味着任意 GPU 可以认为能直接与任意其他 GPU 通信，硬件负责路由。但随着规模增长，节点组成 pod，pod 之间通过 InfiniBand 连接，GPU 需要经过 PCIe、InfiniBand 线缆，速度大幅下降。再往外是以太网，需要经过 PCIe 和 CPU，速度更慢。这正好呼应了内存层级的直觉——节点越多，通信越慢。

课程特别强调了一个关键概念：**RDMA（远程直接内存访问）**。标准以太网通信中，GPU 必须把数据拷贝到 CPU 的 socket 缓冲区，构建网络包，再拷贝到网络接口发送，引入大量延迟。RDMA 允许 GPU 直接读写另一块 GPU 的内存，完全不经过 CPU。NVLink/NVSwitch 环境天然支持 RDMA，InfiniBand 也支持。但标准以太网不支持。

两个值得一提的进展：一是 NVIDIA 的 NVL72 产品——9 个托盘、每个托盘 8 块 GPU，总共 72 块 GPU 可以通过 NVSwitch 连入一个 NVLink 域，让普通人也能获得大范围的快速互联。二是 **RoCE（融合以太网上的 RDMA）**，以太网域中的 RDMA 方案，绕过了 CPU，是 InfiniBand 的廉价替代品，Meta 有论文展示了这一方向的探索。

在编程层面，**NCCL（NVIDIA 集体通信库）** 把集合操作翻译成 GPU 之间发送的实际底层数据包。课程指出，NCCL 会检测硬件拓扑，找出不同 GPU 之间的路径，启动 GPU 内核来发送接收数据——因为 GPU 上的一切最终都是内核。我们不会深入 NCCL 内部，但需要知道它存在。PyTorch 提供了 torch.distributed 库，封装了这些集合操作的简洁接口，支持不同后端：GPU 上用 NCCL，CPU 上用 gloo（并行处理在 GPU 出现之前就存在了，CPU 上也能执行集合操作）。

### 用代码验证概念

课程通过实际代码演示了这些操作。这里的关键设计是：直接运行课程代码会使用多进程（multiprocessing），每个进程对应一个秩；但在课堂逐步演示时，使用的是特殊的单进程模式，避免多进程的复杂性。

第一个示例是全归约。每个秩创建一个张量 [0, 1, 2, 3] 加上自己的秩号，所以秩 0 有 [0, 1, 2, 3]，秩 1 有 [1, 2, 3, 4]，依此类推。全归约后，每个秩得到的都是各列之和，结果在所有秩上完全一致。课程特别提醒：打印语句出现的顺序取决于硬件，因为进程是异步运行的。这里引入了 **barrier（屏障）** 同步操作——确保所有进程都到达某个执行点后再继续。过度使用屏障会带来不必要的等待。

第二个示例是归约散射。输入是各秩手中的向量，执行归约散射后，输入保持不变，但输出张量在每个秩上得到了对应分量归约后的结果。第三个示例是全收集：以上一步归约散射的输出作为输入，分配输出张量后，执行全收集，所有不同的输入被收集到所有秩上——这正好通过实例验证了"全归约 = 归约散射 + 全收集"。

### 测量通信带宽

课程接着演示了如何测量通信速度。这个环节延续了计算 MFU（模型浮点运算利用率）时的思路：测量有效带宽。对一亿个元素做全归约，预热后开始计时。这里需要考虑两种异步性：CUDA 内核相对于进程是异步的，进程之间也是异步的。因此既要调用 `torch.cuda.synchronize()` 等待 CUDA 内核完成，也要调用 barrier 等待所有进程到达。

有效带宽的计算方式是：发送的字节数除以总持续时间。对于全归约，实际发送的字节数需要一些解释。假设秩 0 加秩 1 加秩 2 加秩 3，需要迭代世界大小减 1 步（因为有世界大小减 1 次加法），因子 2 是因为既需要发送又需要接收（归约）。总持续时间是墙上时钟时间乘以世界大小——因为所有秩都在等待。课程指出一个有趣的性质：随着世界大小增加，表达式约等于 2 乘以数据字节数除以持续时间，也就是说，有效带宽与世界大小无关，也与拓扑结构无关——环形还是树形由 NCCL 决定。

对于归约散射，带宽计算没有 2 倍因子。课程强调：由于全归约等于归约散射加上全收集，全归约自然移动两倍的数据量，需要两倍的时间，但两者相抵消，得到相同的带宽。

## 第二部分：三种并行化策略

课程进入核心部分：通过一个简洁的 MLP 训练实现，从零开始讲解数据并行、张量并行和流水线并行。之所以选 MLP，是因为 Transformer 中 MLP 才是计算瓶颈所在，这非常能代表真实情况。这里所有的并行化都通过切分数据和参数来实现。课程给出的示意图是概念性的：数据并行切分数据，张量并行切分宽度（每层的一部分），流水线并行切分深度（层数）。

### 数据并行：最优雅的起点

课程用"数据并行就是切分批次维度，每个 GPU 保留所有参数，做正常的模型训练，然后同步"这句话精炼概括了核心思想。具体实现中，先从 128 行、1024 维的数据矩阵出发，按世界大小切分行——每个秩获得 32 个数据点（本地批次大小 local batch size）。在实践里，每个秩应该自己加载自己的数据，而不是通过主进程加载再分发——课程只是为了说明问题才这样做。

MLP 有若干层，每层是一个 1024×1024 的参数矩阵。训练循环是标准的：前向传播遍历层，应用激活函数；反向传播计算梯度；关键是反向传播之后多了至关重要的一步：**对所有参数做全归约（ReduceOp.AVG 均值）**。这是标准训练和 DDP（Distributed Data Parallel）之间唯一的区别。课程认为这非常优雅："基本上就是标准训练，把训练应用到本地批次上，但只是在反向传播之后插入了这一步。"

课程解释了数据并行的两个前提：批次大小至少要等于世界大小才有意义（实践中通常远大于），最好能整除世界大小，否则可能需要用零填充。

数据并行的一个显著优势是模块化：DDP 只关心对参数做平均，并不关心前向传播长什么样。因此对 Transformer 模型同样适用。但它的局限也很明显：需要在内存中保存所有模型参数。如果参数放不进内存，就需要更聪明的方式——这正是下一课 FSDP 和 ZeRO 的主题。

分析师们会注意到，数据并行中每个秩的损失不同（基于本地数据计算），梯度最初也不同，但通过全归约，梯度在所有秩间变得相同，因此参数也始终保持一致。这就是数据并行的收敛保证。

### 张量并行：切分每层，收集激活

与数据并行不同，张量并行不切分数据，而是切分每一层。每个秩获得每层的一部分参数，因此需要在每层之后通信激活值。课程采用按列切分（称为列张量并行 column tensor parallel），也可以按行切分。

具体实现中，本地维度数量（local num dim）是每个秩负责的维度子集大小。前向传播中，每个秩计算自己那部分参数对应的激活值（形状为批次大小×本地维度），然后需要把所有这些激活值放到所有秩上——这正是全收集操作的应用场景。简单来说：每层计算后，分配激活值列表，执行全收集，拼接成完整维度的数据，继续下一层。

张量并行的一个关键区别是：它必须修改模型本身，而不像数据并行那样把模型当作黑盒模块。它利用的核心事实是：矩阵乘法可以拆分成一组更小的矩阵乘法，让不同秩各自计算再收集结果。

关于反向传播，课程明确了一个要点：如果在张量并行中直接调用 `.backward()`，并不会自动做所需操作，因为其中没有并行性。实践中有高层封装自动处理这些，但课程刻意保持低层次，让学习者理解机制。反向传播中，梯度的分布对应着前向传播的逆操作：通过归约散射将梯度分发到所有设备。因此可以说，某种意义上的对偶关系存在于前向和反向：前向是全收集，反向是归约散射。

### 流水线并行：切分深度，减少气泡

流水线并行的思路是按深度切分网络：每个秩获得一部分层，但每层内部拥有所有维度。所有秩以某种形式看到所有数据。

实现的核心是**微批次（micro-batches）**概念。除拆分层外，还要把批次拆分成多个微批次。具体流程是：秩 0 获得数据，分块成微批次；对每个微批次，从前一个秩接收（receive），只在分配给本秩的层上做前向传播，然后发送（send）给下一个秩。代码中使用点对点操作 `dist.recv` 和 `dist.send`，它们比集合操作更直接但同样直观。

引入微批次的原因正是为了解决**流水线气泡（pipeline bubble）**问题：当等待其他张量被处理时，GPU 处于空闲状态。把数据分解成更小的批次，就能快速处理并发送到下一个秩，减少气泡数量。课程承认，这个朴素的实现没有处理**通信与计算重叠**的问题，而这在实际流水线并行中至关重要。理想的做法是在计算的同时接收或发送数据——给操作加上异步标志并编写更多管理代码。

课程还指出流水线并行中常见的范式：通信与计算重叠。数据并行中同样存在这种机会，一旦梯度计算完成就可以开始发送，不必等所有梯度都算完。这是作业二将探索的内容。

### 并行化策略的选择与缺失环节

除了上述三种，还有更多并行化类型：序列并行（切分序列，允许并行化注意力计算）、专家并行（为 MoE 并行化专家，全对全在此发挥作用），以及不同技术的组合。

并行化技术的选择强烈依赖于硬件互连能力。张量并行通信量大——每一层都需要发送相当规模的激活值，因此通常局限在节点内部使用 NVLink/NVSwitch 这类高带宽环境，不会跨越 NVLink 域。流水线并行则能容忍慢得多的互连，甚至可以在跨地域的去中心化训练中工作。典型的组合是：节点内部用张量并行，节点间用数据并行（或 FSDP），需要时再叠加流水线并行。

数据并行也有其极限：当批次大小增大到某个**临界批大小**后，继续增加不再有帮助，大量算力浪费在同步上，此时更好的选择是转向张量并行。这些决策需要计算和权衡。

课程最后对比了 PyTorch 与 JAX/TPU 生态的哲学差异。PyTorch 路线让你用原始集合操作从机制上看到发生了什么；JAX 路线则可以简单地定义模型和起始策略，编译器负责处理需要什么样的通信操作——你只需说明"这份数据需要放在这里、这里还有这里"，编译器施展魔法。这很吸引人，但课程带着一点幽默说："它会夺走很多从零开始构建东西的乐趣。"

## 结语

回到课程开始提出的问题：为什么需要多 GPU？答案是双重的——参数、激活值、梯度或优化器状态无法容纳在单 GPU 内存中；即使能容纳，拆分到更多 GPU 上也能利用更多算力训练更快。但代价是通信带宽的开销，这需要仔细计算如何并行化。

本讲建立了一个统一的视角：在单 GPU 和多 GPU 的情况下，原理相同——计算单元与数据相距遥远，核心是编排计算以避免传输瓶颈。上周用融合和分块减少内存访问，本周用复制和分片减少 GPU 间通信。这是一个从单 GPU 到多 GPU，从快速缓存到慢速网络的完整层级结构。

值得一提的是，课程最后给出了硬件发展的长期判断：尽管硬件在变快，但我们总是想要更大的模型，因此这种层级结构的思想会持续存在。正如内存层级中我们有 L1、L2、HBM、主存，"你要么重新计算，要么存储在内存中，要么存储在另一块 GPU 的内存里并通过通信获取"——这不仅是技术选择，更是设计哲学。

下一讲将由 Tatsu 深入讲解更先进的数据并行技术——FSDP 与 ZeRO。它们用全收集和归约散射的组合替代简单的全归约，在保留数据并行优雅性的同时，规避了"所有参数都在内存中"的限制。理解本讲的集合原语与三种基本并行化策略，正是迎接这些高级技术的最佳准备。
