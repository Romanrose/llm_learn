## 1. 张量与数据类型

### 1.1 张量是基础构建块

在深度学习中，所有数据——参数、梯度、优化器状态、激活值——都是张量(Tensor)。例如 DeepSeek 3.2 模型的参数就是一组不同形状的张量。

每个张量具有：
- **秩(rank)**：维度数量。例如 `torch.zeros(4, 8)` 是秩 2 的矩阵
- **数据类型(dtype)**：决定每个元素占用的字节数

### 1.2 浮点数精度详析

**float32 (fp32)**——默认精度
- 组成：1 位符号位 + 8 位指数位 + 23 位尾数
- 每个元素 4 字节
- 在深度学习中使用 fp32 往往过于浪费

**float16 (fp16)**——半精度
- 组成：1 位符号位 + 5 位指数位 + 10 位尾数
- 每个元素 2 字节
- **问题**：动态范围差，`1e-8` 下溢为 0，训练中易出现 NaN

**bfloat16 (bf16)**——Google Brain 2018 年开发
- 组成：1 位符号位 + 8 位指数位 + 7 位尾数
- 与 fp32 相同的动态范围，但分辨率更差
- 深度学习训练过程粗糙，高分辨率并非必需，因此 bf16 是很好的折中

**fp8**——2022 年标准化
- 两种变体：E4M3（范围 [-448, 448]）和 E5M2（范围 [-57344, 57344]）
- 由 NVIDIA Transformer Engine 支持

**fp4**——NVIDIA 2025 年开发
- 仅 4 比特，所有可能值从 -6 到 6
- 实际应用时使用分块缩放(block scaling)，每块可整体放大或缩小
- Nemotron 3 Super 使用 fp4 训练

**混合精度训练**
- 通用规则：参数、激活值、梯度用 bf16，优化器状态用 fp32
- PyTorch 提供 AMP 库自动处理，在安全处（如矩阵乘法）使用低精度，在危险处（如指数运算）保持 fp32

### 1.3 内存计算基础

内存占用 = 元素个数 × 每元素字节数

示例：4×8 的 fp32 张量占用 128 字节。GPT-3 前馈层中一个矩阵约 2.3 GB。

**关键操作**：PyTorch 默认张量在 CPU 上，需要显式 `.to(device)` 移到 GPU。

## 2. einops：命名维度的张量操作

### 2.1 动机

传统 PyTorch 代码中的 `x.transpose(-2, -1)` 容易混淆维度。einops 用命名维度替代索引，代码更清晰、不易出错。

**einsum**——带记账的广义矩阵乘法
```python
z = einsum(x, y, "seq1 hidden, hidden seq2 -> seq1 seq2")
```
- 命名出现在输出中的维度保留
- 未出现在输出的维度（如 `hidden`）自动求和

**reduce**——sum/mean/max/min 的推广
```python
y = reduce(x, "... hidden -> ...", "sum")
```
- `...` 代表任意数量的批量维度
- 右侧未出现的维度被聚合

**rearrange**——重塑与分解
```python
# 将 total_hidden 分解为 heads × hidden1
x = rearrange(x, "... (heads hidden1) -> ... heads hidden1", heads=2)
# 处理后合并
x = rearrange(x, "... heads hidden2 -> ... (heads hidden2)")
```
- 括号表示维度的合并或分解
- 分解时需指定其中一个维度的值

### 2.2 实际优势

在反向传播中，einsum 使维度推导变得清晰：
- 通过形状匹配确定索引顺序，无需记忆转置规则

## 3. 计算量核算：FLOPs

### 3.1 术语澄清

- **FLOPs**（小写 s）：浮点运算次数，衡量已完成的计算量
- **FLOP/s 或 FLOPS**（大写 S）：每秒浮点运算次数，衡量硬件速度

注意 H100 规格表中的 1979 teraFLOP/s 包含稀疏性(sparsity)，稠密计算需除以 2。

### 3.2 矩阵乘法 FLOPs

对于 B×D 与 D×K 的矩阵乘法：
```
FLOPs = 2 × B × D × K
```
原因：对每个 (i, j, k) 三元组，做一次乘法和一次加法。

直观理解：**线性层 FLOPs = 2 × token数 × 参数量**。这正是 Transformer 6ND 公式的雏形。

### 3.3 其他操作

- 逐元素操作（如加法）：FLOPs = 矩阵大小
- 对于足够大的矩阵，矩阵乘法主导所有其他操作

## 4. 实际性能与 MFU

### 4.1 测量实际性能

```python
torch.cuda.synchronize()  # 等待 GPU 异步任务完成
time = benchmark(lambda: x @ w)  # 多次运行取平均
actual_flop_per_sec = num_flops / time
```

### 4.2 模型 FLOPs 利用率 (MFU)

```
MFU = 实际 FLOP/s ÷ 规格书 FLOP/s
```

- MFU ≥ 0.5 是良好水平
- 纯矩阵乘法可达 0.8
- 若 MFU 约 0.1，说明需要优化

## 5. 算术强度与 Roofline 模型

### 5.1 为什么 MFU 不到 1？

需要从加速器架构角度理解：
- **HBM**（高带宽内存）→ **加速器芯片**（计算核心）
- 每步计算需：从内存发送输入 → 计算 → 发回输出
- 时间取决于：计算速度（FLOP/s）和内存带宽（bytes/s）

### 5.2 关键比量

**加速器强度**：每传输 1 字节可做多少计算
```
H100: 1979e12/2 FLOP/s ÷ 3.35e12 bytes/s ≈ 295 FLOPs/byte
```

**算术强度**：工作负载的 FLOPs ÷ 字节数

**判断标准**：
- 算术强度 < 加速器强度 → **内存受限**(memory-bound)
- 算术强度 > 加速器强度 → **计算受限**(compute-bound)

### 5.3 各操作算术强度分析

| 操作 | 算术强度 | 类型 |
|------|---------|------|
| ReLU | ~0.25 | 内存受限 |
| GELU | ~5 | 内存受限（即使计算量是 ReLU 的 20 倍）|
| 点积 | ~0.5 | 内存受限 |
| 矩阵-向量乘 | ~1 | 内存受限 |
| 矩阵-矩阵乘 | ~n/3 | 计算受限（n=1024 时约 340）|

**关键洞察**：
- ReLU 和 GELU 的隔离性能相同，因为瓶颈在内存，不在计算
- 矩阵乘法因数据量 O(n²) 但计算量 O(n³)，具有高算术强度
- Transformer 设计即保证大矩阵乘法主导，这是刻意的架构选择

### 5.4 推理 vs 训练

- 推理逐 token 生成 = 矩阵-向量乘 → 内存受限
- 训练处理整个序列 = 矩阵-矩阵乘 → 计算受限

## 6. 梯度计算与 6ND 公式

### 6.1 反向传播 FLOPs

对于一层 h2 = h1 @ w2：
- **前向**：2 × B × D × D FLOPs
- **反向**：需计算两个梯度
  - h1.grad = h2.grad @ w2ᵀ → 2 × B × D × D
  - w2.grad = h2.gradᵀ @ h1 → 2 × B × D × D
  - 总计 4 × B × D × D

反向传播恰好是前向的 2 倍。

### 6.2 6ND 公式推导

对 L 层网络，每层 D² 参数：
- 前向：2 × B × (D² × L) = 2 × token数 × 参数量
- 反向：4 × token数 × 参数量
- **总计：6 × token数 × 参数量 FLOPs/步**

此公式对短上下文的 Transformer 也是良好近似。上下文很长时，注意力 O(L²) 项会有额外贡献。

## 7. 训练内存核算

### 7.1 内存组成

以 Adam 优化器为例（每参数 4+4=8 字节状态）：

| 组件 | 每参数字节数 |
|------|------------|
| 参数(bf16) | 2 |
| 梯度(bf16) | 2 |
| 优化器状态(fp32) | 8（Adam 需要一阶矩+二阶矩）|
| **总计** | **12** |

80GB H100 上最大模型规模：80e9 × 8 ÷ 12 ≈ 530 亿参数
注意：未计入激活值，实际取决于批大小与序列长度。

### 7.2 内存的双重作用

- **容量限制**：决定能否容纳大模型
- **速度影响**：数据传输耗时，优化器状态虽不主导计算，但影响能加载的模型大小

## 8. 内存优化技术

### 8.1 梯度累积 (Gradient Accumulation)

问题：大 batch 提高训练稳定性，但激活内存随 batch 线性增长。

方法：
- 在微批次上计算梯度并累积（不调 zero_grad）
- 每 batch_size/micro_batch_size 步更新参数并清零

激活内存降为：2 × micro_batch_size × D × L

### 8.2 激活检查点 (Activation Checkpointing)

**思想**：训练需要存储所有层激活值（内存 O(L)），推理不需梯度仅存当前层。

**实现**：前向时只保留部分层的激活值；反向时从最近检查点重算缺失激活。

- 不检查点：内存 O(L)，无需重算
- 完全不存储：内存 O(1)，计算 O(L²)——每层都从头算
- **平衡方案**：每 √L 层存一个检查点 → 内存 O(√L)，计算 O(√L)

## 常见误区

1. **混淆 FLOPs 与 FLOP/s**：前者是工作总量，后者是速率
2. **忘记 H100 规格要除以 2**：稀疏性虚高
3. **盲目追求大 batch**：忽略激活内存线性增长
4. **认为 ReLU 比 GELU 快**：隔离性能相同，因为内存带宽是瓶颈
5. **忽略 GPU 异步性**：不调用 `cuda.synchronize()` 的计时结果虚低
6. **训练推理混淆**：推理是矩阵-向量乘（内存受限），训练是矩阵-矩阵乘（计算受限）
